## 一句话概括

**灰度发布问的是"会不会出事"，A/B 测试问的是"哪个更好"。** 前者是技术决策（降低爆炸半径），后者是业务决策（用数据选方案）。面试里这两个概念经常被混着问，混着答就露怯。

前端做这两件事时，真正麻烦的是三个问题：

1. **落点选在哪**——网关、前端资源、功能开关，还是埋点？每个落点的回滚速度和粒度完全不同；
2. **分流怎么算**——用随机数分流的实验，数据基本是废的（第 4 节有实测数字）；
3. **怎么不闪**——客户端改 DOM 的方案天然会闪，而闪烁会**系统性地污染结果**，不只是体验问题（第 5 节）。

## 核心知识点

### 1. 先分清两件事：目标不同，指标不同，结束条件不同

| 维度 | 灰度（金丝雀） | A/B 测试 |
|---|---|---|
| 目的 | 降低新版本的爆炸半径 | 验证哪个方案在业务上更优 |
| 关注指标 | 错误率、延迟、崩溃率（**技术指标**） | 转化率、留存、GMV（**业务指标**） |
| 分流依据 | 按比例随机 / 白名单 / 设备渠道 | 按用户特征分组，**通常固定分组** |
| 时长 | 稳定就快速全量 | 必须跑满预计算样本量 |
| 结论形态 | "没出问题，继续放量" | "B 组赢，置信区间是……" |
| 失败处理 | 立刻缩量回滚 | 结论不显著 → 这个假设不成立 |

顺手把四个发布姿势记牢（高频追问）：

- **蓝绿**：两套完整环境，切流量。回滚最快（秒级切回），成本最高（双倍资源）。
- **金丝雀**：小流量先试，逐步放量。成本低，但需要**实时观测能力**，不然就是"慢慢放量、没人知道什么时候该停"。
- **滚动**：逐批替换实例。日常小迭代够用，但过程中新老版本共存，要能兼容。
- **红黑**：新环境上线、旧环境留几天当备胎。介于蓝绿和滚动之间。

一句话区分三者：**蓝绿是"换厨房"，金丝雀是"先请一桌客人试菜"，A/B 是"两种菜都上，看哪桌点得多"。**

### 2. 前端的四个落点：越靠内，回滚越快、粒度越细

- **网关 / CDN 层**：按比例、按 Cookie / IP 分流。对应用透明，但粒度粗，而且**只能切"整份资源"**，切不了"单个功能"。
- **应用层（前端资源版本）**：HTML 里引用 `main-a1b2c3.js` 还是 `main-d4e5f6.js`。**回滚 = 把 HTML 改回旧 hash**，不用发版、秒级生效。注意 CDN 缓存粒度：如果分流结果体现在 HTML 里，就必须保证 HTML 不被 CDN 缓存成单一版本（否则会出现"所有人都看到同一个变体"）。
- **功能层（Feature Flag）**：代码全量上线，功能按开关放开。**唯一能做到"秒关单个功能、且不用重新部署"的落点**，也是灰度与 A/B 共用的基础设施。
- **数据层（埋点归因）**：每个事件必须带上**实验 ID + 变体 ID**。少这一环，前三个落点做得再漂亮也拿不到结论。这是最容易被漏掉、也最贵的一环。

判断法则：**落点越靠内，回滚越快、粒度越细，代价是业务代码里留下的分支越多**——所以功能层的开关必须有回收机制。

### 3. Feature Flag 的前端实现：三条硬要求

- **① 求值必须同步**：首屏渲染前就要能拿到值。
- **② 必须有默认值兜底**：远端挂了、超时了，页面照常渲染。
- **③ 拉取绝不能阻塞渲染**：宁可所有人先用默认值，也不能白屏等网络。

```js
// ✅ 同步求值 + 默认值兜底 + 缓存优先
const DEFAULTS = { newCheckout: false, newHome: false }
let flags = { ...DEFAULTS, ...readCache() }        // 首屏：默认值 + 上次缓存

export const flag = (name) => flags[name] ?? DEFAULTS[name]  // 同步，永不 await

// 远端配置异步回来，只影响"下一次渲染"，绝不阻塞首屏
fetchFlags({ timeout: 800 }).then((next) => {
  flags = { ...flags, ...next }
  writeCache(next)
})
```

```js
// ❌ 反例 1：await 完才渲染 —— 白屏等网络
const flags = await fetchFlags()
renderApp(flags)

// ❌ 反例 2：用随机数在启动时分流，刷新一次就换组
const inNewHome = Math.random() < 0.5
```

还有一条工程纪律：**每个开关都要有"死期"**。开关用完不回收，半年后代码里全是 `if (flagA && !flagB)`，没人敢删——这才是 Feature Flag 最大的成本。

### 4. 分流算法：必须"稳定 + 单调"（本机实测）

正解只有一种写法：**用哈希，不要用随机数**。

```js
import { createHash } from 'node:crypto'

// experimentId 当 salt：不同实验之间互不相关
// userId 当输入：同一个用户永远落同一组
const bucket = (experimentId, userId, mod = 1000) =>
  parseInt(createHash('md5').update(experimentId + ':' + userId).digest('hex').slice(0, 8), 16) % mod

const inExperiment = (expId, uid, percent) => bucket(expId, uid) < percent * 10
```

实测数据（20000 个用户，本机 node 跑的）：

| 做法 | 结果 |
|---|---|
| `Math.random()` 当分流依据 | 同一用户两次分组的**失配概率 49.8%**（等于没分流） |
| `hash(expId + uid)`，同一个用户重复 5 次 | 结果完全一致 ✅ |
| 10 桶分布均匀性（20000 用户） | 2039 / 1980 / 1982 / 2008 / 2057 / 1940 / 2001 / 1980 / 1973 / 2040 |

**放量的正确姿势是"单调放大阈值"**，实测：

| 变更方式 | 原 A 组保持率 |
|---|---|
| 阈值 500 → 1000（单调放量） | **100%**（老用户不会跳组，新用户从原 B 组里补进来） |
| 取模位数 100 → 1000（看着等价，其实重洗） | **50.6%**（约一半人换了组） |
| 实验名 `exp-btn` → `exp-btn-v2` | **50.8%**（等于开了一个新实验） |

三种做法的差别在面试上是加分项：**"改百分比可以，改分桶空间或 salt 等于重开实验，之前的数据全废。"**

还有两件容易翻车的事：

- **分流实体必须稳定**。实测用 `sessionId` 分流，同一个用户三次会话落到 **A / B / B**；换成 `userId` 才是 **A / A / A**。未登录用户必须先落一个持久化的匿名 ID（localStorage/cookie），否则登录那一刻就换组，数据直接污染。
- **salt 用实验 ID，不要用模块名或固定字符串**。固定 salt 会让所有实验的 A 组成分完全相同，养出一批"专业 A 组用户"，各实验之间也不再独立。

### 5. 客户端 vs 服务端 / 边缘：闪烁是架构问题，不只是体验问题

客户端方案（JS 拿到配置后改 DOM）的天然缺陷是 **FOOC（flash of original content）**：页面先渲染了原始版本，脚本到位后才换成变体。

四种做法，代价各不相同：

| 做法 | 还闪吗 | 代价 |
|---|---|---|
| 异步加载脚本、不做处理 | 明显闪 | 无（代价转移给用户） |
| 脚本同步放在 `<head>` 顶部 | 基本不闪 | **阻塞**脚本下载与执行，首屏变慢 |
| anti-flicker（`.async-hide` 把整页藏起来等） | 不闪 | **页面被藏着**直到变体应用或超时，直接吃掉 LCP |
| 服务端 / 边缘（CDN 节点出 HTML） | 不闪 | 每个变体都要能落到应用代码里，工程成本最高 |

**为什么说闪烁会污染实验结论**：对照组只被渲染一次，变体组被"渲染 → 撤销 → 再渲染"。任何由这个切换引起的负面反应（困惑、点错位置、滚动位置丢失）**只发生在变体组**。于是你测到的其实是「变体效果 − 切换代价」，会系统性地低估变体。anti-flicker 把代价摊给了两组（两组都慢），所以它修的是"视觉不对称"，但整站的性能损失是**两组一起承担的、实验内部看不见的**。

选型建议：**文案 / 颜色 / 小布局 → 客户端够用；支付、定价、大布局改版、要测后端逻辑、跨端一致 → 必须服务端或边缘。**

顺带记一下工具层面的现状（面试提到会显得你还在跟进）：**Google Optimize 已于 2023-09-30 停服**（2023 年 1 月宣布），GA4 本身跑不了 A/B 测试、只能接收变体参数做分析；现在客户端阵营是 VWO / AB Tasty / Optimizely，服务端与开关阵营是 LaunchDarkly / Statsig / GrowthBook（后者开源可自托管）。

做这一块还要背四条 Google 官方规范（Search Central「A/B Testing Best Practices for Search」原文）：

- **不要 cloaking**："Don't show one set of URLs to Googlebot, and a different set to humans." 官方还专门提醒：**Googlebot 一般不支持 cookie**，所以用 cookie 控制实验时，爬虫看到的永远是"不接受 cookie 的用户"那个版本。
- **用 `rel="canonical"`**，官方推荐它而不是 `noindex`——你不想让首页不被索引，只想让搜索引擎知道这些测试 URL 是同一页的变体。
- **重定向用 302，不要用 301**，否则搜索引擎可能用变体 URL 替换掉原 URL；JS 重定向也可以。
- **实验别长期挂着**，"Run the experiment only as long as necessary"，结束后测试脚本和备用 URL 都要清掉。

### 6. 统计决策：p 值不是"胜率"

前端同学答 A/B 常栽在统计部分，记住四个点就够用：

**① 样本量对效应大小极其敏感**：`n ∝ 1/Δ²`——**效应减半，流量要翻四倍**。5% 的基线转化率下，想检出 20% 的相对提升大约要 1.6 万访客，想检出 5% 的相对提升要 24 万。所以"这个改动大概有 1% 提升，我们跑两天看看"基本等于白跑。

**② 中途窥视会把假阳性率抬高好几倍**（本机实测：用双比例 z 检验做 A/A 测试，重复 3000 次，每次每组 2000 样本）：

| 观察方式 | 实际假阳性率（名义 α = 5%） |
|---|---|
| 只看一次就决策 | 5.4% |
| 分 10 次窥视、一看到显著就停 | **20.4%** |
| 分 60 次窥视、一看到显著就停 | **33.2%** |

这就是"p 值 0.04 我们就上线吧"最危险的地方：**不是效果变好了，是你看了太多次。** 需要提前看，就要用 sequential testing 这类专门的方法，或者干脆只看 SRM 和错误率、不看效果。

**③ SRM（样本比例失衡）要当成第一道门禁**。计划 50/50，实际 503,000 / 497,000 —— 看着只差 0.6%，但 χ² = 36，p ≈ 1.9×10⁻⁹，绝非随机波动。**SRM 一旦不过，任何结论（无论正负）都不能用**，先查上游：分流代码、缓存层、爬虫过滤、JS 报错。两个细节：算 SRM 要用**被分配的唯一用户数**，不能用会话数（变体提高了活跃度会让会话数天然失衡）；平台通常用比 0.05 严格得多的阈值（p < 0.01 甚至 0.001 量级）。

**④ 辛普森悖论与多重比较**：整体提升、每个分层都在跌，是流量在层间分布不均造成的（按设备、新老用户分层各看一遍就能发现）。一次实验挂了 14 个独立指标、每个按 α = 0.05 看，**至少出现一个假阳性的概率约 51%**（1 − 0.95¹⁴）。

所以专业的做法是**预登记**：实验开始前定好**一个主指标 + 一小串护栏指标（不能被搞坏的东西：错误率、延迟、收入）**、算好样本量、定好结束日期，跑满再看；报告给置信区间和效应量，而不只是一个 p 值。最后一句自问：**置信区间的下界，在业务上有意义吗？**

## 其实你每天都在用

- **App 里的"新功能体验"弹窗**：那个开关就是 Release Flag，出问题直接关，不用等发版审核。
- **大促时"临时关掉推荐计算"**：Ops Flag，用开关换系统形态，属于保命手段。
- **`localStorage` 里那个 `ab_variant` 字段**：前端实验最常见的落点，也是"同一用户换组"事故的高发地。
- **埋点里多出来的 `exp_id` / `variant`**：数据同学做实验分析全靠它，没有它整个实验白做。
- **测试页面先白一下再出现内容**：anti-flicker 在藏页面，你看到的"白"是它的工作时间。
- **同一个页面在 Safari 上看到 A、在 Chrome 上看到 B**：分流实体取错（大概率取了设备或会话级 ID）。
- **Nginx 里那段按 Cookie 转发的配置**：最朴素的网关层灰度，前端同学迟早要跟运维一起调它。
- **灰度期间线上出现的"两个人看到不一样"**：这不是 bug，是新旧版本共存期的正常状态，前提是后端接口必须双向兼容。

## 常见误解（FAQ）

**❌ 误区 1：「灰度和 A/B 测试是一回事，都是放一部分流量」**

机制像，目标完全不同：灰度看**技术指标**，稳定就全量；A/B 看**业务指标**，必须跑满样本量才能下结论，而且结束条件和时间都更长。把 A/B 当灰度做（两天出结论就全量）是最常见的浪费。

**❌ 误区 2：「用 `Math.random()` 分流就行」**

实测同一用户两次分组的失配概率 **49.8%**——刷新一次就换组，用户会看到 A/B 反复横跳，数据同时被污染。必须用 `hash(experimentId + userId)` 这类确定性的分桶。

**❌ 误区 3：「放量时把百分比从 10% 调到 20%，老用户会被重新洗一遍」**

用"单调放大阈值"的方式是实现不了的——实测阈值 500 → 1000 时原 A 组保持率 **100%**。真正会重洗的是**改分桶空间（如 `%100` 改成 `%1000`）或改 salt / 实验名**，实测保持率都掉到 50% 左右。所以百分比可以调，分桶方式不能动。

**❌ 误区 4：「p < 0.05 就说明变体有 95% 的概率更好」**

p 值的定义是"若原假设成立，观察到当前数据的概率"，**不是**"变体更好的概率"。而且中途多次查看会把它算错（实测从 5.4% 抬到 20%~33%）。判断该不该上线的更实用依据是**置信区间的下界有没有商业意义**。

**❌ 误区 5：「实验结果整体提升 3%，可以上线」**

先过三道门：SRM 有没有异常 → 主指标是否显著且 CI 下界有意义 → 分层看会不会出现辛普森悖论（整体赢、每个分组都输）。这三步不做完，3% 可能只是流量构成变了。

**❌ 误区 6：「客户端 A/B 工具因为会闪，所以结果偏乐观」**

方向正好相反。闪烁带来的负面反应**只发生在变体组**，等于给变体额外加了一层成本，测出来的差值倾向于**低估**变体。anti-flicker 把延迟摊到两组，看起来"公平"了，但整站的性能损失在实验内部是看不见的。

**❌ 误区 7：「Feature Flag 只是临时开关，用完自然会有人删」**

没有人会删。没有回收机制的开关会持续堆积，半年后没人敢动手——工程上要给每个开关写死"过期日期"和负责回收的人，否则开关系统本身就是最大的技术债。

## 一句话总结

**分流用哈希不用随机、放量只动阈值不动分桶、变体在服务端定不要靠 JS 换、结论先过 SRM 再看 p 值——这四句能答对，这道题就稳了。**
