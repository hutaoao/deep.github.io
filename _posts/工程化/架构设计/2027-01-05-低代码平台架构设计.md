## 一句话概括

低代码平台本质上不是"拖拽 UI"，而是**把一份描述页面的 JSON 协议，交给引擎渲染成界面或者编译成代码**。拖拽只是产生这份协议的一种交互方式，真正的地基是协议本身。

面试为什么爱问它？因为它一次性考四件事：你能不能设计一份可扩展的数据结构、能不能把"数据驱动渲染"这套思路讲清楚、知不知道运行时求值的安全边界、有没有想过"平台上线第二年怎么不塌"。这几件事在业务代码里都碰不全，所以是区分"用过组件库"和"做过平台"的好题目。

答这类题的通用姿势：**先分层，再讲协议，最后落在取舍上**。别一上来就说"我们用了某某低代码引擎"。

## 核心知识点

### 1. 三层结构：协议、引擎、编辑器

面试官问「讲讲你理解的低代码平台架构」，先分层。

- **协议层（Schema）**：一份 JSON，描述页面长什么样、数据从哪来、点一下干什么。这是平台唯一的长期资产。
- **引擎层（渲染 / 出码）**：把 Schema 变成可交互界面（运行时渲染），或者编译成源码工程（出码）。
- **编辑器层（设计器）**：拖拽、属性面板、图层树、撤销重做——它的产物就是协议。
- **外围**：物料体系（组件怎么进平台）、数据源编排、发布与版本管理。

一句话答法：**低代码平台 = 一棵 Schema 树 + 这棵树的两种消费方式 + 一套让它不断长大的物料与插件机制。**

### 2. Schema 协议：低代码平台的真正资产

国内的事实标准是阿里开源的**低代码引擎**（lowcode-engine.cn），它把协议分成了三份规范：搭建协议、物料协议、资产包协议。面试能报出名字和结构，就已经超过大多数人。

顶层字段（规范原文：`version` / `componentsMap` / `componentsTree` / `utils` / `i18n` / `constants` / `css` / `config` / `meta` / `dataSource` / `router` / `pages`），节点字段是 `id` / `componentName` / `props` / `condition` / `loop` / `loopArgs` / `children`。

两个最重要的设计决策：

**① `componentName` 只是逻辑名，真正加载哪个包由 `componentsMap` 决定。**

```json
{
  "version": "1.0.0",
  "componentsMap": [
    { "componentName": "Button", "package": "@my/ui", "version": "1.2.0", "exportName": "Button" }
  ],
  "componentsTree": [
    {
      "id": "node_1",
      "componentName": "Page",
      "fileName": "Home",
      "props": {},
      "children": [
        {
          "id": "node_2",
          "componentName": "Button",
          "props": {
            "children": "提交",
            "disabled": { "type": "JSExpression", "value": "this.state.count === 0" }
          }
        }
      ]
    }
  ]
}
```

好处有两个：协议和物料实现彻底解耦（换一套组件库不用改协议），以及运行/出码时**只加载真正被用到的组件包**。

**② 属性值不止有字面量，还有四种"类型"**——这是协议能表达显隐、循环、插槽的全部秘密：

| 类型 | 用途 | 例子 |
| --- | --- | --- |
| `JSExpression` | 变量绑定、条件、循环数据 | `this.state.num + 1` |
| `JSFunction` | 事件、生命周期、自定义方法 | `function onClick(){ ... }` |
| `JSSlot` | 属性值是 ReactNode 或"函数返回 ReactNode" | 插槽内容 |
| `i18n` | 多语言文案 | `{ "type": "i18n", "key": "..." }` |

节点的显示隐藏走 `condition`（按表达式结果决定渲不渲染），列表渲染走 `loop` + `loopArgs`（默认取 `["item", "index"]`）。这两个字段是"低代码能干活"和"低代码只能搭静态页"的分界线。

最后一个常见追问：**为什么用 JSON 而不是直接生成代码？** 因为 JSON 可序列化、可 diff、可入库、可版本管理，还能让非前端的人参与编辑。代码不行。

### 3. 运行时渲染 vs 出码渲染：不是二选一

这是最经典的对比题，答成"谁取代谁"就输了。

| 维度 | 运行时渲染 | 出码渲染 |
| --- | --- | --- |
| 原理 | 用户访问时实时解析 Schema，递归生成组件树 | 构建期把 Schema 转成 React/Vue 源码，再走正常打包 |
| 灵活性 | 高，改完即生效 | 中，改动要重新出码 + 部署 |
| 首屏 | 要下 Schema + 解析 + 按需下组件资源，偏慢 | 与手写项目无差异 |
| 技术复杂度 | 高（依赖一个常年维护的渲染器） | 中（转译器更重，但产物是标准代码） |
| 适用 | 变更频繁、多租户、运营页 | 稳定性要求高、性能敏感的页面 |

有一个点必须说清楚：**运行时渲染不是"只下一个 JSON 就完事"**。Schema 里引用的组件，必须在运行环境里真实存在。所以运行时方案的必备配套是**资产包协议 + 按需加载**——根据 Schema 里用到的 `componentName`，动态插入 `<script>` 拉取对应的组件资源，加载完再渲染。这就是"资产包协议"存在的原因。

官方给的适合出码的三个真实场景，面试可以直接引用：

1. **C 端极致打开速度**：Schema 一大，前端解析开销就很可观，把解析挪到编译期能显著降 LCP，页面越简单差距越明显；
2. **老项目 + 新需求**：老项目不可能整体切到运行时方案，那就只把新页面用搭建产出、出码后 merge 进老工程；
3. **协议表达不了的定制逻辑**：协议能力不足的信号出现时，最合理的做法是"低代码研发 + 源码研发结合"，此时必须要产出可读性好的代码模块——这正是出码的强项。

结论：**成熟平台两个都提供，按页面选。** 运营页、多租户页走运行时，C 端首页、性能敏感页走出码。

### 4. 表达式引擎：区分"用过"和"做过"的地方

面试官很爱问：「Schema 里 `this.state.count + 1` 是个字符串，运行时怎么变成值的？」

直接给源码级答案——下面是 `@alilc/lowcode-renderer-core@1.3.4` 中 `parseExpression` 的核心（已精简）：

```js
// 精简自 @alilc/lowcode-renderer-core lib/utils/common.js
function parseExpression(str, self, thisRequired = false) {
  // 1. 把 this 替换成 __self（纯字符串替换，不是 AST 改写）
  const body = str.trim().replace(/this(\W|$)/g, (_a, b) => '__self' + b);
  // 2. with 提供一个作用域；thisRequired 时传空对象，直接关掉"省略 this"的口子
  const scope = thisRequired ? '{}' : '$scope || {}';
  const code = `with(${scope}) { "use strict"; var __self = arguments[0]; return ${body} }`;
  return new Function('$scope', code)(self);
}
```

三个设计意图，能讲出来就是加分项：

1. **`with($scope)` 是为了支持"省略 this"的写法**。业务同学写 `state.count` 比写 `this.state.count` 顺手，`with` 会把标识符解析优先引到作用域对象上；反过来，要求必须显式写 `this` 的场景传 `{}`，作用域就断了。
2. **`this` → `__self` 是字符串替换**，所以对格式有要求：`this` 后面必须紧跟非单词字符或行尾才会被替换。
3. **出错只打日志、返回 `undefined`，不抛异常**。表达式写错了不能让整页白屏。

顺便说一个我实测踩到的副作用：因为第 2 点是**纯字符串替换**，字符串字面量里的 `this` 也会被改写。

```js
const self = { state: { count: 1, num: 3, num2: 2 }, utils: { add: (a, b) => a + b } };
parseExpression('this.state.count + 1', self)   // 2
parseExpression('state.num - state.num2', self) // 1（省略 this 可用）
parseExpression('`${this.state.num}万`', self)  // '3万'
parseExpression('"this is text"', self)         // '__self is text' —— 字符串里的 this 被改写了
```

**所以协议里写固定文案时别把 `this` 放在字符串里。**

然后是这道题真正的考点：**`new Function` 不是沙箱，只是作用域隔离。** 用与源码一致的构造实测（Node 22）：

```js
parseExpression('typeof globalThis', self)              // 'object'  ← 全局对象照样拿得到
parseExpression('globalThis.__peek = "leaked"', self)   // 真的写进了全局
parseExpression('leak2 = 42', self)                     // 未声明赋值也创建了全局变量
```

第三行说明 `with` 块里那句 `"use strict"` **并没有生效**（它不是函数体的指令序言，只是个普通字符串表达式），所以表达式运行在非严格模式下，未声明赋值会静默创建全局变量。

由此得出一条工程结论：**用 `new Function` 求值的信任边界是「Schema 由谁写的」**。自己平台内部搭的页面，够用；一旦 Schema 来自外部或租户，就必须换方案：

- 放进独立 iframe / Worker 里求值（拿不到主文档的 window）；
- 或者先用 `@babel/parser` 遍历 AST 做白名单校验，把 `fetch` / `localStorage` / `document` / `window` 这类标识符和成员访问直接拒掉，再执行。

事件函数（`JSFunction`）这里还有个容易忽略的差别：**兜底只做在了 `parseExpression` 上**。`JSFunction` 的转换走的是另一个函数 `transformStringToFunction`，它就是 `new Function('"use strict"; return ' + str)()`，**外面没有 try/catch**——所以事件函数字符串里的语法错误会在转换阶段直接抛出去。真要做到"写错代码不白屏"，得自己在这一层补兜底。

### 5. 渲染性能：Schema 变大之后才暴露的问题

小页面上这些都不明显，一张大表单（几千个节点）会全部暴露出来。面试答三条就够：

**① 全量更新 vs 增量更新。** 全量更新是"任何数据变化就重算整棵组件树"；增量更新是"只重算依赖了变化数据的那些节点"，通常靠 MobX observable 或 Proxy 做依赖收集。低代码页面里数据源、联动规则一多，全量方案立刻卡死。

**② 维护 `id → node` 索引表。** Schema 既是一棵树，又需要按 id 快速定位（选中某个节点、更新某个节点的 props）。每次都从头递归是 O(N)，建索引后是 O(1)。这就是"别老是重新遍历整棵树"的实在含义。

**③ 更新时只 patch 变化的 props，别整个重建 props 对象。** 这一点很致命：props 引用一变，React 侧的 `memo` 全部失效，Vue 侧也全部是新 prop——你精心做的增量更新会被这一下抵消掉。

另外两条配套：长列表走虚拟列表（但注意把"数据驱动"和"节点展开"分开，别把列表项展开成 N 份 Schema 节点）；首屏要同时管 Schema 体积和组件资源体积，这也是出码存在的理由。

### 6. 编辑器三个工程细节

设计器本身也是不小的工程，面试常挑这三个问：

**① 画布跑在独立 iframe 里。** 设计器自身的全局样式、CSS 变量、全局变量都可能污染画布里的真实页面，反过来页面样式也会污染设计器。同源 iframe 可以直接通过 `iframe.contentWindow` 调渲染器挂在 window 上的 API，组件增删改、拖拽定位、hover 高亮这些高频交互都走这条通道，不用 postMessage。

这里有个很能说明问题的源码细节：`parseExpression` 在检测到同域、且宿主窗口上存在 `__newFunc` 时，会优先调用宿主窗口上的那个函数来生成表达式——源码注释写的是「默认调用顶层窗口的 parseObj，保障 new Function 的 window 对象是顶层的 window 对象」。也就是说**画布在 iframe 里，但表达式求值要回到宿主窗口**，否则 `window` 指向就不对了。

**② 撤销重做用命令模式 / patch，不要存整棵树的深拷贝。** 记录"改了哪个节点的哪个字段、改前是什么、改后是什么"，大页面下深拷贝会把内存吃掉。同时要把连续操作合并成一条历史——拖动一次数字输入框不该产生几十条记录。

**③ 拖拽器只算"落在哪"，改 Schema 的必须是模型层同一入口。** 拖拽组件只输出"目标父节点 + 目标下标"，真正修改协议要经过统一的模型 API。这样撤销重做、脏标记、以后的多人协同才有唯一的真相源。

### 7. 物料与版本兼容：平台能不能活过第二年

这是最容易被忽略、但真正决定平台生死的一层。

- **物料协议三件套**：组件本身 + 属性设置器（决定这个组件在右侧面板能配什么）+ 片段（拖进来时的默认结构）。**没有设置器的组件是进不了平台的**——物料能不能规模化，取决于"接入一个新组件要不要改引擎"。
- **微内核 + 插件**：核心只保留协议模型和渲染/出码调度，大纲树、代码面板、数据源、国际化、发布这些全是插件。判断标准很简单：**加一个编辑能力，要不要动核心？**
- **版本兼容**：协议里的 `version` 是强约束字段，不同版本对应不同渲染 SDK。老 Schema 必须能在新引擎上跑通，并且渲染器 SDK 的升级节奏要和协议解耦。这是平台第二年最容易翻车的地方：引擎升了级，历史页面全白屏。
- **Schema 是长期资产**：加字段要自带默认值兜底，删字段要先废弃一段时间，永远给老数据留一条能渲染的路。

## 其实你每天都在用

- 钉钉宜搭、飞书多维表格、企业微信审批流：表单 + 流程就是最成熟的低代码形态，你填过的每一张都是它在跑。
- 大屏可视化平台：拖组件、绑数据源、配轮播，本质就是低代码 + 图表库。
- Formily / FormRender 这类 schema 表单方案：低代码最窄、也最实用的一个切口。
- 后台管理系统里的"列表列配置"：选哪几列显示、筛选项有哪些、导出哪些字段——这就是一份迷你 Schema。
- 埋点平台和 A/B 实验平台：事件定义、变体配置面板，就是把配置变成了结构化数据。
- 营销落地页搭建、公众号排版工具、海报编辑器：都是"编辑器产出 Schema，引擎消费 Schema"。
- 甚至你写的框架代码也是同一条链路：Vue 的 template 要编译成 render 函数，JSX 要被编译成 `createElement` 调用——**"声明式描述 → 运行时结构"这件事你早就在用了**。
- 反向的例子也有：你手工写过的每一个 CRUD 页面，都是低代码平台想替你消掉的那部分工作量。

## 常见误解（FAQ）

**❌ 误区1："低代码就是把组件拖来拖去。"**
拖拽只是一种交互。真正的资产是协议——协议设计不好，第二年加需求就得推翻重来，而拖拽器换一个并不难。

**❌ 误区2："运行时渲染就是递归 JSON、然后 createElement 出来。"**
那只是能跑起来。真正的难点是表达式的作用域与错误兜底、节点更新粒度、组件资源按需加载、以及大 Schema 下的性能——这四件才是"做过"和"见过"的差别。

**❌ 误区3："运行时渲染和出码渲染是替代关系。"**
两者互补：运行时胜在改完即生效，出码胜在产物性能。成熟平台两个都提供，按页面类型选。

**❌ 误区4："用 `new Function` 做沙箱就比较安全了。"**
它不是沙箱，是作用域隔离。实测表达式里能直接访问 `globalThis`、能写全局变量。安全性取决于 Schema 的可信来源；不可信的 Schema 必须换 iframe / Worker 求值，或做 AST 白名单校验。

**❌ 误区5："低代码只适合简单页面。"**
限制不在业务复杂度，而在两件事：协议能不能表达（表达不了的要留出码口子）、引擎能不能兜住性能。复杂的定制逻辑本来就应该走源码。

**❌ 误区6："低代码就是零代码，前端要被替代。"**
低代码省掉的是重复的 CRUD 搭建。真正吃功力的是协议设计、物料治理、版本兼容、性能兜底——这些活只会变多，不会变少。

## 一句话总结

低代码平台的本质是**把"页面"变成一份可序列化、可版本管理的 JSON，再由引擎把它渲染成界面或编译成代码**；面试只要把「协议怎么定、渲染怎么选、表达式怎么跑、性能怎么兜」这四件事讲清楚，这道题就稳了。
