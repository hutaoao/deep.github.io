## 一句话概括

面试官问 BEM，往往不是想听你背 `block__element--modifier`——**他是在问"多人协作下样式怎么才不会失控"**。这个问题有三层，一层的方案解决不了另一层：

1. **同一个页面里，我的样式不要污染别人的** → 作用域方案（BEM / Scoped / CSS Modules / 原子类）
2. **十个业务系统长得像一套产品** → 设计令牌（design token）：把"颜色/间距/字号"变成有语义、可派生的契约
3. **业务方要改组件样式时，改哪里、能改到什么程度** → 组件 API 与覆盖边界（props / 变量 / className / 插槽）

所以这篇的主线不是"BEM 怎么写"，而是**"样式决策该放在哪一层"**：`#1e80ff` 这种原始值放最底层、`--color-brand-primary` 放中间层、`Button` 组件里只准引用中间层。**层级一乱，换肤和主题就变成工期黑洞。**

## 核心知识点

### 1. 先把 BEM 的官方语法对齐：不是 `--modifier`

网上 90% 的文章把 BEM 写成 `block__element--modifier`。这个写法确实最流行，但**它不是 BEM 的经典语法，而是社区变体**。BEM 官方（bem.info）的经典语法是：

```
block-name__elem-name_mod-name_mod-val
```

- 全小写拉丁字母，单词用连字符 `-` 分隔
- 元素用**双下划线** `__` 与块名连接
- 修饰符用**单下划线** `_` 连接，修饰符**值**也用单下划线连接
- **布尔修饰符不带值**（`menu_hidden`，不是 `menu_hidden_true`）

官方另有一张"替代命名方案"表，其中第一项就是 **Two Dashes style**：`block-name__elem-name--mod-name_mod-val`——也就是我们最熟悉的那套。**Element Plus 的 `el-button--primary` / `el-input__inner` 走的就是这个变体。**

还有一条**几乎所有人都答错**的规则，官方原文写得很硬：

> **Important:** Elements of elements **do not exist** in the BEM methodology. The naming rules do not allow creating elements of elements, but you can nest elements inside each other in the DOM tree.

也就是说 **`block__elem1__elem2` 是不存在的**。DOM 里你可以随便嵌套，但类名层级只有一级：元素永远挂在**块**下面，不挂在元素下面（真要复用就往里塞一个新块，或者用 mixes）。面试里能主动说出这条，基本就能判断你是真用过 BEM 而不是背过语法。

### 2. BEM 的真正内容是"选择器纪律"，不是"类名长一点"

BEM 官方把 CSS 部分的规则列得很清楚，而且**每条都给了理由**。这些理由才是面试要答的东西：

| 官方规则 | 官方给的理由 |
| --- | --- |
| 只使用 class 选择器，**不用 tag 和 ID 选择器** | tag + class（如 `button.button`）会抬高权重，导致修饰符 `.button_active` 再也压不过它 |
| **不推荐组合选择器**（如 `.button.button_theme_islands`） | 同样抬高权重，修饰符要覆盖就得跟着一路加选择器，最后变成"为了能覆盖而加选择器"的军备竞赛 |
| 允许嵌套但**尽量少用** | 嵌套提高代码耦合、让复用不可能；只在"块的状态/主题影响内部元素"时才用（如 `.button_hovered .button__text`） |
| 名字要能准确描述 BEM 实体 | `.button__text` 一看就知道是哪个块的哪个元素，`.text` 猜不出来 |

换句话说，**BEM 的核心不是让你把类名写长，而是让你把权重压到最低**：所有规则都是单类选择器（权重 0,1,0），谁能覆盖谁只取决于**源码顺序**，你不需要算权重。这跟 `@layer`（见《现代 CSS 新特性：容器查询 / 子网格 / :has() / @layer》）解决的是同一个问题的两种办法——一个靠命名纪律，一个靠层叠排序。

### 3. mixes：BEM 最实用的一条，也是最少人提的

BEM 允许**同一个 DOM 节点挂多个块的类**，官方叫 mix：

```html
<header class="header">
  <button class="header__button button button_theme_islands">...</button>
</header>
```

官方对它的用法有一句非常关键的约束：

> **Important!** When mixing blocks, their CSS properties **shouldn't overlap**. Shared properties belong in the mixin block (`text`), while section-specific properties stay in their own block.

翻译一下：**`header__button` 只放"外部定位"（margin、对齐、位置），`button` 只放"内部样式"（圆角、内边距、颜色）**。这样按钮在任何地方都能当按钮用，位置由所在区块负责。

这就是组件化里最常见的那个问题——**"组件的样式该不该管自己的外边距"**——BEM 早在设计系统流行之前就给了答案：**组件只管内部，外部几何归使用方**。现在组件库把这条做成了"默认不给你加 margin"，原因就在这里。

### 4. BEM 今天还需要吗：看你的作用域方案是哪种

BEM 是**用命名换作用域**的方案，它解决的是"没有工具帮忙时怎么隔离"。今天大多数项目已经有别的作用域机制，所以判断标准很简单：**谁负责"让两条规则互不干扰"这件事**。

| 方案 | 隔离手段 | 权重水平 | 适合 |
| --- | --- | --- | --- |
| BEM | 人工命名约定 | 全部 0,1,0 | 无构建工具、样式与模板分离、需要被外部覆盖的组件库 |
| Scoped CSS | 编译期加属性选择器 + 运行时打 `data-v-*` | +1 属性 | Vue SFC 单文件组件 |
| CSS Modules | 编译期哈希类名（`._red_1cpek_1`） | 0,1,0 | React / 需要 JS 引用类名 |
| 原子化 CSS | 类名即声明、无自定义语义类 | 靠 `@layer` 排序 | 组件与页面都直接消费令牌 |

这四种不是互斥的，真实项目常常是"组件库用 BEM 保证外部可覆盖，业务应用用 Scoped/Modules"。**面试里能说清"BEM 的对手不是某个框架，而是另一套隔离机制"，比背语法有用得多。**

### 5. 设计令牌：三层结构，和一条铁律

设计令牌（design token）的定义很朴素：**把设计决策存成"名字 + 值"的实体**。但真正决定它成不成的，是**分几层**：

| 层 | 例子 | 谁维护 | 谁读 |
| --- | --- | --- | --- |
| 原始层（primitive / global） | `color.blue.500 = #1e80ff`、`space.4 = 16px` | 设计负责人 | **只允许中间层读** |
| 语义层（semantic / alias） | `color.surface.primary = {color.blue.500}` | 设计系统团队 | 组件层 + 业务 |
| 组件层（component） | `button.primary.background = {color.surface.primary}` | 组件负责人 | 只有该组件自己 |

**铁律：组件永远不直接引用原始层。** 业界那句被反复引用的话是——"如果 Button 直接读 `color.blue.500`，那暗色模式就会变成一个为期六个月的项目"。因为原始层的值不表达意图：`#1e80ff` 在浅色下是品牌色，在深色下可能必须换成更亮的蓝；而语义层的 `color.surface.primary` 换个值就行，所有引用它的组件自动跟上。

**Ant Design 5 的三层就是这套结构的工业级样本**：Seed Token（种子，如 `colorPrimary`）→ 由**算法**派生 Map Token（梯度色板、各档圆角）→ Alias Token（语义别名，如 `colorLink`，供组件批量消费），再加一层 Component Token 做单组件覆盖。因为中间是算法派生，**改一个种子色，所有梯度和别名自动重算**——这就是"语义层 + 派生"比"手写一堆变量"强的地方。

### 6. 令牌的文件格式与流水线：DTCG

令牌要想在 Figma、设计文档、多端代码之间流转，就必须有个中立格式。现在事实上的标准是 **W3C 设计令牌社区组（DTCG）的 Format Module**，核心约定：

```json
{
  "color": {
    "blue": { "500": { "$value": "#1e80ff", "$type": "color", "$description": "品牌主色" } },
    "surface": {
      "primary": { "$value": "{color.blue.500}", "$type": "color", "$description": "主要按钮/品牌面" }
    }
  }
}
```

三个要点：

1. **`$` 前缀**区分"令牌数据"和"用户自定义分组"（`$value` / `$type` / `$description` / `$extensions` / `$deprecated`）
2. **别名用花括号引用**：`{color.blue.500}`——这是"语义层指向原始层"的表达方式
3. **复合类型**：`typography`、`shadow`、`border`、`transition`、`cubicBezier` 都能整体作为一个有类型的值，不用再拼字符串

**状态要说准**：它是 W3C **社区组报告（Community Group Report）**，规范页面自己写明 *"It is not a W3C Standard nor is it on the W3C Standards Track."* ——**是行业共识，不是正式标准**。落地工具是 Style Dictionary、Tokens Studio、Supernova 这类"一份源文件编译出多端产物"的转换器（CSS 变量、JS 常量、iOS/Android 常量）。面试答成"W3C 标准"是个小减分点。

### 7. 组件 API 与样式的边界：从 props 到逃生舱

有了令牌，还得定义**业务方怎么改组件**。推荐的是"分层放开"，越往下越不推荐：

| 手段 | 用途 | 风险 |
| --- | --- | --- |
| **props（variant / size / tone）** | 配置：设计系统内允许的形态 | 受限于预设值，这是优点 |
| **令牌 / CSS 变量** | 主题：整体换色、换密度 | 需要一套可靠的令牌体系 |
| **className / 插槽** | 逃生舱：一次性、局部调整 | 用法容易失控，但可控、可审计 |
| **style prop（裸内联样式）** | — | 绕过令牌，一致性直接崩，设计系统里通常不推荐暴露 |

`variant` 这类 prop 的**正确实现方式是"映射表"，不是 if-else 链条**：

```js
// ❌ 每加一个 variant 就要动渲染逻辑
if (variant === 'primary') cls = 'btn--primary';
else if (variant === 'danger') cls = 'btn--danger';

// ✅ 查表：加形态只加一行数据
const VARIANT_CLS = {
  primary: 'btn--primary',
  danger: 'btn--danger',
  ghost: '',                 // 无修饰符类
};
const cls = ['btn', VARIANT_CLS[variant], SIZE_CLS[size]].filter(Boolean).join(' ');
```

这套"把 props 组合映射成类名"的活儿已经有专门的库（如 CVA，`class-variance-authority`），它的价值不只是省代码，而是**让"哪些组合合法"变成一份可枚举、可类型化的声明**——`variant: 'primary' | 'danger'` 这种字面量联合类型，编译期就能挡住 `variant="primry"` 这种拼写错误。

### 8. 主题切换为什么落在 CSS 变量上

主题切换有三种落点，面试常问"你选哪种、为什么"：

- **纯 JS 生成样式**（CSS-in-JS 运行时）：能力强（能根据 props 算样式），代价是运行时开销、SSR 要注水样式
- **CSS 变量**（`--color-*` + `:root` / `.dark` 覆盖）：零运行时，切换只是改一组变量；代价是变量名对不上就失效、没法做"根据 props 计算"的事
- **编译期变量**（Sass/Less 变量）：**做不了运行时切换**，因为它编译完就没了

所以成熟方案基本都是**两层配合**：**令牌落到 CSS 变量上**（换来运行时切换能力 + 零 JS 开销），**组件内部的复杂逻辑仍然用 JS/构建期处理**。Ant Design 5 走的是运行时 CSS-in-JS 路线，但它同时提供了 `cssVar` 配置来接 CSS 变量，后续版本还加了 `zeroRuntime` 模式（不在运行时生成样式，改为额外引入一份 CSS 文件）——**方向很清楚：尽量把运行时的活儿挪到构建期**。

主题切换本身的实现要点：**用 `:root` 存浅色、用 `[data-theme="dark"]` 或 `.dark` 覆盖**。默认值可以用 `@media (prefers-color-scheme: dark)` 跟随系统，但**最终落点必须是属性/类而不是纯媒体查询**——否则用户没法手动切回浅色。另外记得**配合 `color-scheme` 让浏览器原生控件（滚动条、表单、`<input type=date>`）也跟着变**，只改自己的颜色不管 `color-scheme`，是深色模式最典型的"看起来没做完"。

### 9. 治理：设计系统真正难的部分

技术上把令牌和组件搭起来是一两周的事，难的是让它**活过两个季度**。四个必须有：

1. **命名规约**：令牌名是 API，改一次就是破坏性变更。名字里不要出现"当前值"（`--color-light-blue` 这种，色调一改就变成谎言），要出现"用途"（`--color-surface-primary`）
2. **发布与废弃**：组件库走语义化版本，废弃要有明确的废弃期和迁移路径（先加新 API、再标 deprecated、最后大版本删）
3. **硬编码率监控**：衡量设计系统是否真的在下沉，最有效的指标就是**代码库里硬编码颜色/间距的比例**，把它做成 lint 规则或 CI 检查
4. **文档即组件**：Storybook 之类的控件面板把 `variant` / `size` 的合法组合摆出来，业务方就不需要靠读源码猜

## 其实你每天都在用

- **Element Plus 的 `el-button--primary` / `el-input__inner`**：BEM 的 Two Dashes 变体，块前缀 + 双连字符修饰符 + 双下划线元素。
- **Ant Design 5 在 `ConfigProvider` 的 `theme` 里改 `token.colorPrimary`**：改一个种子令牌，派生层和别名层全部重算——这就是三层令牌结构的价值。
- **Tailwind v4 的 `@theme { --color-brand: ... }`**：`@theme` 里的 `--color-*` 就是原始/语义令牌，写 `bg-brand` 时产物引用的是 `var(--color-brand)` 而不是字面值。
- **你项目里的 `:root { --color-primary: #1e80ff }`**：这已经是设计令牌的雏形，缺的只是"分层"和"纪律"。
- **深色模式切 `document.documentElement.dataset.theme = 'dark'`**：改一组 CSS 变量，全站跟着变，这是"令牌落在 CSS 变量上"的直接收益。
- **组件库里"我不给你加 margin"**：BEM mixes 那条规矩（外部几何归使用方）在组件时代的延续。
- **`className` / `class` prop 的覆盖口**：这是组件库留给业务方的标准逃生舱，比暴露 `style` 更可控。
- **设计师给的"色彩规范"文档**：如果它只有色号没有用途命名，那它还不是令牌，只是色卡。

## 常见误解（FAQ）

**❌ 误区一："BEM 就是 `block__element--modifier`"**

这是社区 Two Dashes 变体，**不是 BEM 经典语法**。官方经典写法是 `block__elem_mod-val`（修饰符用单下划线，布尔修饰符不带值），`bem-naming` 工具还要靠额外规则才能识别 `--` 这套。答对这一点能直接区分"背过"和"查过"。另外别忘了那条更硬的规则：**BEM 里没有"元素的元素"**，`block__elem1__elem2` 不存在。

**❌ 误区二："BEM 类名太长、太啰嗦，已经过时了"**

判断 BEM 该不该退役，看的不是类名长度，而是**有没有别的东西负责隔离**。`<style scoped>`、CSS Modules、原子类都在做同一件事，你用了它们就不必再叠 BEM。但**组件库这种需要被外部覆盖的场景，BEM 仍然是合理选择**：它的权重全是单类、可预测、容易覆盖。反过来，如果你的项目既没有 Scoped 也没有 Modules，还嫌 BEM 啰嗦——那是没有隔离方案，不是 BEM 过时。

**❌ 误区三："设计令牌就是 Sass 变量 / CSS 变量"**

变量只是**机制**，令牌是**带语义分层的契约**。`$blue-500: #1e80ff` 是变量；`color.surface.primary = {color.blue.500}` 才是令牌，因为它表达了"用途"，并且指向原始层。判断标准很简单：**如果换肤时要改的是"值"而不是"引用关系"，说明你缺了语义层。** 另一个常见误区是把 DTCG 格式当成 W3C 正式标准——它是社区组报告，规范首页自己声明不在 W3C 标准轨道上。

**❌ 误区四："组件多暴露一个 `style` prop，用户改起来最方便"**

`style` 绕过令牌，用户写一次 `style="color: #f00"`，深色模式、换肤、对比度调整全部失效，而且**你无法审计**（哪来的红？搜不到）。设计系统里的覆盖应该是**有层级、可审计**的：先是 props（配置），再是令牌/CSS 变量（主题），最后才是 `className` / 插槽这种逃生舱。注意反转：`className` 和 `style` 的差别不是"哪个更灵活"，而是**前者能被静态检查、能被统一约束，后者不能**。

**❌ 误区五："换肤就是加个 `.dark` 覆盖一下颜色变量"**

如果组件里散落着 `#1e80ff`、`rgba(0,0,0,.65)`、`box-shadow: 0 2px 8px rgba(0,0,0,.15)` 这种硬编码，`.dark` 覆盖只能覆盖到你想起来的那几个，剩下的全靠人肉找。**深色模式是检验令牌分层质量的试纸**：能不能只改语义层就完成切换，取决于当初有没有守住"组件不引用原始层"这条铁律。另外别忘了 `color-scheme`，不然浏览器原生控件还是浅色。

**❌ 误区六："设计系统就是把所有组件都做一遍"**

组件数量不是指标，**约束才是**。真实失败模式有两个极端：一是只做组件不做令牌，于是"统一"只统一了外观、没统一语义，改主题还是全量改；二是**过度建模**——给每个可能的组合都生成令牌和变体，结果没人记得住、也背不下来，最后大家又回去硬编码。**"这份令牌解决哪个决策"说不清，就该删掉它。**

## 一句话总结

**BEM 是"用命名换作用域"的纪律（核心是单类低权重、允许 mix、不存在元素的元素）；设计令牌是"用语义层换一致性"的契约（原始层只给中间层读，组件永远不直接引用原始层）；组件样式方案的关键是划清"配置（props）/ 主题（令牌）/ 逃生舱（className、插槽）"三层的边界——这三件事分别解决隔离、一致性和可覆盖，缺一层都会在团队规模下失控。**
