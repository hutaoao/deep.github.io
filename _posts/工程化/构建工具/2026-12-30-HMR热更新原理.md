## 一句话概括

热更新的本质就一句话：**文件变了，沿着 import 的引用链往上找，谁愿意接住这次更新，就在谁那里停下。** 找到了就只替换受影响的那几个模块，页面状态全保留；一路找到顶都没人接，才退化成整页刷新。

你可以这样理解：模块图是一棵树，改动发生在某个叶子节点。HMR 从叶子开始往根部爬，每爬一层就问一句"你接得住吗"——接得住就在这层把新代码换上去，接不住就继续往上爬。爬到根节点（入口）还没人接，那就只能整页重来。

**"边界（boundary）"就是这个愿意接住的模块。** `import.meta.hot.accept()` 的作用，就是举手说"我能接"。Vite 里 CSS 和 Vue SFC 之所以改样式不丢状态，就是因为构建时它们各自的产物里已经自动写好了这句举手代码——不是你写的，是插件生成的。

面试里 HMR 常见的问法有三种，从浅到深：①"HMR 为什么比整页刷新好"（送分）；②"HMR 的完整链路是什么"（考流程）；③"为什么我改一个文件，结果整页刷新了"（考边界传播，这题才是分水岭）。本文重点讲第三种。

## 核心知识点

### 1. 先分清两个词：热更新 ≠ 整页刷新

很多人一开始就把 HMR 理解成"自动刷新浏览器"。不是。

| | 整页刷新（Live Reload） | 热更新（HMR） |
|---|---|---|
| 怎么发现变更 | 文件系统监听 | 文件系统监听 |
| 怎么通知浏览器 | WebSocket | WebSocket |
| 谁来处理 | 直接 `location.reload()` | 服务端先在模块图里找边界 |
| 应用状态 | **全丢**，回到初始 | **保留** |
| 改样式的体感 | 页面闪一下 | 无感 |

关键差别只有一个词：**状态保留**。你在表单里填了半屏内容，改一行 CSS 保存，页面不该重来。这就是 HMR 存在的全部理由。

Live Reload 和 HMR 用的是同一套「文件监听 + WebSocket」基础设施，区别只在于收到通知后干什么：前者 `reload()`，后者去找边界。

### 2. 边界：`accept()` 到底声明了什么

Vite 的 HMR API 挂在一个虚拟模块 `import.meta.hot` 上，只在开发环境存在（生产构建里整个 `if (import.meta.hot) {}` 块会被摇掉）。

三种举手姿势，语义完全不同：

```js
// ① 自我接受：这个模块自己变了，我自己能处理
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // newModule 是重新执行后的新模块
    // 这里负责把旧状态迁移过去
    data = newModule.data;
  });
}

// ② 接受某个依赖：我的依赖变了，我来接
import { render } from './render';
let currentRender = render;
if (import.meta.hot) {
  import.meta.hot.accept('./render', (newModule) => {
    currentRender = newModule.render;
    currentRender();          // 拿到新实现，重新渲染
  });
}

// ③ 接受一组依赖
if (import.meta.hot) {
  import.meta.hot.accept(['./a.js', './b.js'], ([a, b]) => { /* ... */ });
}
```

`accept()` 不带参数 = 自我接受（等价于 `accept(cb?)` 的简化形态），带字符串/数组 = 接受依赖。

这里有个几乎必踩的坑，值得单独说：**`accept` 不是"Vite 自动帮你把内存里所有旧引用换成新的"。** 它只是把你标记成边界并把新模块交给你，怎么把新实现接回运行中的应用，是你（或者插件）的责任。这就是为什么 Vue SFC 的 HMR 不需要你写一行代码——`@vitejs/plugin-vue` 在编译 `.vue` 时已经把这套交接逻辑生成了。

### 3. 传播算法：`propagateUpdate` 在找什么

这是全文最重要的一段。Vite 8 里这个函数长这样（`packages/vite/src/node/server/hmr.ts`，我做的是去掉分支里的日志和循环依赖细节）：

```js
function propagateUpdate(node, traversedModules, boundaries, currentChain = [node]) {
  if (traversedModules.has(node)) return false;
  traversedModules.add(node);

  // 模块还没被分析过（isSelfAccepting 是 undefined），先跳过
  if (node.id && node.isSelfAccepting === undefined) return false;

  if (node.isSelfAccepting) {
    // ① 自己就是边界，就地停下
    boundaries.push({ boundary: node, acceptedVia: node, isWithinCircularImport: ... });
    return false;
  }

  if (node.acceptedHmrExports) {
    boundaries.push({ boundary: node, acceptedVia: node, isWithinCircularImport: ... });
  } else if (!node.importers.size) {
    // ② 死路：没人引用我，且我自己也接不住 → 必须整页刷新
    return true;
  }

  for (const importer of node.importers) {
    // ③ 上游显式 accept 了我
    if (importer.acceptedHmrDeps.has(node)) {
      boundaries.push({ boundary: importer, acceptedVia: node, isWithinCircularImport: ... });
      continue;
    }
    // ④ 上游虽然没 accept 我，但它 accept 的导出正好覆盖了我用到的那些
    if (node.id && node.acceptedHmrExports && importer.importedBindings) {
      const importedBindingsFromNode = importer.importedBindings.get(node.id);
      if (importedBindingsFromNode &&
          areAllImportsAccepted(importedBindingsFromNode, node.acceptedHmrExports)) continue;
    }
    // ⑤ 都没接住，继续往上爬
    if (!currentChain.includes(importer) &&
        propagateUpdate(importer, traversedModules, boundaries, [...currentChain, importer])) return true;
  }
  return false;
}
```

翻译成人话，就四个判断：

1. **我自己 `isSelfAccepting` 吗？** 是 → 我就是边界，停。
2. **没人 import 我，我也接不住？** → 死路，**整页刷新**。
3. **谁 import 了我，而且它 `accept('./我.js')` 了？** → 它是边界，停。
4. **以上都不满足？** → 顺着 importers 继续往上爬。

返回 `true` 只有一个含义：**路上出现了死路**。只要有任意一条分支返回 `true`，整个更新就降级成 `full-reload`。

在第 2 步和第 4 步之间还有个细节值得记：`if (node.id && node.isSelfAccepting === undefined) return false;`。这说明模块**必须先被分析过**才能参与传播。没被 transform 过的模块是"未知状态"，直接跳过而不是当成死路——这是 Vite 按需编译模型留下的痕迹。

### 4. 我实测到的七种结果

光看源码不够，我起了个真实的 Vite 8.3.4 dev server，用真的 WebSocket 客户端连上去抓服务端推的原始 payload。七种改动场景，模块图如下：

```
leaf.js  ← mid.js ← entry.js          （entry 没有 importer）
dep.js   ← acceptor.js（acceptor 里写了 accept('./dep.js')）
self.js                               （自己写了 accept()）
style.css, Counter.vue                （插件自动生成 accept）
```

实测结果：

| 被改的文件 | 谁接住的 | 服务端推送的 payload |
|---|---|---|
| `self.js` | 自己 | `{type:"update", updates:[{type:"js-update", path:"/src/self.js", acceptedPath:"/src/self.js"}]}` |
| `dep.js` | 上游 `acceptor.js` | `{type:"update", updates:[{type:"js-update", path:"/src/acceptor.js", acceptedPath:"/src/dep.js"}]}` |
| `style.css` | CSS 产物自己 | `{type:"update", updates:[{type:"js-update", path:"/src/style.css", acceptedPath:"/src/style.css"}]}` |
| `Counter.vue`（改 template） | SFC 自己 | `{type:"update", updates:[{type:"js-update", path:"/src/Counter.vue", acceptedPath:"/src/Counter.vue"}]}` |
| `Counter.vue`（改 script） | SFC 自己 | 同上，`path` 都是 `/src/Counter.vue` |
| `leaf.js`（全链无人 accept） | 无 | `{type:"full-reload", triggeredBy:"/private/tmp/hmrcheck/src/leaf.js", path:"*"}` |
| `mid.js`（自己没 accept） | 无 | `{type:"full-reload", triggeredBy:".../src/mid.js", path:"*"}` |

**请重点看第 2 行和第 6、7 行**，这是两个最容易答错的地方：

- **第 2 行**：改的是 `dep.js`，但 payload 里的 `path` 是 `acceptor.js`（边界），`acceptedPath` 才是 `dep.js`（真正变了的）。客户端拿 `path` 去找"谁注册了回调"，拿 `acceptedPath` 去决定"要重新 import 哪个 URL"。**一个字段是边界，一个字段是变更源，别搞反。**
- **第 6、7 行**：`mid.js` 自己有 importer（`entry.js` 引用了它），但依然整页刷新了。因为传播从 `mid.js` 往上爬到 `entry.js`，`entry.js` 自己没有 importer，既不是边界也没有出口——撞死路。**"有上游"不等于"能被接住"。**

### 5. 客户端拿到 payload 后做了什么

服务端推送 `update` 后，客户端（`@vite/client`）对每条 update 分两路：

```js
// client/src/client.ts handleMessage 的 update 分支
case 'update':
  await notifyListeners('vite:beforeUpdate', payload);
  await Promise.all(payload.updates.map(async (update) => {
    if (update.type === 'js-update') {
      return hmrClient.queueUpdate(update);      // 路径 A：重新 import 模块
    }
    // 路径 B：老的 CSS 处理方式——找 <link> 标签换 href
    const el = [...document.querySelectorAll('link')].find(...);
    // 克隆一个新 link，插入、加载、再删掉旧的（避免闪烁）
  }));
  await notifyListeners('vite:afterUpdate', payload);
  break;
```

`queueUpdate` → `fetchUpdate`，核心是这个：

```js
async function importUpdatedModule({ acceptedPath, timestamp, explicitImportRequired }) {
  // 就是带时间戳重新 import，绕过浏览器缓存
  const importPromise = import(
    `${base}${browserPath.slice(1)}?${explicitImportRequired ? 'import&' : ''}t=${timestamp}`
  );
  return await importPromise;
}
```

重新 import 之后，`fetchUpdate` 会按顺序做三件事：**先跑 `dispose` 清理旧模块的副作用 → 新模块执行（模块顶层代码重新跑一遍）→ 调用 `accept` 回调交接状态**。顺序不能乱，`dispose` 必须在 `accept` 之前，否则你会在新模块已经生效的情况下再去清理它。

### 6. 一个 Vite 8 的变化：CSS 也走 `js-update` 了

老版本 Vite 的 HMR payload 里有个 `css-update` 类型，客户端看到它就去找 `<link>` 标签换 href。**Vite 8 里 `css-update` 已经彻底没了**——我在 `vite@8.3.4` 的 `dist/node/` 和 `dist/client/` 里 grep `css-update`，命中数为 **0**。

那样式是怎么更新的？看 CSS 模块被 transform 后的产物：

```js
import { createHotContext as __vite__createHotContext } from "/@vite/client";
import.meta.hot = __vite__createHotContext("/src/style.css");
import { updateStyle as __vite__updateStyle, removeStyle as __vite__removeStyle } from "/@vite/client";

const __vite__id = "/abs/path/src/style.css";
const __vite__css = "body { color: blue; }\n";

__vite__updateStyle(__vite__id, __vite__css);
import.meta.hot.accept();                                    // ← 自我接受
import.meta.hot.prune(() => __vite__removeStyle(__vite__id)); // ← 模块被移除时清掉样式
```

CSS 模块**自己就是边界**：产物里带着 `accept()`，同时把 CSS 文本交给 `updateStyle` 去维护 `<style>` 标签。所以服务端只需要推一条普通的 `js-update`，走的完全是 JS 路径，`updateStyle` 内部自己处理标签的新增/替换。

顺手解释一个现象：为什么改 CSS 时老版本能用"换 link 标签"这种更省事的方式？因为生产/老模式下 CSS 是通过 `<link>` 引入的独立资源；Vite 8 统一成 JS 模块边界后，代码路径少了一条，`css-update` 这个类型、以及客户端那段找 `<link>` 换 href 的逻辑，就自然被删掉了。

> 补充：客户端里那段处理 `<link>` 的代码分支**还在**（`if (update.type === 'js-update') return queueUpdate(...)` 之后的兜底），因为 SSR、`?direct` 等边缘场景仍可能产出非 js-update 的条目。但服务端已经不再主动推 `css-update` 了。

### 7. `isSelfAccepting` 是怎么被算出来的

服务端怎么知道一个模块"愿不愿意接住"？靠构建时的**静态分析**，不是运行时问它。

Vite 在 `importAnalysisPlugin` 里扫每个模块的源码，只认这一种字面形式：

```js
// 只匹配字符串字面量或字面量数组
import.meta.hot.accept('./dep.js', cb);              // ✅ 识别
import.meta.hot.accept(['./a.js', './b.js'], cb);    // ✅ 识别
import.meta.hot.accept(`./${name}.js`, cb);          // ❌ 直接报错
```

遇到模板字符串，Vite 会抛出一个明确的错误：

```
import.meta.hot.accept() can only accept string literals or an Array of string literals.
```

原因很直接：**编译期要拿到确定的依赖路径去建模块图**，动态拼接的路径根本不知道指向谁。所以 `accept` 的依赖参数必须是字面量——这是 API 设计上就锁死的，不是实现偷懒。

扫描结果落到三个字段上，我实测打印出来（做了预热，让每个模块都被 transform 过一遍）：

| 模块 | 源码里写了什么 | `isSelfAccepting` | `acceptedHmrDeps` | `importers` |
|---|---|---|---|---|
| `self.js` | `accept()` | `true` | 0 | 0 |
| `acceptor.js` | `accept('./dep.js', cb)` | `false` | 1 | 0 |
| `dep.js` | 无 | `false` | 0 | 1 |
| `leaf.js` | 无 | `false` | 0 | 1 |
| `mid.js` | 无 | `false` | 0 | 1 |
| `entry.js` | 无 | `false` | 0 | 0 |
| `style.css` | 由插件生成 | **`true`** | 0 | 1 |
| `Counter.vue` | 由插件生成 | **`true`** | 0 | 1 |
| `main.js` | 无 | `false` | 0 | 0 |

两个值得注意的点：

- **`acceptor.js` 的 `isSelfAccepting` 是 `false`，但 `acceptedHmrDeps` 是 1。** 这两个字段是独立的：`accept()`（不带依赖）才置 `isSelfAccepting = true`；`accept('./dep.js')` 只往 `acceptedHmrDeps` 里塞一条。所以"能接住依赖更新"和"能接住自己更新"是两码事——上文传播算法的第 3 步专门查的就是 `acceptedHmrDeps`。
- **没被 transform 过的模块，`isSelfAccepting` 是 `undefined`。** 这就是传播算法里那句 `=== undefined` 判断的来源。

还有一个反直觉的细节：**纯 JS 模块不会被注入 `import.meta.hot`。** 我拿 `store.js`（没有任何 hot 代码）测试，transform 产物里既没有 `__vite__createHotContext` 也没有 `hot.accept`。注入条件是有条件的：

```js
if (hasHMR && !ssr && !isClassicWorker) {
  str().prepend(
    `import { createHotContext as __vite__createHotContext } from "${clientPublicPath}";` +
    `import.meta.hot = __vite__createHotContext(${JSON.stringify(importerModule.url)});`
  );
}
```

`hasHMR` 只有在你源码里出现了 `import.meta.hot` 才为真。**你不写 hot 代码，Vite 就不给你注入 hot 上下文**——这个"按需注入"避免了给每个模块塞无用代码。

### 8. Vue SFC 的产物：`_rerender_only`

`<script>` 和 `<template>` 改动在客户端的处理路径不一样，插件用 `_rerender_only` 这个标记来区分。SFC 产物里的关键片段：

```js
import.meta.hot.accept((mod) => {
  if (!mod) return;
  const { default: updated, _rerender_only } = mod;
  if (_rerender_only) {
    // 只有模板变了 → 只重跑 render，组件实例和状态全保留
    __VUE_HMR_RUNTIME__.rerender(updated.__hmrId, updated.render);
  } else {
    // 逻辑变了 → 替换组件定义并强制刷新
    __VUE_HMR_RUNTIME__.reload(updated.__hmrId, updated);
  }
});
```

`__VUE_HMR_RUNTIME__` 是 Vue 运行时暴露的 HMR 接口，就三个方法：

- `createRecord(id, component)` —— 模块加载时登记组件，建立 id → 组件定义的关系。
- `rerender(id, newRender)` —— 只换 render 函数，**不动组件实例**。所以改模板时 `data`/`ref` 的值都在。
- `reload(id, newComp)` —— 换整个组件定义。Vue 会把受影响的组件实例标记进 `hmrDirtyComponents`，在下一个 tick 强制重渲染，同时把新的 options 合并进去。

这就是"改模板不丢状态、改逻辑丢状态"的底层原因——它们走的是两个不同的方法。`rerender` 只碰 render，`reload` 换的是整个组件定义，实例上的状态自然会被重置。

### 9. 和 Webpack 的 HMR 对比

两者思路一致（都是找边界 + 冒泡），但实现层差别不小：

| 维度 | Webpack | Vite |
|---|---|---|
| 更新产物 | manifest JSON + hot-update JS chunk | 客户端直接 `import()` 新模块 |
| 传输方式 | JSONP 拉 `[chunkId].[hash].hot-update.js` | ESM 动态 import，URL 带 `?t=` 时间戳 |
| 边界表达 | `module.hot.accept()` | `import.meta.hot.accept()` |
| 冒泡终点 | 到达 entry 就失败 → 整页刷新 | 走到 `!importers.size` → full-reload |
| 模块图 | 编译期确定，全量构建 | 按需分析，浏览器请求时才建 |

Webpack 官方对冒泡的描述很精确：*"For each invalid module, there needs to be an update handler in the module or in its parent(s). Otherwise, the invalid flag bubbles up."* 和 Vite 的 `propagateUpdate` 是同一个算法，只是 Webpack 在 `apply` 阶段做，Vite 在服务端推送前就做完了。

Webpack 有个容易搞错的知识点：**hot-update 文件名里的 hash 是"新版本的 hash"，不是旧版本的。** 因为 update 描述的是"从旧版本变化到新版本"，名字标识的是目标版本。

### 10. 为什么你的 HMR 会失效

回到第三个面试问法。整页刷新只有两个根本原因：

**原因一：改动落在死路里。**
传播一路向上找不到边界，最后撞到 `!importers.size`。典型场景：改了 `main.js`、改了没写 `accept` 的工具函数、改了 store 的某个 action。Vite 官方 troubleshooting 写得直白：*HMR not being handled, or it falls into a circular dependency, in which case a full reload is triggered.*

对症办法：在合适的位置补一个边界。比如 Redux/Zustand 这类 store，官方的 store 中间件其实已经在做这件事；纯手写的全局模块就得自己 `accept`。

**原因二：循环依赖。**
循环依赖里模块的执行顺序不确定，局部替换可能拿到半初始化的模块。Vite 的处理很直接：

```js
if (isWithinCircularImport) {
  importPromise.catch(() => {
    console.info(
      `[hmr] ${acceptedPath} failed to apply HMR as it's within a circular import. ` +
      `Reloading page to reset the execution order. ` +
      `To debug and break the circular import, you can run \`vite --debug hmr\``
    );
    pageReload();
  });
}
```

注意 payload 里的 `isWithinCircularImport` 字段——它就是给客户端做这个判断用的。调试手段也给了：`vite --debug hmr` 会把静态分析结果和传播过程打出来，能看到 `[self-accepts]` / `[accepts-deps]` / `[detected api usage]` 这些标记，直接定位哪个模块没接住。

## 其实你每天都在用

- **改一行 CSS，浏览器不闪、滚动位置不变**：CSS 模块自己就是边界，`updateStyle` 换掉 `<style>` 的内容。
- **改 Vue 的 `<template>`，`<input>` 里已经输一半的内容还在**：走 `rerender`，组件实例没被销毁。
- **改 Vue 的 `<script setup>` 里的 `ref` 初始值，页面上的值回到初始状态**：走 `reload`，组件定义被换了。
- **在 Pinia store 里加一个 action，页面整页刷新了**：你的 store 模块没有被任何边界接住，传播撞了死路。Pinia 的 HMR 支持需要显式写 `if (import.meta.hot) { import.meta.hot.accept(acceptHMRUpdate(useStore, import.meta.hot)) }`。
- **改 `vite.config.ts`，整个 dev server 重启了**：配置文件和客户端环境文件变更不走模块传播，直接重启 dev server 再整页刷新。
- **改一个 `.env` 文件，页面全刷了**：同理，环境变量变更触发的是 full-reload（`path: '*'`）。
- **改 `index.html`，整页刷新了**：HTML 不是 JS 模块，进不了模块图，只能整页重来。
- **React 项目里改文件偶尔整个组件树 remount、useState 全丢**：多半是文件里出现了非组件的命名导出，Fast Refresh 无法做 identity 追踪，只能退化成 remount。
- **删掉一个组件文件，控制台打印样式被移除**：`import.meta.hot.prune()` 触发了，CSS 模块被移除时会清掉对应的 `<style>`。
- **改共享工具函数库，全项目刷新**：工具库通常没写 `accept`，而且被大量模块引用，传播路径必然撞死路。

## 常见误解（FAQ）

**❌ 误区一："HMR 就是自动刷新浏览器"**

这是 Live Reload。HMR 的区别在于**状态保留**：它在服务端先沿模块图找边界，找到就只重新 import 受影响的模块，找不到才降级成刷新。判断标准很简单——你改完代码，页面滚动位置和表单内容还在不在。

**❌ 误区二："`import.meta.hot.accept()` 会自动帮我更新内存里的旧引用"**

不会。`accept` 只做两件事：① 告诉 Vite「我是边界」；② 把新模块作为参数交给你的回调。旧变量怎么指向新实现、状态怎么迁移，全是你（或插件）的责任。这就是为什么手写模块的 HMR 很容易出错，而 Vue/React 插件生成的代码能正常工作——它们替你写好了这套交接逻辑。

**❌ 误区三："只要模块有 importer，更新就能被接住"**

错，而且这是我实测直接推翻的。`mid.js` 有 importer（`entry.js` 引用了它），但改它依然整页刷新——因为传播爬到 `entry.js` 后，`entry.js` 既不是边界、也没有 importer，撞了死路。**能否被接住取决于链上有没有边界，而不是链条有多长。**

**❌ 误区四："payload 里的 `path` 就是被修改的文件"**

不是。`path` 是**边界模块**（谁注册了回调），`acceptedPath` 才是**真正变更的模块**（要重新 import 的那个）。我实测改 `dep.js` 时，服务端推的是 `path: "/src/acceptor.js", acceptedPath: "/src/dep.js"`。搞反了会完全理解错客户端的匹配逻辑。

**❌ 误区五："CSS 更新走的是 `css-update` 类型"**

Vite 8 已经删掉这个类型了（我在 `dist/` 里 grep 命中数为 0）。CSS 模块的产物自带 `accept()`，走的是普通 `js-update` 路径，由 `updateStyle` 维护 `<style>` 标签。如果你看过老文章说"CSS 走单独通道"，那是 Vite ≤ 7 的行为。

**❌ 误区六："`accept()` 可以接受动态计算的依赖路径"**

不行。`import.meta.hot.accept(` 后面必须是字符串字面量或字面量数组，遇到模板字符串 Vite 会直接抛错：`can only accept string literals or an Array of string literals.`。因为编译期需要确定依赖路径来建模块图，动态路径无从下手。

**❌ 误区七："纯 JS 模块都会被注入 `import.meta.hot`"**

不是。注入条件是 `hasHMR && !ssr && !isClassicWorker`，而 `hasHMR` 只有你源码里出现了 `import.meta.hot` 才为真。我实测 `store.js`（无 hot 代码）的 transform 产物里根本没有 `__vite__createHotContext`。这也解释了为什么没写 HMR 代码的模块改起来必然整页刷新——它压根没有 hot 上下文可用。

**❌ 误区八："`isSelfAccepting` 和 `acceptedHmrDeps` 是一回事"**

两码事。`accept()`（不带参数）→ `isSelfAccepting = true`；`accept('./dep.js')` → 只往 `acceptedHmrDeps` 塞一条，`isSelfAccepting` 仍是 `false`。我实测的 `acceptor.js` 就是后者。传播算法里对这两个字段的检查是分开的两步。

**❌ 误区九："改 Vue 的 script 也能保住组件状态"**

保不住。改 `<script>` 走 `reload`（换整个组件定义），改 `<template>` 才走 `rerender`（只换 render 函数）。插件用 `_rerender_only` 标记分流。所以"改模板不丢状态"是对的，"改什么都不丢状态"是错的。

## 一句话总结

HMR 的完整链路是「文件监听 → 沿模块图向上传播找边界 → 找到就按 `dispose → 新模块执行 → accept 回调` 交接，找不到就整页刷新」；面试时能把「**边界是 `accept` 声明出来的，传播撞到没有 importer 的模块就是死路**」这句话讲清楚，再补一句「payload 里 `path` 是边界、`acceptedPath` 是变更源」，这道题就稳了。
