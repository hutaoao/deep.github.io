> **一句话概括：** HTTP/2 没有改 HTTP 的语义（方法、状态码、头部都没变），它只做了一件事——把传输层从"文本串行"改成"二进制多路复用"，让一个 TCP 连接上可以同时跑几十个请求而不互相阻塞。

## 一、核心知识点

### 1. 队头阻塞：HTTP/1.1 的核心痛点

```js
// HTTP/1.1 在一个连接上：请求必须排队，前面的没响应完，后面的发不了
// 6 个连接 × 1 个并发 = 6 个并发请求
// 100 个资源 ÷ 6 = 约 17 轮串行
// 100ms RTT × 17 = 1.7 秒纯排队时间

// HTTP/2：1 个连接，所有请求同时发送
// 100ms RTT × 1 = 0.1 秒排队时间
```

### 2. 二进制分帧：HTTP/2 的基石

```js
// HTTP/1.1：文本协议 → 每个请求是字符串，解析靠换行符
// HTTP/2：二进制协议 → 每个请求被切成帧（Frame），9 字节固定头 + 负载

// 帧类型：
// HEADERS (0x1)：传头部 → 已压缩
// DATA (0x0)：传 body → 可以分多帧
// SETTINGS (0x4)：连接参数协商
// PUSH_PROMISE (0x5)：服务端预告"我要推送这个资源了"
// GOAWAY (0x7)：优雅关闭连接

// 一个请求 = HEADERS 帧 + N 个 DATA 帧，通过 Stream ID 关联
// 不同 Stream 的帧可以交错发送（这就是多路复用的本质）
```

### 3. HPACK 头部压缩

```js
// HTTP/1.1 每个请求的 Header 约 800-1000 字节，纯文本重复发送
// HTTP/2 HPACK 压缩后约 30-50 字节，节省 80-90%

// 三层压缩：
// ① 静态表：61 个预定义常用字段（如 :method: GET → 索引 2）
// ② 动态表：连接生命周期内缓存新出现的头部
// ③ Huffman 编码：对字符串值进一步压缩
```

### 4. Server Push：服务端主动推送

```js
// 流程：客户端请求 index.html
// 服务端在返回 HTML 之前先推送 style.css 和 app.js
// 客户端收到推送通知 → 放入缓存 → HTML 解析到 <link> 时直接命中缓存

// Nginx 配置：
// location = / {
//   http2_push /style.css;
//   http2_push /app.js;
// }

// 注意：过度推送会浪费带宽（浏览器可能已经有缓存了）
// 更好的做法：用 <link rel="preload"> 提示 + CDN 自动判断是否推送
```

### 5. 流优先级

```js
// HTTP/2 允许声明资源的依赖关系和权重（1-256）
// 浏览器会设置：HTML > 关键 CSS > 关键 JS > 非关键 CSS/JS > 图片
// 服务端根据优先级决定先发送哪些帧

// 这就是为什么 HTTP/2 下首屏 CSS 比页面底部的图先到
```

## 二、其实你每天都在用

- **Chrome DevTools Network 面板的 Protocol 列**：看到 h2 就说明走了 HTTP/2，看到 http/1.1 说明还有优化空间
- **GitHub 页面的快速加载**：大量小资源（头像、图标、片段）在 HTTP/1.1 下会排队，在 HTTP/2 下全部并发
- **Nginx 的 `listen 443 ssl http2`**：这行配置就是你让 Nginx 开启 HTTP/2 的全部操作了
- **CDN 自动升级**：Cloudflare、阿里云 CDN 默认就提 供 HTTP/2，你的源站甚至不用配
- **移动端的弱网体验**：HTTP/2 的连接复用在高延迟移动网络（4G 延迟 50-100ms）下提升最明显

## 三、常见误解（FAQ）

**❌ 误区一："HTTP/2 替代了 HTTPS"**

HTTP/2 和 HTTPS 是两层。HTTPS 是在 TCP 之上加 TLS 加密，HTTP/2 是在 TLS 之上跑 HTTP 语义。主流浏览器只支持 HTTPS + HTTP/2 的组合（h2），但技术上 HTTP/2 可以在明文 TCP 上跑（h2c）。它们是互补关系，不是替代关系。

**❌ 误区二："HTTP/2 下就不用合并 CSS/JS 了"**

对了一半。CSS Sprite、JS Bundle 这些"人工合并"确实不需要了——HTTP/2 多路复用让大量小文件几乎零额外开销。但 HTTP/2 仍然建议做代码层面的 tree-shaking 和 code splitting，只是不推荐为了"减少请求数"而机械合并文件。

**❌ 误区三："HTTP/2 没有队头阻塞了"**

HTTP 层的队头阻塞解决了，但 TCP 层的队头阻塞还在——如果 TCP 包丢失了，该包后面的所有包都要等重传。这就是 HTTP/3 要解决的：基于 UDP 的 QUIC 协议每个流独立传输，一个流的丢包不影响其他流。

**❌ 误区四："迁移到 HTTP/2 需要改代码"**

不需要改任何业务代码。HTTP/2 是传输层的升级，请求/响应的语义完全不变。你只需要升级服务器软件（Nginx 1.9.5+）并配置 TLS 证书。对前端代码来说是完全透明的。

## 四、一句话总结

HTTP/2 是最低成本的性能优化——不改一行代码，只需升级服务器、配好 TLS，就能让资源加载速度提升 50-70%，尤其在多资源、高延迟的移动端场景下，效果立竿见影。
