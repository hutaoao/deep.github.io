## 一句话概括

先说结论：**切片变量本身只存三个东西——指向底层数组的指针、长度 len、容量 cap**，数据在底层数组里。切片是"值"，但值里装着指针。

面试问切片，翻来覆去就四句：

- len 和 cap 有什么区别？
- `append` 会不会改到原切片？
- 切片传进函数，为什么 `append` 改了长度外面看不到？
- 扩容是翻倍吗？

这四问其实是同一个知识点的不同侧面。把"24 字节"这件事想明白，四问一起解决。

## 核心知识点

### 1. len 是"能读几个"，cap 是"最多能长到几个"

```go
package main

import "fmt"

func main() {
	s := make([]int, 2, 5)      // len=2 cap=5，后 3 个位置已经分配好但不可见
	fmt.Println(len(s), cap(s)) // 2 5

	// s[2] = 1 // ❌ panic: runtime error: index out of range [2] with length 2

	s = s[:3] // 只要不超过 cap，重新切片是合法的
	s[2] = 1
	fmt.Println(s, len(s), cap(s)) // [0 0 1] 3 5

	s = s[:0] // 清空但容量还在，可以反复复用
	fmt.Println(s, len(s), cap(s)) // [] 0 5
}
```

三条硬规则：

1. **下标只能到 `len-1`**，越界就是 `index out of range [2] with length 2`——哪怕 cap 还有 3 个空位。
2. **想用到 cap 里剩下的位置，先 `s = s[:n]` 把 len 拉上去**，这是合法操作（不超过 cap 就行）。
3. **`s = s[:0]` 是"逻辑清空"**，底层数组一个字节都没释放，后面 append 直接复用，不触发分配。

cap 在两索引子切片（`s[low:high]`）时怎么算，记住一个公式：`cap = 原 cap - low`。所以 `make([]int, 5, 10)[2:3]` 的 len 是 1、cap 是 8——**从索引 2 一直到原数组末尾**都还在这个视图的势力范围内。

### 2. append：cap 够就"原地写"，这时候会踩到别人的数据

```go
package main

import "fmt"

func main() {
	// cap 还有余量 → 直接写进底层数组，不分配
	a := make([]int, 2, 3)
	b := append(a, 100)
	c := append(a, 200)
	fmt.Println(b, c) // [0 0 200] [0 0 200]  ← b 被 c 覆盖了

	// cap 刚好用满 → 扩容，各走各的
	d := make([]int, 2, 2)
	e := append(d, 100)
	f := append(d, 200)
	fmt.Println(e, f) // [0 0 100] [0 0 200]
}
```

第一段是**线上事故的经典模板**：`b` 和 `c` 都往 `a` 的第 3 个位置写，后写的覆盖先写的，最后两个变量拿到同一个值。第二段因为 cap 用满了，两次都新建了数组，反而互不影响。

所以两条铁律：

- **`append` 的返回值必须接住**。写 `append(s, 3)` 单独一行编译就报 `append(s, 3) (value of type []int) is not used`——Go 干脆禁止你忽略它，因为长度可能变了、底层数组可能换了。
- **两个变量共享底层数组时，往任一边 append 都可能污染另一边**。要独立就 `slices.Clone(s)` 或 `copy` 一份。

### 3. 传参：能改元素，改不了长度

```go
package main

import "fmt"

func addLen(s []int)   { s = append(s, 100) } // 改的是副本的描述符
func addPtr(s *[]int)  { *s = append(*s, 100) }
func setFirst(s []int) { s[0] = 777 } // 改的是同一块底层数组

func main() {
	base := []int{1, 2, 3}

	addLen(base)
	fmt.Println(base, len(base)) // [1 2 3] 3   ← 长度没变

	setFirst(base)
	fmt.Println(base) // [777 2 3]   ← 元素变了

	addPtr(&base)
	fmt.Println(base, len(base)) // [777 2 3 100] 4
}
```

一句话解释：**传参复制的是那 24 字节的切片头**。函数里的 `s` 是副本，`append` 让副本指向别处（或至少改了副本的 len），调用方的头一动不动。但副本里的指针和调用方相同，所以写元素是同一块内存。

Rob Pike 那篇官方博客的原话可以直接背：**"the contents of a slice argument can be modified by a function, but its header cannot."**

想让函数帮你 append，就两条路：传指针 `*[]int`，或者返回新切片 `s = addOne(s)`——后者更 Go 一些。

### 4. 扩容规则 + 三索引封顶 + 内存不释放

**扩容规则**（Go 1.18 起，沿用至今）：

- 需要的容量超过当前两倍 → 直接用需要的
- 当前 cap 小于 256 → 直接翻倍
- 当前 cap 更大 → 倍率随 cap 增长**一路从 2 倍滑向 1.25 倍**，不是硬跳
- 最后一步还要**按内存分配器的尺寸档向上取整**

最后这条对齐最坑：算出来是 200，实际拿到 224。实测（`len = cap = n` 时 append 一个元素）：

| 原 cap | append 后 cap |
| --- | --- |
| 100 | 224 |
| 255 | 512 |
| 256 | 512 |
| 1000 | 1536 |

结论：**别背具体数字，记住"倍率从 2 倍一路滑向 1.25 倍，最后再对齐"**，保证的是摊还 O(1)。

**三索引切片** `s[low:high:max]` 能顺手把 cap 锁死，让后面的 append 必然复制：

```go
package main

import "fmt"

func main() {
	origin := []int{1, 2, 3, 4}
	limited := origin[0:2:2] // len=2 cap=2，和 origin 断干净
	limited = append(limited, 99)
	limited[0] = -1
	fmt.Println(origin, limited) // [1 2 3 4] [-1 2 99]  ← origin 完好

	// 反过来：大数组摘一小段，cap 还在，整块内存都释放不掉
	big := make([]byte, 1<<20)
	small := big[:10]
	fmt.Println(len(small), cap(small)) // 10 1048576
}
```

`small := big[:10]` 这段就是真实的内存泄漏：只要 `small` 活着，那 1MB 的底层数组就整块被 GC 认为是可达的。修法就是 `small = slices.Clone(big[:10])` 或 `big[:10:10]`。

## 落到项目里长什么样

1. **已知数量就预分配**：`list := make([]Item, 0, len(ids))`。不预分配也行，但 10 万条数据会多复制十几次底层数组。
2. **循环里复用缓冲**：`buf = buf[:0]` 每轮开头清长度、不释放容量，比每轮 `make` 少一堆分配。日志拼装、批量导出都这么写。
3. **从大 buffer 里摘小片段必须切断**：上传解析、读文件常要"取前 10 个字节做魔数判断"，`data[:10]` 会把整个文件留在内存里，加个 `slices.Clone` 或者三索引。
4. **删元素用 `append(a[:i], a[i+1:]...)` 会原地挪数据**：它不新建数组，后面的元素整体前移。如果别处还持着 `a` 的旧切片视图，看到的数据也会跟着变。
5. **返回切片的函数要明确契约**：要么"内部新建、调用方随便改"，要么"返回共享视图、别乱改"。混着来是并发场景下最难查的一类 bug。

跟前端对照一下：JS 的 `push` 原地改数组，返回值是新长度；Go 的 `append` **返回新切片**，必须接住，因为底层数组可能已经换了一块。这是从 JS 转 Go 最常踩的第一个坑。

## 常见误解（FAQ）

**❌ 误区1："`append` 每次都会新建底层数组"**

不会。cap 还有余量就原地写，只有 `len == cap` 时才分配新数组并拷贝旧数据。这也是它被设计成"返回新切片"而不是"原地改"的原因——行为不一致，只能靠返回值统一。

**❌ 误区2："`append` 之后原切片一定受影响"**

看有没有扩容。没扩容时两个切片共享底层数组，新元素写在同一块内存上，别人看得见；扩容后各走各的。**能不能互相影响，取决于 cap 有没有用满**，不是取决于"append 这个动作本身"。

**❌ 误区3："切片传进函数，函数里 append 之后外面长度也会变"**

不会。传的是切片头的副本，副本的 len 改了跟调用方无关。实测外面依旧 `[1 2 3] 3`。想改长度就传 `*[]int` 或者接收返回值。

**❌ 误区4："扩容就是容量翻倍"**

cap 小于 256 才翻倍。cap 越大倍率越小，一路滑到 1.25 倍左右（不是"到 256 就变 25%"，实测 256 扩容后是 512，还是翻倍）。而且最后还要按内存尺寸档向上取整，所以 100 扩容后是 224 而不是 200。

**❌ 误区5："cap 是 5，所以 `s[3]` 可以直接赋值"**

不行。下标上限是 `len-1`，跟 cap 无关，越界报 `index out of range [3] with length 2`。要先用 `s = s[:4]` 把长度拉上去，再写 `s[3]`。

**❌ 误区6："`copy` 会自动扩容目标切片"**

不会。`copy(dst, src)` 只复制 `min(len(dst), len(src))` 个元素，返回实际复制的个数。目标不够长就只复制一部分，一个字节都不多分配。要扩容得先 `make` 或 `slices.Grow`。

## 一句话总结

**切片就是 24 字节的头：指针、len、cap。len 管你能不能读，cap 管 append 会不会搬家；传参复制的是这个头，所以元素改得动、长度改不动；扩容倍率从 2 倍滑到 1.25 倍、最后按内存对齐——把这三句说出来，切片题基本就问不下去了。**
