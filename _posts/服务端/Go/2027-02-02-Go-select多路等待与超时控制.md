## 一句话概括

上一题说 channel 是管道，那 `select` 就是**同时盯好几根管道的水龙头**：哪个先出水就从哪个接。

它的语义只有三句话：

1. 有一个 case 就绪（能收或能发）→ 走那个；
2. 有多个就绪 → **随机挑一个**，源码顺序没有任何优先级；
3. 一个都没就绪 → 阻塞，除非你写了 `default`。

面试问 select 通常不考语法，而是考**你要用 select 干什么**——超时控制、退出信号、多路合并。所以真正要背的是那几个坑：随机不是优先级、break 跳不出去、超时之后 goroutine 还在漏。

## 核心知识点

### 1. select = channel 版的 switch

语法跟 `switch` 长得一样，区别是**每个 case 必须是一次 channel 的收或发**，另外 `case` 后面不能跟普通表达式。

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	fast := make(chan string, 1)
	slow := make(chan string, 1)

	go func() {
		time.Sleep(30 * time.Millisecond)
		slow <- "慢的回来了"
	}()
	go func() {
		time.Sleep(10 * time.Millisecond)
		fast <- "快的回来了"
	}()

	select {
	case v := <-fast:
		fmt.Println("选中:", v)
	case v := <-slow:
		fmt.Println("选中:", v)
	}
}
```

实测输出 `选中: 快的回来了`——这就是 select 的核心价值，**你不需要知道哪个先回，谁先回就处理谁**。前端最接近的东西是 `Promise.race`，区别是 select 不新建 promise，只是"等一组 channel"。

如果所有 case 都永远不就绪，就永久阻塞：

```go
package main

func main() {
	select {} // 一个 case 都没有：永久阻塞
}
```

实测直接退出，报的是：

```text
fatal error: all goroutines are asleep - deadlock!

goroutine 1 [select (no cases)]:
main.main()
```

注意 `select {}` 不是"死循环"——它是**挂起**，不烧 CPU，运行时发现所有 goroutine 都睡死了才报 fatal error。所以别拿它当"故意卡住"的写法，除非你真想让 goroutine 永远停在那儿。

### 2. default：不阻塞的"试一下"

加了 `default`，select **永远不会阻塞**：有 case 就绪走 case，全都没就绪立刻走 default。这个特性最大的用途是"非阻塞地试一次"。

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)

	for i := 1; i <= 3; i++ {
		select {
		case ch <- i:
			fmt.Println("塞进去了", i)
		default:
			fmt.Println("满了，丢弃", i)
		}
	}

	for {
		select {
		case v := <-ch:
			fmt.Println("取出", v)
		default:
			fmt.Println("空了，退出")
			return
		}
	}
}
```

实测输出：`塞进去了 1` / `塞进去了 2` / `满了，丢弃 3` / `取出 1` / `取出 2` / `空了，退出`。

这就是**削峰**的雏形：队列满了宁可丢也不阻塞调用方，打日志、埋点上报这类场景非常常用。

但 `default` 有个致命用法要避开：

```text
// ❌ 别这么写：没有任何 case 就绪时会 100% 空转，直接烧满一个核
for {
	select {
	case v := <-ch:
		handle(v)
	default:
		// 什么都不做，立刻进入下一轮
	}
}
```

`for` + `default` = **忙轮询**。要么去掉 `default` 让它阻塞，要么加 `time.Sleep` / `time.Ticker` 控制节奏。

### 3. 超时：`case <-time.After(d)`

标准写法就三行。`time.After(d)` 返回一个 `<-chan time.Time`，到点往里发一次时间：

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

var errTimeout = errors.New("超时了")

func fetch(d time.Duration) (string, error) {
	result := make(chan string, 1) // ⚠️ 缓冲 1，关键
	go func() {
		time.Sleep(d)
		result <- "数据"
	}()

	select {
	case r := <-result:
		return r, nil
	case <-time.After(50 * time.Millisecond):
		return "", errTimeout
	}
}

func main() {
	r, err := fetch(10 * time.Millisecond)
	fmt.Println(r, err) // 数据 <nil>

	r, err = fetch(200 * time.Millisecond)
	fmt.Printf("%q %v\n", r, err) // "" 超时了（超时分支返回空字符串）
}
```

面试官大概率追问一句："**`result` 为什么要有缓冲？**" 这是这道题真正的考点，答不上来就白写了。

因为超时那个分支赢了之后，就再也没人去收 `result` 了。如果它是无缓冲的，那个后台 goroutine 会永远卡在 `result <- "数据"` 上——**泄漏了，而且 GC 收不走**。加个容量 1 的缓冲，它可以自己把结果塞进去然后正常退出。实测对比：

```go
package main

import (
	"fmt"
	"runtime"
	"time"
)

// ❌ 无缓冲，超时后 worker 卡死在发送上
func badFetch(d time.Duration) {
	result := make(chan string)
	go func() {
		time.Sleep(d)
		result <- "数据"
	}()
	select {
	case <-result:
	case <-time.After(50 * time.Millisecond):
	}
}

// ✅ 缓冲 1，超时后 worker 也能把结果塞完退出
func goodFetch(d time.Duration) {
	result := make(chan string, 1)
	go func() {
		time.Sleep(d)
		result <- "数据"
	}()
	select {
	case <-result:
	case <-time.After(50 * time.Millisecond):
	}
}

func main() {
	fmt.Println("起手:", runtime.NumGoroutine())

	badFetch(200 * time.Millisecond)
	time.Sleep(250 * time.Millisecond)
	fmt.Println("badFetch 之后:", runtime.NumGoroutine())

	goodFetch(200 * time.Millisecond)
	time.Sleep(250 * time.Millisecond)
	fmt.Println("goodFetch 之后:", runtime.NumGoroutine())
}
```

实测 `起手: 1` / `badFetch 之后: 2` / `goodFetch 之后: 2`——泄漏的那个 goroutine 一直活着，只有 badFetch 涨了一个。

另外两个配套知识点：

- **循环里用 `time.After` 要小心**。Go 1.23 起，不再被引用的 Timer 可以被直接回收（官方 release notes 原文：Timers that are no longer referred to by the program become eligible for garbage collection immediately），所以 1.23+ 在循环里写 `case <-time.After(d)` 不像老版本那样攒一堆 timer。但**一个总 deadline 就建一个 timer 放循环外**，这个原则和版本无关。
- **退出信号用 `close(done)` 或 `ctx.Done()`，不是发一个值**。关闭是广播，所有监听方一起醒。

```go
package main

import "fmt"

func worker(jobs <-chan int, done <-chan struct{}, out chan<- int) {
	sum := 0
	for {
		select {
		case v, ok := <-jobs:
			if !ok {
				out <- sum
				return
			}
			sum += v
		case <-done:
			out <- sum
			return
		}
	}
}

func main() {
	jobs := make(chan int, 3)
	out := make(chan int, 1)
	done := make(chan struct{})

	jobs <- 1
	jobs <- 2
	close(jobs) // 关闭是广播：所有 <-jobs 都会醒

	go worker(jobs, done, out)
	fmt.Println("sum =", <-out) // 3
}
```

### 4. 五个坑

**坑一：以为 case 有优先级。** 多个 case 同时就绪时，Go 是**均匀随机**选一个。实测两个都就绪的 case 跑 1000 次：

```go
package main

import "fmt"

func main() {
	a := make(chan int, 1)
	b := make(chan int, 1)
	a <- 1
	b <- 2

	countA, countB := 0, 0
	for i := 0; i < 1000; i++ {
		select {
		case <-a:
			countA++
			a <- 1
		case <-b:
			countB++
			b <- 2
		}
	}
	fmt.Println("a:", countA, "b:", countB)
}
```

我跑出来是 `a: 483 b: 517`，每次结果都不一样，但长期一定往五五开靠。如果它严格按源码顺序，`a` 会拿满 1000 次。

想"退出优先"，只能**先单独试一次**再进正式 select：

```go
package main

import "fmt"

func worker(jobs <-chan int, done <-chan struct{}, strict bool) int {
	processed := 0
	for {
		if strict {
			// 先探一次：已经取消了就直接返回，不用跟 jobs 抢
			select {
			case <-done:
				return processed
			default:
			}
		}
		select {
		case <-done:
			return processed
		case <-jobs:
			processed++
		}
	}
}

func main() {
	run := func(strict bool) int {
		total := 0
		for i := 0; i < 20; i++ {
			jobs := make(chan int, 1000)
			for j := 0; j < 1000; j++ {
				jobs <- j
			}
			done := make(chan struct{})
			close(done) // 一开始就已经取消了
			total += worker(jobs, done, strict)
		}
		return total
	}
	fmt.Println("普通 select，20 轮共多处理:", run(false))
	fmt.Println("先探一次 done，20 轮共多处理:", run(true))
}
```

我连跑几遍，第一行稳定在 20 多（每次不一样），第二行永远是 0。取消之后还会"顺手"多处理二十几个任务，这就是没有优先级的代价。

**坑二：`break` 只跳出 select，不跳出 for。** 和 `switch` 一样，`break` 的作用范围是 select 本身：

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 1
	ch <- 2
	close(ch)

	guard := 0
	for {
		select {
		case v, ok := <-ch:
			if !ok {
				break // ❌ 只跳出 select，for 接着转
			}
			fmt.Println("收到", v)
		}
		guard++
		if guard > 4 {
			fmt.Println("死循环了，跑了", guard, "轮")
			break
		}
	}
}
```

实测 `收到 1` / `收到 2` / `死循环了，跑了 5 轮`——channel 早就关了，但循环还在空转。正确做法是 `return` 或者给 `for` 打标签用 `break loop`。

**坑三：超时赢了，发送方漏了。** 上面 §3 已经实跑过（1 → 2）。凡是 `select` 一侧可能提前返回的地方，另一侧的发送都要考虑"没人收怎么办"：给缓冲、或者用 `ctx.Done()` 让发送方也能退出。

**坑四：nil 分支是开关，已关闭分支是陷阱。**

`case` 上的 channel 是 nil 时，这个分支**永远不就绪**，等于被静默禁用——这不是 bug，是特性，可以用它动态关掉某条路：

```go
package main

import "fmt"

func main() {
	var nilCh chan int // 永远是 nil，这个分支等于关掉
	ready := make(chan int, 1)
	ready <- 7

	for i := 0; i < 3; i++ {
		select {
		case v := <-nilCh:
			fmt.Println("永远不会打印", v)
		case v := <-ready:
			fmt.Println("收到", v)
			ready <- v + 1
		}
	}
}
```

反过来，**已关闭的 channel 在 select 里永远就绪**（立刻返回零值），如果它和别的分支并列，可能一直赢，把正常分支饿死：

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	done := make(chan struct{})
	close(done)

	for i := 0; i < 3; i++ {
		select {
		case <-done: // 每次都立刻返回
			fmt.Println("done 分支", i)
		case <-time.After(10 * time.Millisecond):
			fmt.Println("超时分支", i)
		}
		time.Sleep(20 * time.Millisecond)
	}
}
```

实测三次全是 `done 分支`。所以收到关闭信号后**要立刻 return**，别让它留在循环里继续被 select。

**坑五：case 里的函数不是"选中了才执行"。** 进入 select 时，所有 case 的 channel 表达式和发送值都会**按源码顺序各求值一次**，不管最后哪个分支赢：

```go
package main

import "fmt"

func pick() chan int {
	fmt.Println("pick() 被调用")
	return make(chan int) // 无缓冲、没人收，这个分支不可能就绪
}

func compute() int {
	fmt.Println("compute() 被调用")
	return 42
}

func main() {
	done := make(chan struct{})
	close(done)

	select {
	case pick() <- compute(): // 两个函数都会跑
		fmt.Println("选中了发送分支")
	case <-done:
		fmt.Println("选中了 done 分支")
	}
}
```

实测输出三行：`pick() 被调用` / `compute() 被调用` / `选中了 done 分支`。所以**别在 case 里放有副作用或者很贵的调用**，select 不是惰性分发。

## 落到项目里长什么样

1. **等最先返回的结果**：并发调两个数据源（缓存 + DB），`select` 谁先回用谁，另一个丢弃——这就是 Go 版的 `Promise.race`。
2. **接口超时**：`http.Client{Timeout: ...}` 标准库帮你做了，但自己包 RPC、数据库查询时就得手写 `select` + `time.After`，记得给结果 channel 加缓冲。
3. **消费队列 + 优雅退出**：`for { select { case job := <-jobs: ... case <-ctx.Done(): return } }`，K8s 滚动更新时靠这个把在途任务收完再退出。
4. **多路合并（fan-in）**：好几个 goroutine 往各自 channel 写，主流程用一个 `for` + `select` 汇总，不用加锁也不用 WaitGroup。
5. **WebSocket 推送**：一个 goroutine 里同时等"业务消息"和"心跳 ticker"，`select` 两路一起看，比两条线程简单得多。

和前端对照着记：`Promise.race` 是"谁先 resolved 用谁"，`select` 是"谁先就绪走谁"，思路完全一样；区别是 Go 这边**没赢的分支不会自动取消**，得自己用 context 通知对方收工——这也是坑三的根源。

## 常见误解（FAQ）

**❌ 误区1："select 从上往下匹配，写在前面的 case 优先"**

不，多个 case 同时就绪时是**均匀随机**。实测两个都就绪跑 1000 次，结果接近五五开（一次跑出 483 / 517）。想要优先级只能拆成两段：先用带 `default` 的 select 单独探一次高优先级分支，再进正式 select。

**❌ 误区2："加了 default 更安全，循环里都加上"**

`default` 的作用是"不阻塞"。放在 `for` 里，没有 case 就绪时会 100% 空转，直接烧满一个 CPU 核。要么去掉 default 让它阻塞，要么用 ticker / Sleep 控制节奏。

**❌ 误区3："超时返回了，后台那个 goroutine 就自己结束了"**

不会。超时只是 select 这一侧不等了，后台 goroutine 还卡在发送上。实测 `runtime.NumGoroutine()` 从 1 涨到 2 就再也不降。解法是给结果 channel 缓冲 1，或者用 `ctx.Done()` 让发送方也能退出。

**❌ 误区4："select 里写 break 就能退出外面的 for"**

和 `switch` 一样，`break` 只结束 select 本身。实测关闭 channel 后 `for` 还在空转（跑到第 5 轮靠 guard 才停）。要退循环得用 `return` 或 `break 标签名`。

**❌ 误区5："select 可以等任何东西，比如锁、普通变量、Promise"**

只能等 channel 的**收和发**。`case v := <-ch`、`case ch <- v` 是仅有的两种形式，`case x > 1` 直接编译不过。要等条件变量用 `sync.Cond`，要等异步结果就先把它转成 channel。

## 一句话总结

select 等的是"最先就绪的那根 channel"：多个就绪随机挑（没有优先级）、`default` 让它不阻塞（但别放循环里空转）、超时用 `time.After` 且结果 channel 必须带缓冲、`break` 只跳 select——这四条答出来，select 的面试就结束了。
