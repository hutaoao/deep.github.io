## 一句话概括

Gin 没有发明新东西，它只是在 `net/http` 上包了三层便利：

- **路由**：`r.GET("/users/:id", h)` 加 `r.Group("/api/v1")`，分组和参数一次搞定；
- **绑定 + 校验**：`c.ShouldBindJSON(&req)` 一句话把 body 解析进结构体并按 `binding:"required,email"` 校验；
- **中间件**：签名统一成 `func(*gin.Context)`，用 `c.Next()` 放行、`c.Abort()` 掐断。

面试重点不是背 API，而是知道**它和 net/http 的分工**，以及 `ShouldBind` 和 `Bind` 那个坑——用错了，前端只能拿到一个空 body 的 400。

## 核心知识点

### 1. 起服务、路由参数与分组

`gin.Default()` = `gin.New()` + `Logger()` + `Recovery()`。前者开箱有日志和兜 panic，后者是白板。线上一般 `gin.New()` 然后自己按需 `Use`。

```go
package main

import (
	"net/http"

	"github.com/gin-gonic/gin"
)

func authMW() gin.HandlerFunc {
	return func(c *gin.Context) {
		if c.GetHeader("Authorization") == "" {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "缺少 token"})
			return
		}
		c.Next()
	}
}

func main() {
	gin.SetMode(gin.ReleaseMode)
	r := gin.New()
	r.Use(gin.Logger(), gin.Recovery())

	v1 := r.Group("/api/v1")
	{
		v1.GET("/users/:id", func(c *gin.Context) {
			c.JSON(http.StatusOK, gin.H{
				"id":   c.Param("id"),
				"page": c.DefaultQuery("page", "1"),
			})
		})
	}

	admin := r.Group("/admin", authMW())
	{
		admin.GET("/stats", func(c *gin.Context) {
			c.JSON(http.StatusOK, gin.H{"uv": 42})
		})
	}

	r.Run("127.0.0.1:18080")
}
```

实测三发 `curl`：

```text
$ curl -s "http://127.0.0.1:18080/api/v1/users/42?page=3"
{"id":"42","page":"3"}

$ curl -s -w "\nstatus=%{http_code}\n" "http://127.0.0.1:18080/admin/stats"
{"error":"缺少 token"}
status=401

$ curl -s -w "\nstatus=%{http_code}\n" -H "Authorization: Bearer x" "http://127.0.0.1:18080/admin/stats"
{"uv":42}
status=200
```

`gin.Logger()` 打出来长这样：

```text
[GIN] 2026/11/10 - 09:02:31 | 200 | 206.334µs |       127.0.0.1 | GET      "/api/v1/users/42?page=3"
[GIN] 2026/11/10 - 09:02:31 | 401 | 100.084µs |       127.0.0.1 | GET      "/admin/stats"
```

几个要点：

- **参数用 `:` 声明、`c.Param("id")` 取**，query 用 `c.Query` / `c.DefaultQuery`。这跟 net/http 1.22 的 `"GET /users/{id}"` + `r.PathValue("id")` 是同一件事，只是语法不同。
- **`r.Group("/admin", authMW())` 的中间件只作用于组内**——实测 `/api/v1/users/42` 不需要 token，`/admin/stats` 需要。这是分组的最大价值：把"要登录"的路由聚在一起，而不是每条都挂一遍中间件。
- **组可以嵌套**，`v1.Group("/admin")` 会有 `/api/v1/admin`，鉴权中间件逐层叠加。
- `c.JSON(status, obj)` 帮你设 `Content-Type: application/json; charset=utf-8` 并序列化，省掉 net/http 里"设头 → 写码 → 写 body"的三步顺序。

### 2. 参数绑定：一定要用 ShouldBind，不要用 Bind

bind 有两套，只在**出错时**表现不同：

| 方法 | 出错时谁负责 |
| --- | --- |
| `Bind` / `BindJSON` | Gin 自己 `AbortWithError(400)`，直接结束请求 |
| `ShouldBind` / `ShouldBindJSON` | 返回 `error`，你自己决定回什么 |

第一套看着省事，实测很坑：

```go
func bindDemo(r *gin.Engine) {
	r.POST("/bind", func(c *gin.Context) {
		var req struct {
			Name string `json:"name" binding:"required"`
		}
		if err := c.BindJSON(&req); err != nil {
			return // 以为不用管，其实 Gin 已经写了 400
		}
		c.JSON(http.StatusCreated, req)
	})
}
```

```text
POST /bind  {"name":"a"}  -> 400 ct="" body=
```

状态码 400，**响应体是空的，连 Content-Type 都没设**。前端拿不到任何提示，只能显示"请求失败"。（官方文档说会把 Content-Type 设成 `text/plain`，本机 gin v1.12.0 实测连这个头都没有。）

换成 `ShouldBindJSON`，你就能自己拼错误结构：

```go
type CreateUserReq struct {
	Name  string `json:"name" binding:"required,min=2"`
	Email string `json:"email" binding:"required,email"`
	Age   int    `json:"age" binding:"gte=0,lte=150"`
}

func createUser(c *gin.Context) {
	var req CreateUserReq
	if err := c.ShouldBindJSON(&req); err != nil {
		c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()})
		return
	}
	c.JSON(http.StatusCreated, req)
}
```

实测三种错误输入，`err.Error()` 的原文：

```text
{"name":"a","email":"not-an-email","age":300}
-> Key: 'CreateUserReq.Name' Error:Field validation for 'Name' failed on the 'min' tag
   Key: 'CreateUserReq.Email' Error:Field validation for 'Email' failed on the 'email' tag
   Key: 'CreateUserReq.Age' Error:Field validation for 'Age' failed on the 'lte' tag

{"email":"ada@example.com"}
-> Key: 'CreateUserReq.Name' Error:Field validation for 'Name' failed on the 'required' tag

{"name":
-> unexpected EOF
```

注意两个信息：

1. **多条错误用换行拼在一起**（上面为了排版折行了，实际是 `\n` 分隔），所以直接丢给前端会很难看；
2. **JSON 语法错和校验失败是同一类 error**，都是 `unexpected EOF` / `Field validation`，前者不是 `validator.ValidationErrors`。

所以生产里一般做结构化输出，`errors.As` 判一下类型（需要 `import "github.com/go-playground/validator/v10"`，它是 Gin 的依赖，不用另装）：

```go
func bindError(c *gin.Context, err error) {
	var ve validator.ValidationErrors
	if errors.As(err, &ve) {
		out := make(map[string]string, len(ve))
		for _, f := range ve {
			out[f.Field()] = f.Tag() // 字段名 -> 失败的规则名
		}
		c.JSON(http.StatusBadRequest, gin.H{"fields": out})
		return
	}
	c.JSON(http.StatusBadRequest, gin.H{"error": err.Error()}) // 语法错走这里
}
```

实测输出 `{"fields":{"Email":"email","Name":"min"}}`——前端可以直接把"哪个字段错了"标在表单上，不用解析英文句子。

常用 tag 抄这一张就够：

| tag | 含义 | 备注 |
| --- | --- | --- |
| `required` | 不能是零值 | **0 和 "" 都算没传** |
| `min=2,max=20` | 长度/数值区间 | 字符串按**字符**数、数字按值 |
| `gte=0,lte=150` | 数值区间 | 想允许 0 就用这个，别用 `required` |
| `email` | 邮箱格式 | |
| `oneof=admin user` | 枚举 | |
| `uuid` / `len=11` | 格式/定长 | 手机号用 `len=11` 起步 |

最后一行那个 `required` 的坑值得单说：`Age int binding:"required"` 表示"前端必须传 age"，但 `age: 0` 会判失败，因为 0 是 int 的零值。想要"可以不传，传了就得在 0~150"，只能写 `gte=0,lte=150`。

再补一个中文场景的实测：`min/max` 对字符串数的是**字符数不是字节数**。`{"name":"中文"}` 配 `binding:"min=3"` 判失败，`"中文名"` 通过——所以前端 `input.maxlength` 和后端 `max` 数的是同一个东西，不用为中文留 buffer。

### 3. 中间件：`c.Next()` 放行，`c.Abort()` 掐断

Gin 的中间件签名统一是 `func(*gin.Context)`，靠 `c.Next()` 手动推进。实测顺序：

```text
全局 前
分组 前
handler
分组 后
全局 后
```

也就是**先进后出**，和 net/http 的 `func(http.Handler) http.Handler` 一个模型，区别只在控制方式：net/http 是"不调 `next.ServeHTTP` 就断"，Gin 是"不调 `c.Next()` 就断"。Gin 多给了一个 `c.Abort()`，语义是"**把后面所有 handler 标成跳过**"。

这个"标成跳过"很关键，实测：

```go
func abortDemo(r *gin.Engine) {
	r.GET("/abort", func(c *gin.Context) {
		fmt.Println("A 前")
		c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "no token"})
		fmt.Println("A Abort 之后还在跑")
	}, func(c *gin.Context) {
		fmt.Println("这个 handler 不会执行")
	})
}
```

```text
A 前
A Abort 之后还在跑
/abort  status=401 body={"error":"no token"}
```

**`Abort` 只拦后面的人，不拦自己**——当前函数里 `Abort` 后面的代码照跑。所以 `c.AbortWithStatusJSON(...)` 后面该 `return` 还得 `return`，不然你会接着干一堆"已经鉴权失败"的活。

更阴的是忘了写响应：

```go
func forgetResponse(c *gin.Context) {
	c.Abort() // 什么都没写，客户端会收到 200 + 空 body
}
```

实测这么写（路由名 `/abort-noreturn`）返回 **200 + 空 body**。前端看到的是"成功，但没数据"，这个 bug 能查一下午。

生产里的中间件三连，顺序是 `Recovery → Logger → CORS → 鉴权`：

```go
func cors() gin.HandlerFunc {
	return func(c *gin.Context) {
		c.Header("Access-Control-Allow-Origin", "http://localhost:5173")
		c.Header("Access-Control-Allow-Headers", "Content-Type, Authorization")
		c.Header("Access-Control-Allow-Methods", "GET, POST, PUT, DELETE, OPTIONS")
		if c.Request.Method == http.MethodOptions {
			c.AbortWithStatus(http.StatusNoContent) // 预检，直接回 204
			return
		}
		c.Next()
	}
}
```

几个实测结论：

- **CORS 那段不能省**，`gin.Default()` 里没有 CORS。OPTIONS 预检实测回 `204` 且带上 `Access-Control-Allow-Origin: http://localhost:5173`；`Allow-Origin` 千万别写 `*` 配 `Allow-Credentials: true`，浏览器直接拒。
- **`gin.Recovery()` 接住 panic 后回的是 500 + 空 body**（实测），前端同样拿不到错误信息。想要统一错误体，得自己写 Recovery 或用 `gin.CustomRecovery`。
- **`Recovery` 必须第一个 `Use`**，否则它前面那层的 panic 没人兜。gin 对 `c.Next()` 里发生的 panic 能兜住，但你自己中间件"进入阶段"的 panic 也在链上，顺序错了就漏。

### 4. 收尾：30 行以内的最简令牌桶

限流是每个接口都要问一句的东西。固定窗口有"临界点双倍"问题（59 秒和 61 秒各打满一次），令牌桶更平滑：**桶里最多 `burst` 个令牌，按固定速率补充，来一个请求扣一个，扣不到就 429。**

```go
// 用到 sync / time / net/http / gin，放在独立文件里
type limiter struct {
	mu     sync.Mutex
	tokens float64
	last   time.Time
	rate   float64 // 每秒补几个
	burst  float64
}

func newLimiter(rate, burst float64) *limiter {
	return &limiter{tokens: burst, last: time.Now(), rate: rate, burst: burst}
}

func (l *limiter) allow() bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	now := time.Now()
	// 先按流逝的时间补令牌，补不满就补到 burst 为止
	l.tokens = min(l.burst, l.tokens+now.Sub(l.last).Seconds()*l.rate)
	l.last = now
	if l.tokens < 1 {
		return false
	}
	l.tokens--
	return true
}

func rateLimit(l *limiter) gin.HandlerFunc {
	return func(c *gin.Context) {
		if !l.allow() {
			c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{"error": "请求太频繁"})
			return
		}
		c.Next()
	}
}
```

挂上去：`r.GET("/ping", rateLimit(newLimiter(1, 3)), handler)`，意思是"每秒补 1 个，最多攒 3 个"。实测连打 5 次：

```text
第 1 次 -> 200
第 2 次 -> 200
第 3 次 -> 200
第 4 次 -> 429
第 5 次 -> 429
等 1.1s 后 -> 200
```

三个必须说的点：

1. **`sync.Mutex` 不能省**，`tokens` 是多个请求 goroutine 同时改的，不加锁就是数据竞争（`-race` 一跑就红）。
2. 这个桶是**单机**的。多实例部署时每个进程各算各的，实际放行量是 N 倍——真限流得上 Redis（`INCR` + 过期，或者 Redis 版的令牌桶 Lua 脚本）。
3. 生产别手写，用 `golang.org/x/time/rate`：`lim := rate.NewLimiter(rate.Limit(10), 20)`，`lim.Allow()` 一行就是同样的语义，还带 `Wait(ctx)` 阻塞版。

## 落到项目里长什么样

1. **`main.go` 只做装配**：`gin.New()` → `Use` 中间件 → `Group` 注册路由 → `Run`。业务逻辑一律不进 `main`，handler 只做"取参 → 调 service → 写响应"。
2. **分组就是权限边界**：`/api/v1` 公开、`/admin` 挂鉴权、`/internal` 挂内网 IP 校验。一个分组的中间件挂错，影响面一眼可见。
3. **请求体和响应体各建一套 struct**：`CreateUserReq` 带 `binding` tag，`UserResp` 只带 `json` tag。绝不要把数据库 model 直接当入参——前端能改的字段你就全放开了（比如 `is_admin`）。
4. **统一错误响应**：`{code, message, fields?}` 三件套，前端拦截器按 `code` 处理。`ShouldBindJSON` 的错误务必走到你自己的格式里，别把 `Key: 'CreateUserReq.Name'...` 原样丢给用户。
5. **给前端的对齐清单**：`c.Param` 是路径、`c.Query` 是问号、`ShouldBindJSON` 只认 `Content-Type: application/json`。前端忘了设这个头，绑定的就是空结构体然后报 `required`，看起来像"后端没收到参数"。
6. **和 net/http 怎么选**：三五个接口、不想引依赖，标准库足够（1.22 之后连路由参数都有）。要分组、要绑定校验、要一套现成中间件，上 Gin 省下的模板代码就是价值。别在这上面纠结——面试官想听的是"知道两者边界"。

## 常见误解（FAQ）

**❌ 误区1："`gin.Default()` 什么都有，包含 CORS。"**
只有 `Logger` 和 `Recovery`。跨域、限流、鉴权、超时全得自己挂。前端报 CORS 错的时候，第一反应应该是"后端有没有写这段"。

**❌ 误区2："`c.Abort()` 会中断当前函数。"**
只把后续 handler 标成跳过，当前函数里 `Abort` 之后的代码照跑（实测打出了那行"Abort 之后还在跑"）。所以 `AbortWithStatusJSON` 后面必须 `return`。

**❌ 误区3："`BindJSON` 和 `ShouldBindJSON` 只是名字不同。"**
`BindJSON` 出错会自己写 400 并结束请求——实测响应体是空的、连 Content-Type 都没有，前端没法给提示。要用 `ShouldBindJSON` 自己接管错误。

**❌ 误区4：`binding:"required"` 表示"字段必须存在"。**
它判的是**零值**。`age: 0`、`name: ""` 都会判失败。数值字段想允许 0，用 `gte=0`。

**❌ 误区5："中间件不调 `c.Next()`，后面的 handler 也会执行。"**
不会。不调 `Next` 就等于链断在这里，而且响应还是 200 空 body——和 `c.Abort()` 没写响应是同一个症状。

## 一句话总结

Gin 记住三句就够：**路由分组划权限边界，`ShouldBindJSON` 拿 error 自己回错误体，中间件里 `Next` 放行 `Abort` 掐断但都别忘了 `return`**。
