## 一句话概括

Go 的闭包跟 JS 一样，抓的是**变量本身**，不是"当时的值"。而 Go 1.21 及以前，一个 `for` 循环里自始至终只有**一个**循环变量——两件事撞在一起，就是那个著名现象：`for i := 0; i < 3; i++ { go func() { fmt.Println(i) }() }` 打印出三个 3，一个 0 都没有。

Go 1.22 改了语义：`:=` 声明的循环变量每次迭代都是新实例，同样的代码读到的是 0、1、2（打印顺序不保证）。但有个容易被忽略的前提——**这个改动由模块 go.mod 里的 `go` 版本决定，不是你装了新工具链就自动生效**。

面试这条线一般这么问：「闭包捕获的是什么」「为什么 goroutine 全打印最后一个值」「1.22 之后还需要写 `v := v` 吗」。三问答得清，这题就过了。

## 核心知识点

### 1. 闭包捕获的是变量，不是值

结论一句话：**闭包 = 函数 + 它引用到的那些外部变量；只要闭包还活着，那些变量就活着，而且读写的是同一份。**

```go
package main

import "fmt"

func counter() func() int {
	n := 0
	return func() int { // 这个匿名函数捕获了 n
		n++
		return n
	}
}

func main() {
	c1, c2 := counter(), counter()
	fmt.Println(c1(), c1(), c2()) // 1 2 1
}
```

两次 `counter()` 各造一份 `n`，所以 `c1` 数到 2 的时候 `c2` 还是 1。再看"闭包改外面变量"这种更直白的：

```go
package main

import "fmt"

func main() {
	x := 0
	inc := func() { x++ }
	inc()
	inc()
	fmt.Println(x) // 2，改的就是外面那个 x
}
```

注意 `inc` 没有返回值，`x++` 直接改到了外部那个变量。**"闭包里的变量是拷贝"是最常见的错答。**

和 JS 对一下：这块两边是一致的，都是词法作用域 + 捕获变量。差别在写法——Go 没有 `this`，函数的"上下文"得靠显式捕获或结构体接收者；JS 里 `this` 丢失、要 `bind` 的那套坑，Go 里压根不存在。

### 2. 1.22 之前：一个循环只有一个变量

`for i := 0; i < 3; i++` 里的 `i`，在 Go 1.21 及以前的语义里是**整个循环唯一的一个变量**，`i++` 改的就是它。所以：

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 3; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println(i)
		}()
	}
	wg.Wait()
}
```

这段放在 `go 1.21` 的模块里实测输出 `3 3 3`（顺序不定，但值全是 3）；放在 `go 1.27` 的模块里读到的是 `0 / 1 / 2` 三个值（打印顺序由调度决定，别指望是 0 1 2）。

原因不难想：goroutine 是"先登记、后执行"，等它真被调度上 CPU，主 goroutine 早把循环跑完了，`i` 已经是 3（正是让 `< 3` 不成立的那个值）。三个 goroutine 看的是同一个 `i`，自然都读到最后一个值。

取地址的版本更狠，连"读值"都省了，三个指针干脆是同一个：

```go
package main

import "fmt"

func main() {
	var ptrs []*int
	for i := 0; i < 3; i++ {
		ptrs = append(ptrs, &i)
	}
	fmt.Println(ptrs[0] == ptrs[1], *ptrs[0], *ptrs[1], *ptrs[2])
	// go 1.21 模块：true 3 3 3
	// go 1.27 模块：false 0 1 2
}
```

1.22 之前的标准修法是"在迭代当下把值固定下来"，两种写法等价：

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	list := []string{"a", "b", "c"}
	var wg sync.WaitGroup

	// 写法一：当参数传进去（官方 FAQ 推荐，最直观）
	for _, v := range list {
		wg.Add(1)
		go func(v string) {
			defer wg.Done()
			fmt.Println("传参:", v)
		}(v)
	}

	// 写法二：循环体里重新声明一个同名变量，遮蔽外层那个
	for _, v := range list {
		v := v
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println("重声明:", v)
		}()
	}
	wg.Wait()
}
```

之所以管用，还是那句话——闭包捕获的是变量。传参是复制出一个新变量，`v := v` 是显式新建变量，本质一样：**让每次迭代捕获不同的变量**。

### 3. Go 1.22：每次迭代都是新变量

官方口径（Go wiki: LoopvarExperiment）：**用 `:=` 声明的循环变量，每次迭代是不同实例**；range 循环相当于每轮循环体开头都做了 `k := k`、`v := v`。

所以上面那段 goroutine 代码在 1.22+ 直接正确，`&i` 拿到的也是三个不同地址。跟 JS 摆一起看就清楚了：

| 写法 | 闭包看到的值 |
| --- | --- |
| JS `for (var i ...)` | 全是最后一个（`3,3,3`，本机实测） |
| JS `for (let i ...)` | `0,1,2` |
| Go ≤ 1.21 `for i := ...` | 全是最后一个（`3,3,3`，本机实测） |
| Go ≥ 1.22 `for i := ...` | `0,1,2` |

说白了，**Go 1.22 干的事就是让 `for i :=` 对齐 JS 的 `let`**。

但有两个细节必须记住，面试常在这儿挖坑。

**① 生效与否看 go.mod，不看工具链版本。** 官方原文是"only apply when the package being compiled is from a module that contains a `go` line declaring Go 1.22 or later"，目的就是让**升级工具链不偷偷改变程序行为**。所以你用 Go 1.27 编译一个 `go 1.18` 的老模块，还是老语义。想确认哪些循环变了：`go build -gcflags=all=-d=loopvar=2`，会对每个"编译结果变了"的循环打一行 `loop variable i now per-iteration, stack-allocated`（本机实测有输出）。

**② 只有 `:=` 声明的那个变量被新建。** 变量在循环外面声明，还是只有一份：

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var j int
	var wg sync.WaitGroup
	for j = 0; j < 3; j++ { // 注意是 = 不是 :=，j 声明在循环外
		wg.Add(1)
		go func() {
			defer wg.Done()
			fmt.Println(j) // 三个都是 3（本机实测）
		}()
	}
	wg.Wait()
}
```

这条很重要：**1.22 之后不等于"循环里随便写都安全"**。想跨迭代累积（求和、拼字符串）的变量本来就该放外面，那种场景本来就该加锁。

### 4. 同一类坑的三个变体

不止 goroutine，只要"闭包活过了这一轮迭代"就会中招。

**变体一：defer。** defer 是函数返回时才执行，天然活过循环：

```go
package main

import "fmt"

func main() {
	for i := 0; i < 3; i++ {
		defer func() { fmt.Print(i, " ") }()
	}
	fmt.Println()
}
```

`go 1.21` 模块实测 `3 3 3`，`go 1.27` 模块实测 `2 1 0`（defer 后进先出，所以倒序）。

**变体二：`t.Run` + `t.Parallel`。** 官方 wiki 举的例子，也是最难发现的——测试会"假通过"：

```go
package looptest

import "testing"

func TestAllEven(t *testing.T) {
	testCases := []int{1, 2, 4, 6}
	for _, v := range testCases {
		t.Run("sub", func(t *testing.T) {
			t.Parallel()
			if v&1 != 0 {
				t.Fatal("odd v", v)
			}
		})
	}
}
```

`t.Parallel()` 会让闭包挂起、循环继续跑，等四个子测试并行执行时 `v` 已经是最后一个值 6，于是**四个子测试都只验证了 6**。本机实测：`go 1.21` 模块下 `ok`（明明有奇数 1 却通过），`go 1.27` 模块下 `--- FAIL: TestAllEven/sub  odd v 1`（新语义才抓得住）。

**变体三：把闭包攒起来批量调用。** 中间件表、回调注册、插件列表都是这个形状：

```go
package main

import "fmt"

func main() {
	var handlers []func()
	for i := 0; i < 3; i++ {
		handlers = append(handlers, func() { fmt.Println("handler", i) })
	}
	for _, h := range handlers {
		h()
	}
}
```

老语义下三个都是 `handler 3`；新语义下是 `handler 0 / 1 / 2`。

## 落到项目里长什么样

1. **批量任务并发**：`for _, o := range orders { go func(o Order) { ... }(o) }`。老代码里到处是这种写法，看着啰嗦但跨版本都安全，删之前先看 go.mod。
2. **注册路由 / 中间件**：把 `http.HandlerFunc` 攒进 slice 或 map，老模块上必须 `h := h`，否则每个闭包用到的都是循环最后那个值。
3. **表格驱动测试**：`t.Run(tc.name, ...)` 不带 `t.Parallel()` 就没事（闭包在当轮内执行完）；一旦加了 `t.Parallel()`，1.22 之前必须 `tc := tc`。
4. **闭包当"配置快照"**：`fn := func() { use(cfg) }` 之后又改了 `cfg`，`fn` 看到的是**新值**。因为捕获的是变量，想要快照就自己 copy 一份进局部变量。
5. **和前端对照记**：JS 里 `var` 的坑（`setTimeout` 打出三个 3）和 Go 1.21 一模一样，`let` 的解法也和 Go 1.22 的判断标准一样——**看这个变量是不是每轮新建**。这条类比说出来，面试官能听出你是真理解了，不是背的结论。

## 常见误解（FAQ）

**❌ 误区1："闭包捕获的是当时的值，所以循环里是安全的"**

反了，捕获的是**变量**。`x := 0; inc := func() { x++ }` 之后 `inc()` 能让外面的 `x` 变成 1，说明它拿的不是副本。正因为所有闭包共享同一个循环变量，才会全打印最后一个值。

**❌ 误区2："我本地是 Go 1.27，所以不会遇到这个问题"**

循环变量语义由**模块 go.mod 里那行 `go` 版本**决定，不是工具链版本。`go 1.21` 的模块用 Go 1.27 编译，还是 `3 3 3`。官方特意这么做：升级工具链不改变既有程序行为。查的办法是 `go build -gcflags=all=-d=loopvar=2`。

**❌ 误区3："1.22 之后循环里就不用管了"**

只有用 `:=` 声明的循环变量是每轮新建。变量声明在循环外（`for j = 0`）还是只有一份，实测三个 goroutine 全打印 3。另外"想跨轮累积"的变量本来就该共享，那就得加锁或换 channel。

**❌ 误区4："1.22 之后 `v := v` 就是废代码，看见就删"**

可以删，但要分情况：变量是 `:=` 声明的、模块已经是 1.22+，删掉没问题；变量在循环外声明、或者模块还是老版本，删了就踩坑。删之前先看 go.mod，别一把梭。

**❌ 误区5："每轮新建变量会让循环变慢、分配变多"**

官方 FAQ 的说法是：只有**取过地址（`&i`）或被闭包捕获**的循环，编译结果才会变；即便如此，编译器也可能仍然把它放在栈上。绝大多数循环完全不受影响，公开 benchmark 也没有统计上的性能差异。

## 一句话总结

闭包抓的是变量不是值；1.21 及以前一个 `for` 只有一个循环变量，所以闭包全看到最后一个值；1.22 起 `:=` 声明的循环变量每轮新建——但生不生效，看你 go.mod 里那行 `go`。
