## 一句话概括

map 就是**哈希表**：给一个 key，O(1) 拿到 value。Go 里的写法是 `map[K]V`，K 必须"可比较"。

面试官问 map，八成是这四个问题：

- 遍历顺序为什么是随机的？能保证吗？
- nil map 能不能读、能不能写？
- 两个 goroutine 同时写会怎样？怎么解决？
- map 是引用类型吗？传参会不会复制？

这四个问题的答案其实都指向同一件事：**map 变量本身只是个 8 字节的指针，真正的数据在堆上的哈希表里；而这张表没有任何锁。**

## 核心知识点

### 1. 三种建法 + nil map 的规矩

```go
package main

import "fmt"

func main() {
	var a map[string]int           // nil map：只声明没分配
	b := map[string]int{}          // 空 map：分配了，可以写
	c := make(map[string]int, 100) // 带容量预估，避免频繁扩容

	fmt.Println(len(a), len(b), len(c)) // 0 0 0
	fmt.Println(a["nope"])              // 0  ← 读 nil map 不报错，给零值

	b["k"] = 1
	fmt.Println(b["k"]) // 1

	// a["k"] = 1 // panic: assignment to entry in nil map
}
```

三条规矩，背下来：

1. **`var m map[K]V` 得到的是 nil map**，读它返回零值、`len` 是 0、`range` 一圈都不转，全都合法。
2. **往 nil map 写就 panic**，报错原文 `assignment to entry in nil map`。编译器不拦你，因为编译期它不知道这个 map 后来会不会被赋值。
3. **`make(map[K]V, n)` 的 n 只是"预估容量"**，`len` 还是 0，`cap(m)` 直接编译不过——map 没有 cap 这个概念。

第 3 点顺带解释一个常被拿来炫技的细节：`unsafe.Sizeof(m)` 是 **8 字节**，就是一个指针。所以"map 是引用类型"这种说法在 Go 里不严谨——Go 根本没有"引用类型"这个分类，只有**值语义**和**引用语义**。map 是值类型（可以赋值、可以传参），但它的值是个句柄，赋值只复制这 8 字节，两张"表"指向同一份数据。

```go
package main

import "fmt"

func main() {
	base := map[string]int{"a": 1}
	alias := base      // 只复制了 8 字节的指针
	alias["b"] = 2
	fmt.Println(len(base)) // 2  ← 改副本等于改原 map

	modify(base)           // 传参同理
	fmt.Println(base["c"]) // 3
}

func modify(m map[string]int) { m["c"] = 3 }
```

这也是为什么**用 map 当"输出参数"是可行的**：函数里往 map 塞值，调用方看得见。跟切片正好相反——切片改长度外面看不见（切片头被复制了），map 没有长度以外的描述符，所以随便加。

### 2. 取值、删除与 key 的合法性

取值永远只有两种写法，别的都是错的：

```go
package main

import "fmt"

type User struct {
	Name string
	Age  int
}

func main() {
	m := map[string]int{"apple": 3}

	// ❌ 用零值判断 key 在不在：key 存在但值就是 0 时会误判
	if m["banana"] == 0 {
		fmt.Println("❌ 这样判断，banana 存了个 0 也会被当成不存在")
	}

	// ✅ comma-ok：第二个返回值才是"存在性"
	if v, ok := m["banana"]; !ok {
		fmt.Println("✅ banana 不存在，v 是零值", v)
	}

	// delete 删不存在的 key 不报错，静默返回
	delete(m, "apple")
	delete(m, "从来没存在过")
	fmt.Println("删完 len:", len(m)) // 0

	// 想改 struct 里的字段，得取出来改完再放回去
	us := map[string]User{"u1": {"Tom", 18}}
	u := us["u1"]
	u.Age = 20
	us["u1"] = u
	fmt.Println(us["u1"]) // {Tom 20}

	// us["u1"].Age = 21 // 编译错：cannot assign to struct field us["u1"].Age in map
	// p := &us["u1"]    // 编译错：cannot take address of us["u1"] (... map index expression ...)
}
```

`us["u1"].Age = 21` 编译不过，原因是 **map 的 value 不是可寻址的**：map 扩容时元素会被搬到新桶，地址会变，语言层直接禁止你拿地址。所以凡是 `map[string]struct{...}` 又想改字段的，标准做法就是"取出来 → 改 → 放回"，或者干脆存指针 `map[string]*User`。

顺便记一下"谁能当 key"这条线。**可比较的类型才能当 key**：布尔、数字、字符串、指针、channel、interface，以及"所有字段都可比较"的数组和结构体。切片、map、函数不行：

```go
package main

import "fmt"

type Point struct {
	X, Y int
}

func main() {
	key := Point{X: 1, Y: 2}
	pm := map[Point]string{key: "原点旁边"}
	fmt.Println(pm[Point{X: 1, Y: 2}]) // 原点旁边  ← 字段相同就是同一个 key

	// map[[]int]string{} // 编译错：invalid map key type []int
	// a == b             // 编译错：a == b (map can only be compared to nil)
	fmt.Println(pm == nil) // false，map 只能和 nil 比
}
```

最后一行是高频追问：**map 之间不能比较**，只能跟 nil 比；要比内容就用 `maps.Equal`（Go 1.21+，要求 value 也可比较）或者 `reflect.DeepEqual`（更慢，但对任意 value 都能用）。

### 3. 遍历顺序随机，是官方故意的

```go
package main

import (
	"fmt"
	"sort"
)

func main() {
	m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4}

	// 连跑 10 次，看有几种不同的顺序
	seen := map[string]bool{}
	for i := 0; i < 10; i++ {
		keys := make([]string, 0, len(m))
		for k := range m {
			keys = append(keys, k)
		}
		seen[fmt.Sprint(keys)] = true
	}
	fmt.Println("10 次遍历出现", len(seen), "种顺序") // 实测 4 种

	// 要有序：先把 key 摘出来排序，再按序取值
	keys := make([]string, 0, len(m))
	for k := range m {
		keys = append(keys, k)
	}
	sort.Strings(keys)
	for _, k := range keys {
		fmt.Printf("%s=%d ", k, m[k])
	}
	fmt.Println()
}
```

为什么随机？官方给的理由很实在：**Go 1 的 release notes 就把遍历顺序定义成"不可预测，即使同一个 map 跑两遍同样的循环也一样"**——因为早期实现看起来是稳定的，结果一堆人（包括测试代码）不知不觉依赖了它，换平台或运行时一改就炸。与其让大家依赖，不如一开始就让你依赖不了。

两个必须知道的细节：

- **每次 `range` 的起始位置都不同，但同一次 `range` 内部是按桶顺序走的**。所以"看起来很有规律"是错觉，实测 10 次能出现 4 种不同顺序。
- **`range` 期间新增的 key 可能被遍历到，也可能不被遍历到**，官方明确说这是未定义行为，别写这种代码。`range` 期间 `delete` 是安全的，删掉的 key 保证不会再出现。

要稳定顺序就只有一个办法：**把 key 摘出来排好序再按序读**。JSON 序列化、日志输出、需要 diff 的场景，全都要这么干。

### 4. 并发写：直接 fatal，recover 救不回来

这是 map 最出名的一条。看最小复现：

```go
package main

import (
	"fmt"
	"sync"
)

// racy 定义在这里但没被调用——一旦调用，进程当场退出
func racy() {
	m := map[int]int{}
	var wg sync.WaitGroup
	for i := 0; i < 2; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			for j := 0; j < 100000; j++ {
				m[j] = id
			}
		}(i)
	}
	wg.Wait()
	fmt.Println(len(m))
}

func main() {
	// racy()
	fmt.Println("racy() 一放开就崩，报错是 fatal error: concurrent map writes")
}
```

实测输出：

```
fatal error: concurrent map writes

goroutine 19 [running]:
internal/runtime/maps.fatal(...)
main.main.func1(0x0)
	/tmp/gocheck/errconcurrent/main.go:16 +0x60
```

注意两个词：**`fatal error` 不是 `panic`**。fatal 是运行时直接 `exit(2)`，**`defer` 不执行、`recover` 接不住、日志都来不及刷**。Go 宁可让程序立刻死掉，也不允许哈希表静默损坏——静默损坏的后果（数据错乱、越权读）比崩一次严重得多。

顺带说，**只读并发是安全的**，只有"有人写"才会炸。所以修法有两种：

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu sync.RWMutex
	m  map[string]int
}

func NewCounter() *Counter { return &Counter{m: make(map[string]int)} }

func (c *Counter) Inc(k string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.m[k]++
}

func (c *Counter) Get(k string) int {
	c.mu.RLock()
	defer c.mu.RUnlock()
	return c.m[k]
}

func main() {
	c := NewCounter()
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 100; j++ {
				c.Inc("hit")
			}
		}()
	}
	wg.Wait()
	fmt.Println(c.Get("hit")) // 10000
}
```

| 方案 | 适合场景 | 代价 |
| --- | --- | --- |
| `sync.RWMutex` 包一层 | 读写都多、逻辑复杂（要"读-改-写"） | 每次操作加锁，读多时 RLock 能并发 |
| `sync.Map` | 读多写少、key 基本不重叠（缓存、注册表） | 写性能差，API 是 `Load/Store/Delete`，没有 `len` |
| 分片锁（shard） | 极高并发计数 | 自己实现，桶数按 CPU 核数取 |

一句面试话术：**默认用 `RWMutex`，`sync.Map` 只在"key 一次写入多次读取、并且各 goroutine 操作不同 key"时才划算。** 大部分项目里直接上 `sync.Map` 反而更慢。

## 落到项目里长什么样

1. **`make` 时给个容量预估**。`make(map[string]*User, len(list))` 能省掉十几次 rehash，批量导入 CSV、构建索引时尤其明显。
2. **别拿 map 当有序容器**。要按插入顺序出结果（比如菜单、步骤条），就用 `[]Item` + `map[string]int` 存下标，或者切片排完序再遍历。
3. **判重先看零值陷阱**。统计接口返回 `map[string]int` 时，`if m[k] == 0` 分不清"没有"和"值是 0"，永远用 `v, ok := m[k]`。
4. **删除不缩容**。一个 100 万条的 map 全 `delete` 完，内存不会还回去——桶还在。要释放就整个换掉：`m = make(map[K]V)`。
5. **`sync.Map` 别当万能钥匙**。它没有 `len()`，要计数还得自己维护；遍历用 `Range(f func(k, v any) bool)`，回调里 return false 就停。

跟前端对照一下：JS 的 `Map` 是**保证插入顺序**的，`Object.keys` 对字符串 key 也是插入顺序（数字 key 会排前面）。所以从 JS 过来最容易犯的错，就是把"遍历顺序"当成理所当然。Go 这边一上来就把这条路堵死了。

## 常见误解（FAQ）

**❌ 误区1："nil map 不能读，读了会 panic"**

能读。读 nil map 返回 value 类型的零值，`len` 是 0，`range` 一圈不转，全都不报错。只有**写**才 panic，报 `assignment to entry in nil map`。所以 `if m["k"] > 0` 这种写法在 nil map 上是安全的——不安全的是你以为它一定有值。

**❌ 误区2："map 遍历顺序随机，所以每次跑肯定都不一样"**

"随机"指的是**不保证**，不是"保证不同"。实测一个 4 元素的 map 连跑 10 次，只出现了 4 种顺序，还重复了好几轮。反过来说，某两次跑出一样的顺序也完全正常，别拿"我跑了很多次都一样"当证据。

**❌ 误区3："并发写 map 会 panic，用 recover 兜住就行"**

兜不住。它是 `fatal error` 不是 `panic`，运行时直接 `exit(2)`，`defer` 不跑、`recover` 接不到、缓冲日志都可能丢。`go run -race` 能在开发期提前抓到这类竞争，但生产上只能靠加锁。

**❌ 误区4："map 的 value 是结构体，直接 `m[k].Field = x` 就能改"**

编译不过：`cannot assign to struct field m[k].Field in map`。因为 map 的 value 不可寻址（扩容会搬家）。要么取出→改→放回，要么 value 存 `*T`。

**❌ 误区5："delete 之后内存就释放了，map 会变小"**

`delete` 只把桶里的槽位标记为空，桶数组一个都不还。所以"用一个 map 当缓存、定期 delete 过期项"并不能控制内存，该整个换新 map 就换。

**❌ 误区6："map 是引用类型，所以函数里重新 make 一个外面也变"**

不会。函数里 `m = make(...)` 只改了那个 8 字节的副本，调用方手里的还是老指针。想换掉整张表就传 `*map[K]V`，或者返回新 map。

## 一句话总结

**map 变量就是一个 8 字节的指针，指向一张没加锁的哈希表：nil map 能读不能写、遍历顺序永远不保证、并发写直接 fatal 且 recover 救不回来——记住这三条，map 题就问不倒了。**
