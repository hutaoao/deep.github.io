## 一句话概括

JWT 在 Go 里落地就三件事：**登录时签一个字符串**、**每个请求校验这个字符串**、**快过期了用 refresh token 换一个新的**。

面试官真正想听的，不是"JWT 是 header.payload.signature 三段"，而是——

- 你签名用什么算法，`Parse` 的时候有没有限制算法？
- 校验失败的分支，你怎么区分"过期"和"签名不对"？
- token 签发出去之后，用户改了密码，你怎么让它失效？

这三个问题背后全是坑，下面一个个过。**先说最重要的那条**：`golang-jwt/jwt/v5` 的 `Parse` 默认**不限制签名算法**，也**不要求 token 必须带 `exp`**——这两件事都得自己加参数，漏一个就是安全洞。

## 核心知识点

### 1. 签发：一个 claims 结构体，两行签出来

结论先摆着：**业务字段放自己的结构体，标准字段嵌 `jwt.RegisteredClaims`，然后 `NewWithClaims` + `SignedString`**。

```go
package main

import (
	"encoding/base64"
	"fmt"
	"strings"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

var secret = []byte("dev-secret-please-change")

type Claims struct {
	UserID uint   `json:"uid"`
	Type   string `json:"typ"` // access / refresh
	jwt.RegisteredClaims
}

func issue(uid uint, typ string, d time.Duration) (string, error) {
	c := Claims{
		UserID: uid,
		Type:   typ,
		RegisteredClaims: jwt.RegisteredClaims{
			ExpiresAt: jwt.NewNumericDate(time.Now().Add(d)),
			IssuedAt:  jwt.NewNumericDate(time.Now()),
		},
	}
	return jwt.NewWithClaims(jwt.SigningMethodHS256, c).SignedString(secret)
}

func main() {
	s, err := issue(42, "access", time.Hour)

	parts := strings.Split(s, ".")
	fmt.Printf("err=%v 段数=%d header=%d 字符 payload=%d 字符\n",
		err, len(parts), len(parts[0]), len(parts[1]))

	p, _ := base64.RawURLEncoding.DecodeString(parts[1])
	fmt.Println("payload 原文:", string(p))
}
```

输出：

```
err=<nil> 段数=3 header=36 字符 payload=79 字符
payload 原文: {"uid":42,"typ":"access","exp":1794363603,"iat":1794360003}
```

`exp` / `iat` 那两个数字是秒级时间戳，每次跑都不一样，结构就这么简单。

第一件事就值得说：**payload 只是 base64url，不是加密**。任何人拿到 token 都能解出这串 JSON。所以面试被问"JWT 安全吗"，标准答法是"**能防篡改，不能防偷看**"——里面别放手机号、身份证、余额，只放 `uid`、`role` 这种标识，要详情再查库。

`jwt.RegisteredClaims` 是库给的标准字段集合（`exp` 过期、`iat` 签发、`nbf` 生效、`iss` 签发者、`sub` 主体、`aud` 受众）。**不嵌它，`exp` 就不会被自动校验**，因为它提供的是 `Claims` 接口里的 `GetExpirationTime()`——你不嵌，这个能力就没了。

### 2. 校验：光 `Parse` 不够，必须锁算法

这是全篇最容易挂的地方。先看一个"看着对、其实有洞"的 Keyfunc——把密钥无脑返回给库，`func(t *jwt.Token) (any, error) { return secret, nil }`，什么算法都认。

我实测过：用 `HS512` 签出来的 token，交给这种 Keyfunc 去解析，**校验通过，err 是 nil**。因为你没拦，库就按 token 自己头上写的 `alg` 去验——token 说 HS512，它就用 HS512 验，当然对。

正确写法是给一个算法白名单。下面这个程序把"不锁"和"锁"放一起对比，顺带验一下 `exp` 那条：

```go
package main

import (
	"fmt"
	"time"

	"github.com/golang-jwt/jwt/v5"
)

var secret = []byte("k")

type Claims struct {
	UserID uint `json:"uid"`
	jwt.RegisteredClaims
}

func main() {
	key := func(t *jwt.Token) (any, error) { return secret, nil }

	// 攻击者把算法换成 HS512，密钥不变
	hs512, _ := jwt.NewWithClaims(jwt.SigningMethodHS512, Claims{
		UserID: 1,
		RegisteredClaims: jwt.RegisteredClaims{
			ExpiresAt: jwt.NewNumericDate(time.Now().Add(time.Hour)),
		},
	}).SignedString(secret)

	_, errLoose := jwt.ParseWithClaims(hs512, &Claims{}, key) // ❌ 不锁算法，谁来都认
	fmt.Printf("不限定算法       err=%v\n", errLoose)

	_, errStrict := jwt.ParseWithClaims(hs512, &Claims{}, key,
		jwt.WithValidMethods([]string{"HS256"})) // ✅ 只认 HS256
	fmt.Printf("WithValidMethods err=%v\n", errStrict)

	// 完全不写 exp 的 token
	noExp, _ := jwt.NewWithClaims(jwt.SigningMethodHS256, Claims{UserID: 2}).SignedString(secret)
	_, errNoExp := jwt.Parse(noExp, key)
	fmt.Printf("没有 exp          err=%v\n", errNoExp)

	_, errReq := jwt.Parse(noExp, key, jwt.WithExpirationRequired())
	fmt.Printf("强制要求 exp      err=%v\n", errReq)
}
```

四行输出，四个结论：

```
不限定算法       err=<nil>
WithValidMethods err=token signature is invalid: signing method HS512 is invalid
没有 exp          err=<nil>
强制要求 exp      err=token has invalid claims: token is missing required claim: exp claim is required
```

**第二行说明**：加白名单后同一个 token 立刻被拒，报错里直接点名"signing method HS512 is invalid"——看到这个错误基本可以判定有人在做算法替换。

**第三、四行是最阴的坑**：不写 `exp` 的 token，`Parse` 返回 `err=<nil>`，也就是**永久有效**。所以校验侧一定要加 `jwt.WithExpirationRequired()`。

顺带说 `alg: none` 那个经典攻击（算法改 none、签名段留空）。**v5 默认帮你拦了**，实测报错：

```
token signature is invalid: token is unverifiable: 'none' signature type is not allowed
```

不用自己写判断，但要知道有这回事——别的语言、更老的库不一定拦。

第三个坑藏在签发侧：`exp` 得是秒级时间戳。手滑写成 `time.Now().Add(time.Hour)` 而不是 `.Unix()`，JSON 会把它序列化成 RFC3339 字符串，解析时报：

```
token has invalid claims: invalid type for claim: exp is invalid
```

好消息是 v5 直接报错，不会静默放过；坏消息是这条错误信息不会告诉你"你少了个 .Unix()"。

校验失败得能**分清类型**，因为前端处理方式完全不同。v5 的错误外层包了 `token has invalid claims:`，所以只能用 `errors.Is`，不能用 `==`：

| 情况 | `err.Error()` 实测原文 | 前端该怎么处理 |
| --- | --- | --- |
| 已过期 | `token has invalid claims: token is expired` | 401 + 换票重试 |
| 签名错误 | `token signature is invalid: signature is invalid` | 401 + 跳登录 |
| 段数不对/乱写 | `token is malformed: token contains an invalid number of segments` | 401 + 跳登录 |
| 算法不在白名单 | `token signature is invalid: signing method HS512 is invalid` | 401 + 跳登录（多半是攻击） |
| 少 `exp` | `token has invalid claims: token is missing required claim: exp claim is required` | 401 + 跳登录 |
| 已过期但在 leeway 内 | `err=<nil>` | 正常放行 |

所以后端**别笼统返回 `{"error":"unauthorized"}`**，"过期"要单独给个标记，前端才知道该不该静默刷新。

还有两个细节值得记牢：

- **过期时 claims 其实是填好的**。我实测过期 token 解析失败，但取出来的 `uid` 仍然是 42——签名先验过了，只是时间检查没过。所以只要 `err != nil`，payload 就当不可信，别拿它做任何判断。
- **服务器有时钟差**。差几秒就会把刚签的 token 判过期。`jwt.WithLeeway(3*time.Second)` 能容忍几秒，我实测过期 2 秒的 token 加上 5 秒 leeway 后 `err=<nil>`。

### 3. 中间件：从 `Bearer` 到 `c.Set("uid")`

Go 的中间件本质就是"接一个 handler，返回一个 handler"。Gin 里签名是 `func(*gin.Context)`，放行靠 `c.Next()`，掐断靠 `c.Abort()`。

下面这段是完整可跑的——签发、校验、刷新、拦截全串起来了：

```go
package main

import (
	"errors"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"time"

	"github.com/gin-gonic/gin"
	"github.com/golang-jwt/jwt/v5"
)

var secret = []byte("dev-secret-please-change")

type Claims struct {
	UserID uint   `json:"uid"`
	Type   string `json:"typ"` // access / refresh
	jwt.RegisteredClaims
}

func issue(uid uint, typ string, d time.Duration) (string, error) {
	c := Claims{UserID: uid, Type: typ, RegisteredClaims: jwt.RegisteredClaims{
		ExpiresAt: jwt.NewNumericDate(time.Now().Add(d)),
		IssuedAt:  jwt.NewNumericDate(time.Now()),
	}}
	return jwt.NewWithClaims(jwt.SigningMethodHS256, c).SignedString(secret)
}

func parseToken(raw string) (*Claims, error) {
	var cl Claims
	_, err := jwt.ParseWithClaims(raw, &cl, func(t *jwt.Token) (any, error) {
		return secret, nil
	}, jwt.WithValidMethods([]string{"HS256"}), jwt.WithExpirationRequired())
	return &cl, err
}

func authRequired() gin.HandlerFunc {
	return func(c *gin.Context) {
		raw, ok := strings.CutPrefix(c.GetHeader("Authorization"), "Bearer ")
		if !ok || raw == "" {
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "未登录"})
			return
		}
		cl, err := parseToken(raw)
		if err != nil {
			if errors.Is(err, jwt.ErrTokenExpired) {
				c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "token 已过期"})
				return
			}
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "token 无效"})
			return
		}
		if cl.Type != "access" { // ✅ 必须拦：refresh token 不许进业务接口
			c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "token 类型不对"})
			return
		}
		c.Set("uid", cl.UserID) // ✅ 校验全过了，这个 uid 才能信
		c.Next()
	}
}

func main() {
	gin.SetMode(gin.ReleaseMode)
	r := gin.New()

	r.POST("/refresh", func(c *gin.Context) {
		raw, _ := strings.CutPrefix(c.GetHeader("Authorization"), "Bearer ")
		cl, err := parseToken(raw)
		if err != nil || cl.Type != "refresh" {
			c.JSON(http.StatusUnauthorized, gin.H{"error": "refresh 无效"})
			return
		}
		at, _ := issue(cl.UserID, "access", 15*time.Minute)
		c.JSON(http.StatusOK, gin.H{"access": at})
	})

	api := r.Group("/api", authRequired())
	api.GET("/me", func(c *gin.Context) {
		c.JSON(http.StatusOK, gin.H{"uid": c.GetUint("uid")})
	})

	// 生产环境换成 r.Run(":8080")，这里用 httptest 直接打
	at, _ := issue(42, "access", time.Minute)
	rt, _ := issue(42, "refresh", 7*24*time.Hour)

	call := func(method, path, token string) (int, string) {
		req := httptest.NewRequest(method, path, nil)
		if token != "" {
			req.Header.Set("Authorization", "Bearer "+token)
		}
		w := httptest.NewRecorder()
		r.ServeHTTP(w, req)
		return w.Code, w.Body.String()
	}

	for _, cs := range []struct{ name, method, path, token string }{
		{"无 token", "GET", "/api/me", ""},
		{"access 访问", "GET", "/api/me", at},
		{"refresh 访问", "GET", "/api/me", rt},
		{"refresh 换票", "POST", "/refresh", rt},
		{"access 换票", "POST", "/refresh", at},
	} {
		code, body := call(cs.method, cs.path, cs.token)
		if len(body) > 40 {
			body = body[:40] + "..."
		}
		fmt.Printf("%-12s → %d %s\n", cs.name, code, body)
	}
}
```

跑出来：

```
无 token      → 401 {"error":"未登录"}
access 访问    → 200 {"uid":42}
refresh 访问   → 401 {"error":"token 类型不对"}
refresh 换票   → 200 {"access":"eyJhbGciOiJIUzI1NiIsInR5cCI6I...
access 换票    → 401 {"error":"refresh 无效"}
```

这段里有两个容易漏的点：

**`Abort` 后面必须 `return`**。`c.Abort()` 只是把后续 handler 从链上摘掉，**当前函数还会继续往下执行**。不 return 就会接着跑到 `c.Set` 甚至 `c.Next()`，越权就出来了。

**必须校验 `typ`**。access 和 refresh 用同一把密钥、同一种算法，所以 refresh token 拿去访问业务接口，签名校验照样通过（我单独实测过，`err=<nil>`）。不判 `cl.Type` 的话，一个 7 天有效期的 refresh token 就等于 7 天的正常访问权限，短过期设计彻底失效。想更彻底，就给两个 token 用**两把不同的密钥**。

### 4. 刷新与吊销：JWT 最贵的那笔账

双 token 的分工很好记：

| | access token | refresh token |
| --- | --- | --- |
| 有效期 | 15 分钟 ~ 2 小时 | 7 天 ~ 30 天 |
| 存哪 | 内存变量 / 短 Cookie | HttpOnly Cookie（前端 JS 读不到） |
| 用途 | 访问业务接口 | 只能打 `/refresh` 换票 |
| 被偷了 | 损失小（很快过期） | 损失大（能一直换） |

`/refresh` 和业务接口的校验逻辑一样，只是反过来**只认 `typ == "refresh"`**。上面那段程序的第三、五行就是这两个方向的实测结果。

然后就是面试爱追问的那个：**用户改密码、被踢下线，旧 token 怎么立刻失效？**

老实答：**没法规矩地失效**。JWT 无状态，签出去就在客户端手里，服务端没有名单。三种补救，按推荐度排：

1. **user 表存 `token_version`**：签发时写进 claims，校验时比一下缓存里的值。改密码就 `+1`，该用户所有 token 立刻作废。一个用户一个数字，比黑名单省得多，我最推荐这个。
2. **Redis 黑名单**：登出/改密时把 `jti` 塞进 Redis，TTL 设成 token 剩余有效期。代价是每个请求多查一次 Redis，等于把无状态又变回有状态。
3. **把 access 压到 15 分钟**：不追求立即失效，接受最长 15 分钟的窗口。多数业务的容忍度其实够，最省事。

最后一条狠的：**密钥不能为空**。我实测 `[]byte("")` 当密钥，签发成功、校验也成功——库不会拦你。所以启动时要断言 `len(secret) >= 32`，否则配置漏一项就是"任何人都能伪造 token"。HS256 的密钥按 RFC 7518 至少 256 bit，也就是 32 字节。

## 落到项目里长什么样

1. **目录先分开**：`internal/auth/jwt.go` 只放 `issue` / `parse` 纯函数（不依赖 gin），`internal/middleware/auth.go` 取 header 调 parse，`internal/handler/user.go` 放登录和刷新，密钥和超时从 `internal/config` 读环境变量。
2. **`parse` 全项目只留一份**：我见过三个 handler 各写一遍 `jwt.Parse` 的代码，某次改算法只改了两处，剩下那处就成了后门。校验函数必须是唯一入口。
3. **密钥启动时断言长度**：`if len(secret) < 32 { panic("JWT_SECRET 太短") }`。配置漏一项不会报错，只会变成"任何人都能伪造 token"，这种事必须在启动时就炸。
4. **错误码分两类**：`token 已过期` 用一个独立 code（前端据此换票），`token 无效` 用另一个（前端据此跳登录）。混成一个 401，前端就没法自动刷新了。
5. **和 Node 对照**：`jsonwebtoken` 的 `jwt.verify(token, secret)` 默认也不锁算法（老版本还默认接受 none），必须传 `{ algorithms: ['HS256'] }`——**同一个坑，换个语言还在**。中间件差别只在写法：Express 是 `app.use((req, res, next) => ...)`，Gin 是 `func(c *gin.Context)`，都是"放行或掐断"两件事，只是 Gin 多了个"`Abort` 之后还要 `return`"的尾巴。
6. **前端配套**：401 别直接跳登录页。区分"已过期"→ 调 `/refresh` 换票并重放原请求（要加"正在刷新"的锁，否则十个并发请求会打十次刷新），刷新失败才跳登录。这套 axios 拦截器和前面《前端鉴权体系》那篇是接得上的。

## 常见误解（FAQ）

**❌ 误区1："JWT 是把用户信息加密了传给前端。"**

没有加密，只有签名。payload 段 base64 一解就是明文 JSON。签名保证的是"改一个字就验不过"，不是"看不见"。手机号、身份证、订单金额这些别往 claims 里塞，放个 `uid` 就够。

**❌ 误区2："`Parse` 返回 err 为 nil，就说明 token 有效。"**

在限制算法和强制 `exp` 之前，这话不成立：HS512 签的能过，没有 `exp` 的永久有效。老老实实写 `jwt.WithValidMethods([]string{"HS256"})` + `jwt.WithExpirationRequired()`，再判 `err != nil`。

反过来的坑也有人踩：只判 `token != nil` 就放行。我实测签名错误的 token **返回的 `*jwt.Token` 不是 nil**，只是 `Valid == false`。判据是 `err != nil`，不是指针非空。

**❌ 误区3："过期了就让用户重新登录。"**

过期是最常见的正常状态，不是异常。手机上 token 十几分钟就过期，用户正填着表单被踢出去，这体验没法看。标准做法是静默刷新：前端拦 401，用 refresh token 换新的 access 再重放请求。只有 refresh 也过期，才让用户重新登录。

**❌ 误区4："用户改了密码，旧 token 自然就失效了。"**

不会。JWT 里没存密码，服务端也不维护会话。改完密码，别人偷到的 token 照样用到过期为止。要真失效就得上 `token_version` 或 Redis 黑名单——这也是"JWT 相比 Session 的缺点是什么"的标准答案：**不可撤销**。

**❌ 误区5："refresh token 也是 token，访问业务接口当然能过。"**

签名确实能过（同一个密钥、同一种算法），所以业务中间件不检查 `typ`，就等于把 7 天的访问权直接发出去了。这是设计缺陷，不是库的问题。

## 一句话总结

JWT 的坑不在"怎么签"，而在"签完之后忘了锁什么"——锁算法、锁必带 `exp`、锁 token 类型、锁密钥长度，四把锁挂齐，再谈刷新和吊销。
