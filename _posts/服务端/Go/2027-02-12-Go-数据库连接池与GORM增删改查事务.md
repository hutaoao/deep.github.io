## 一句话概括

Go 连数据库只有两层：**标准库 `database/sql` 管连接池和 SQL 执行，GORM 在它上面加了一层结构体映射**。

面试问这块，十有八九是这三个问题：

- `sql.Open` 之后为什么还要 `Ping`？`*sql.DB` 到底是连接还是池？
- 连接池参数怎么配？配错了线上会出什么事？
- GORM 的 `Updates` 为什么改不动 0 和空字符串？`Delete` 之后数据怎么还在表里？

前两个是标准库的行为，第三个是 GORM 的默认约定。**核心结论先记住**：`*sql.DB` 是**池**，每次查询从池里借一条连接、用完还回去；连接是有限资源，借了不还（事务没提交、`rows` 没关），整个服务就会卡死在等连接上。

## 核心知识点

### 1. `sql.DB` 是池，不是一条连接

官方文档的原话：`Open` **可能只校验参数而不建立连接**，要确认 DSN 对不对，得调 `DB.Ping`。而且 `*sql.DB` 并发安全、自带空闲连接池，**一个进程开一个就够，几乎不需要 Close**。

四个池参数，默认值全都很保守：

| 方法 | 默认值 | 线上怎么设 |
| --- | --- | --- |
| `SetMaxOpenConns(n)` | `0`，**不限** | 必须设。按 MySQL `max_connections` 除以实例数留余量 |
| `SetMaxIdleConns(n)` | `2` | 官方文档写"目前是 2"；建议跟 MaxOpen 设一样，否则连接忽开忽关 |
| `SetConnMaxLifetime(d)` | `0`，永不过期 | 驱动作者明确建议**必须设**，且小于 5 分钟（中间件常 5 分钟掐空闲连接） |
| `SetConnMaxIdleTime(d)` | `0`，永不回收 | Go 1.15+，想让空闲连接快点退就设 |

`SetMaxIdleConns` 默认只有 2 这点很坑：并发一上来，连接用完就被关掉，下一个请求又要重新握手。QPS 高的服务只设了 `MaxOpenConns` 没设 `MaxIdleConns`，会看到大量建连开销。

"连接被占满"到底长什么样？把 `MaxOpenConns` 设成 1，开一个不提交的事务，再从池外查一次：

```go
package main

import (
	"context"
	"database/sql"
	"fmt"
	"time"

	_ "github.com/glebarez/sqlite" // 生产环境换成 _ "github.com/go-sql-driver/mysql"
)

func main() {
	db, err := sql.Open("sqlite", "test.db")
	if err != nil {
		panic(err)
	}
	defer db.Close()

	db.SetMaxOpenConns(1)
	db.SetMaxIdleConns(1)
	db.SetConnMaxLifetime(3 * time.Minute)

	_, _ = db.Exec(`CREATE TABLE IF NOT EXISTS t (id INTEGER PRIMARY KEY, name TEXT)`)
	_, _ = db.Exec(`INSERT INTO t (name) VALUES ('a')`)

	// 一个没提交的事务把唯一那条连接占住了
	tx, _ := db.Begin()
	var n int
	_ = tx.QueryRow(`SELECT COUNT(*) FROM t`).Scan(&n)
	st := db.Stats()
	fmt.Printf("[1] 事务内查到 %d 条，此刻 Open=%d InUse=%d Idle=%d\n", n, st.OpenConnections, st.InUse, st.Idle)

	ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
	defer cancel()
	err2 := db.QueryRowContext(ctx, `SELECT COUNT(*) FROM t`).Scan(&n)
	fmt.Printf("[2] 池里没连接可用，再查 err=%v\n", err2)

	_ = tx.Rollback()
	err3 := db.QueryRow(`SELECT COUNT(*) FROM t`).Scan(&n)
	fmt.Printf("[3] 回滚归还连接后 err=%v n=%d\n", err3, n)

	// rows 不 Close，连接一直不还
	rows, _ := db.Query(`SELECT id FROM t`)
	_ = rows.Next()
	fmt.Printf("[4] rows 未 Close：InUse=%d Idle=%d\n", db.Stats().InUse, db.Stats().Idle)
	rows.Close()
	fmt.Printf("[5] rows 已 Close：InUse=%d Idle=%d\n", db.Stats().InUse, db.Stats().Idle)

	var name string
	err6 := db.QueryRow(`SELECT name FROM t WHERE id = 999`).Scan(&name)
	fmt.Printf("[6] 查不存在的行 err=%v\n", err6)
}
```

输出（示例用纯 Go 的 sqlite 驱动，换 MySQL 只改两行：driver 名和 DSN）：

```
[1] 事务内查到 1 条，此刻 Open=1 InUse=1 Idle=0
[2] 池里没连接可用，再查 err=context deadline exceeded
[3] 回滚归还连接后 err=<nil> n=1
[4] rows 未 Close：InUse=1 Idle=0
[5] rows 已 Close：InUse=0 Idle=1
[6] 查不存在的行 err=sql: no rows in result set
```

这六行里藏着三个线上事故模型：

- **[2]** 连接被占满时请求不是"报错"，是**卡住等到超时**。没有 `context` 超时就是永久 hang，然后整个服务跟着崩。所以所有查询都该走 `QueryContext`。
- **[4]** **`rows` 不 Close，连接不还**。写了 `rows.Next()` 循环但中途 `return`、忘了 `defer rows.Close()`，跑几百次就把池耗光。这是最经典的 Go 数据库 bug。
- **[6]** 查不到记录时 `Query` 本身**不报错**，只有 `Scan` 才返回 `sql.ErrNoRows`。

### 2. 手写 SQL：三个方法 + 事务里的 `defer Rollback`

不用 ORM 时标准库就三招：

| 方法 | 用途 | 返回 |
| --- | --- | --- |
| `db.Query` | 查多行 | `*sql.Rows`，必须 `Close` |
| `db.QueryRow` | 查一行 | `*sql.Row`，错误推迟到 `Scan` |
| `db.Exec` | 增删改 | `sql.Result`（`RowsAffected`、`LastInsertId`） |

事务的骨架只有三步，但**第二步是《Go 圣经》里那句名言：`defer tx.Rollback()` 一定要写，哪怕后面要 Commit**：

```go
package main

import (
	"context"
	"database/sql"
)

// transfer 在 service 层被调用；db 来自连接池
func transfer(ctx context.Context, db *sql.DB, from, to int64, amount int) error {
	tx, err := db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback() // 已提交后再回滚只会返回 ErrTxDone，无副作用

	if _, err := tx.ExecContext(ctx, `UPDATE account SET balance = balance - ? WHERE id = ?`, amount, from); err != nil {
		return err
	}
	if _, err := tx.ExecContext(ctx, `UPDATE account SET balance = balance + ? WHERE id = ?`, amount, to); err != nil {
		return err
	}
	return tx.Commit()
}

func main() {}
```

为什么 `defer Rollback` 不会把提交好的事务撤掉？因为 `Commit` 成功时事务已经结束，再 `Rollback` 返回的是 `sql.ErrTxDone`，忽略就好。反过来——**只写 Commit 不写 defer Rollback，中间任何一处 `return err` 都会把连接永久占住**，直到进程重启。

### 3. GORM：四个必须知道的行为

GORM 是 Go 里用得最多的 ORM。面试问它，基本围绕"它替你做了什么、又在哪儿悄悄改了你的意思"。

```go
package main

import (
	"errors"
	"fmt"

	"github.com/glebarez/sqlite"
	"gorm.io/gorm"
	"gorm.io/gorm/logger"
)

type User struct {
	ID        uint `gorm:"primaryKey"`
	Name      string
	Age       int
	DeletedAt gorm.DeletedAt `gorm:"index"`
}

func main() {
	db, err := gorm.Open(sqlite.Open("g.db"), &gorm.Config{
		Logger: logger.Default.LogMode(logger.Silent),
	})
	if err != nil {
		panic(err)
	}
	_ = db.AutoMigrate(&User{})
	db.Create(&User{Name: "ada", Age: 20})

	// 1) First 查不到报错，Find 不报错
	var u User
	errFirst := db.First(&u, 999).Error
	var list []User
	errFind := db.Where("id = ?", 999).Find(&list).Error
	fmt.Printf("[1] First err=%q Is(NotFound)=%v；Find err=%v len=%d\n",
		errFirst, errors.Is(errFirst, gorm.ErrRecordNotFound), errFind, len(list))

	// 2) Updates 传结构体，零值被忽略
	db.Model(&User{}).Where("id = ?", 1).Updates(User{Name: "ada2", Age: 0}) // ❌ 零值被丢掉
	db.First(&u, 1)
	fmt.Printf("[2] Updates(struct{Age:0}) 后 name=%s age=%d\n", u.Name, u.Age)

	// 3) 换成 map，零值才生效
	db.Model(&User{}).Where("id = ?", 1).Updates(map[string]any{"age": 0}) // ✅ 零值生效
	db.First(&u, 1)
	fmt.Printf("[3] Updates(map{age:0}) 后 age=%d\n", u.Age)

	// 4) Save 是全字段覆盖
	db.Model(&User{}).Where("id = ?", 1).Update("age", 30)
	db.Save(&User{ID: 1, Name: "ada3"})
	db.First(&u, 1)
	fmt.Printf("[4] Save(&User{ID:1,Name:ada3}) 后 name=%s age=%d\n", u.Name, u.Age)

	// 5) Delete 默认是软删除
	db.Create(&User{Name: "to-delete", Age: 4})
	var del User
	db.Where("name = ?", "to-delete").First(&del)
	db.Delete(&del)

	var gone, raw User
	errGone := db.Where("name = ?", "to-delete").First(&gone).Error
	_ = db.Unscoped().Where("name = ?", "to-delete").First(&raw).Error
	fmt.Printf("[5] 软删后再查 err=%q；Unscoped 查得到，deleted_at 有效=%v\n",
		errGone, raw.DeletedAt.Valid)
}
```

输出：

```
[1] First err="record not found" Is(NotFound)=true；Find err=<nil> len=0
[2] Updates(struct{Age:0}) 后 name=ada2 age=20
[3] Updates(map{age:0}) 后 age=0
[4] Save(&User{ID:1,Name:ada3}) 后 name=ada3 age=0
[5] 软删后再查 err="record not found"；Unscoped 查得到，deleted_at 有效=true
```

**第 1 行**：`First` 语义是"必须有一条"，无记录返回 `gorm.ErrRecordNotFound`（用 `errors.Is` 判）；`Find` 是"列表"，空列表是正常结果。

**第 2 行**：想把年龄改成 0，结果只改了名字。因为 `Updates` 传结构体时只更新非零字段，`Age: 0` 被当成"没填"。这是新人最常踩的坑，根因很简单——**结构体区分不了"没填"和"填了零值"，map 可以**。

**第 4 行**：`Save` 是全字段覆盖，不是"更新改过的字段"。先 `Update("age", 30)` 再 `Save(&User{ID: 1, Name: "ada3"})`，年龄被结构体的零值清成了 0。`Save` 的语义是"保存这个对象当前的样子"，适合表单全量提交，不适合"改个昵称"。局部更新一律用 `Updates`。

**第 5 行**：结构体带 `gorm.DeletedAt`（记得加索引）时，`Delete` 执行的是 `UPDATE ... SET deleted_at = ...`，不是 `DELETE`。之后普通查询自动加 `deleted_at IS NULL` 所以查不到，`Unscoped()` 才看得到，`Unscoped().Delete()` 才是真删。这条不是坑，反而常常是需求——但你要不知道，就会以为"删了还在"是缓存或事务没生效，白查半天。

### 4. 事务：闭包式最好用，但别用错 `db`

GORM 的事务有三种写法，日常就用第一种：

- **① 闭包式（推荐）**：`db.Transaction(func(tx *gorm.DB) error {...})`，返回 error 自动回滚、返回 nil 自动提交。
- **② 手动式**：`tx := db.Begin()`，控制力最强，但要自己保证 Rollback/Commit 配对，还要 recover panic。
- **③ 嵌套**：靠 SavePoint 实现，外层回滚内层跟着回滚。

两个必须知道的坑，都在这个程序里：

```go
package main

import (
	"errors"
	"fmt"

	"github.com/glebarez/sqlite"
	"gorm.io/gorm"
	"gorm.io/gorm/logger"
)

type Order struct {
	ID     uint `gorm:"primaryKey"`
	Name   string
	Amount int
}

func main() {
	db, err := gorm.Open(sqlite.Open("order.db"), &gorm.Config{
		Logger: logger.Default.LogMode(logger.Silent),
	})
	if err != nil {
		panic(err)
	}
	_ = db.AutoMigrate(&Order{})

	var cnt int64

	// 1) 返回 error → 自动回滚
	errTx := db.Transaction(func(tx *gorm.DB) error {
		tx.Create(&Order{Name: "rollback-me", Amount: 1})
		return errors.New("库存不足")
	})
	db.Model(&Order{}).Where("name = ?", "rollback-me").Count(&cnt)
	fmt.Printf("[1] 返回 err=%q，回滚后剩 %d 条\n", errTx, cnt)

	// 2) panic → 先回滚，再把 panic 继续往外抛
	func() {
		defer func() { fmt.Printf("[2] panic 继续往外抛：%v\n", recover()) }()
		_ = db.Transaction(func(tx *gorm.DB) error {
			tx.Create(&Order{Name: "panic-me", Amount: 2})
			panic("boom")
		})
	}()
	db.Model(&Order{}).Where("name = ?", "panic-me").Count(&cnt)
	fmt.Printf("[2] panic 回滚后剩 %d 条\n", cnt)

	// 3) 事务里手滑用了 db：那条写入根本不在事务里
	errTx3 := db.Transaction(func(tx *gorm.DB) error {
		db.Create(&Order{Name: "outside-tx", Amount: 3}) // ❌ 用 db 跑到了事务外
		return errors.New("回滚")
	})
	db.Model(&Order{}).Where("name = ?", "outside-tx").Count(&cnt)
	fmt.Printf("[3] 事务用 db 写入，回滚后还剩 %d 条（err=%v）\n", cnt, errTx3)
}
```

输出：

```
[1] 返回 err="库存不足"，回滚后剩 0 条
[2] panic 继续往外抛：boom
[2] panic 回滚后剩 0 条
[3] 事务用 db 写入，回滚后还剩 1 条（err=回滚）
```

**坑一：panic 会回滚，但不会吞**。GORM 内部 recover 你的 panic、执行 Rollback、然后**原样再 panic 一次**。这个设计是对的——数据安全了，业务异常你也必须知道。

**坑二：事务里必须用 `tx`，不能用 `db`**。第 3 行输出说明一切：事务回滚了，但 `outside-tx` 还在表里。因为 `db` 会从池里**另借一条连接**并自动提交，跟这个事务毫无关系。

这个错误 review 时极难发现——变量名一个字母之差，编译能过，正常路径测试也能过，只有回滚场景才暴露。防御办法：事务闭包的参数**一律叫 `tx`**，并且别把外面的 `db` 捕获进来。

## 落到项目里长什么样

1. **目录分四层**：`model/` 放结构体与 tag，`repo/` 放所有 SQL 与 GORM 调用，`service/` 只调 repo（不认识 `*gorm.DB`），`db/` 负责初始化连接池。分层的收益很直接——换 ORM、加缓存、写单测都只动 repo。
2. **`db/mysql.go` 只做三件事**：开池、配池、Ping。配池必须拿到 `gorm.DB` 底层的 `*sql.DB`，`db.DB()` 那一行不能漏。
3. **DSN 里两个参数不能少**：`parseTime=true`（不加，`DATETIME` 扫到 `time.Time` 会失败，驱动默认返回 `[]byte`）、`loc=Local`（不加，驱动按 UTC 解释时间，"10:30"读出来差 8 小时）。
4. **连接数按公式配**：单实例 `数据库 max_connections ÷ 实例数 × 0.8`，通常 20~50 就够了；`MaxIdle` 跟 `MaxOpen` 设一样，`ConnMaxLifetime` 设 3 分钟。
5. **事务闭包参数一律叫 `tx`**：并且不要把外层的 `db` 捕获进去。这条靠约定，因为编译器不拦你，只有回滚场景才炸。
6. **和 Node 对照**：`mysql2` 的 `createPool({ connectionLimit: 10 })` 就是同一件事，`knex` 的 `pool: { min, max }` 也是，Prisma 干脆藏起来只给 `connection_limit`。**Go 多出来的一件事是：你得自己记得 `rows.Close()`**——Node 那边 `await pool.query()` 一次性拿结果，没有"游标不关"这个概念。

具体写法：

```go
package main

import (
	"time"

	"gorm.io/driver/mysql"
	"gorm.io/gorm"
)

func newDB(dsn string) *gorm.DB {
	db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{})
	if err != nil {
		panic(err)
	}
	sqlDB, err := db.DB() // 拿到底层 *sql.DB 才能配池
	if err != nil {
		panic(err)
	}
	sqlDB.SetMaxOpenConns(50)
	sqlDB.SetMaxIdleConns(50)
	sqlDB.SetConnMaxLifetime(3 * time.Minute)
	return db
}

// dsn 形如：
// user:pass@tcp(127.0.0.1:3306)/demo?charset=utf8mb4&parseTime=true&loc=Local
func main() {
	// 项目启动时调用：db := newDB(os.Getenv("MYSQL_DSN"))
}
```

最后说选型：GORM 适合 CRUD 密集的业务表；报表、统计这类复杂 SQL 别硬套 ORM，直接 `db.Raw(sql, args...).Scan(&result)` 更清楚。两者混用完全正常。面试被问"为什么用 ORM"，答"常规 CRUD 省事、复杂查询照样手写 SQL"比背优点实在。

## 常见误解（FAQ）

**❌ 误区1："`sql.Open` 返回 err 为 nil，说明数据库连上了。"**

没有。`Open` 可能只校验 DSN 格式，连 TCP 握手都没发生。地址写错、密码错、服务没起，`Open` 全都能返回 nil。必须 `db.Ping()` 才真的建连。线上常见的翻车是"服务启动成功，第一个请求才炸"。

**❌ 误区2："连接池开得越大，并发能力越强。"**

反了。MySQL 的连接是进程/线程级资源，`max_connections` 默认才 151。你的服务开 200 个连接、部署 4 个实例，就是 800 连接，直接把数据库打死。经验值：**单实例 20~50，按 `数据库上限 ÷ 实例数 × 0.8` 留余量**。真正提升吞吐的是缩短慢查询、减少无谓查询，不是加连接。

**❌ 误区3："`Updates(User{Age: 0})` 应该把年龄改成 0。"**

不会。传结构体时 GORM 只更新非零字段，`0`、`""`、`false` 全被当成"没填"跳过。要改零值就用 `map[string]any` 或 `Select("Age")`。

**❌ 误区4："`Delete` 之后数据还在表里，是 GORM 的 bug。"**

是设计。结构体带 `gorm.DeletedAt` 就走软删除，只写 `deleted_at`，查询自动过滤。想真删用 `Unscoped().Delete()`。

**❌ 误区5："事务里用 `db` 还是 `tx` 都一样，反正都是连数据库。"**

完全不是。`db` 从池里另借连接并自动提交，回滚撤不掉它。这是最隐蔽的一类 bug：正常路径全对，只有回滚时数据不一致。写事务闭包时参数一律命名 `tx`，并且不要把外层的 `db` 捕获进来。

## 一句话总结

`*sql.DB` 是池：借了要还（`rows.Close()`、事务必提交或回滚），池要设上限；GORM 是层壳：零值只有 map 和 `Select` 认、`Save` 是全量覆盖、`Delete` 默认软删、事务里只能信 `tx`。
