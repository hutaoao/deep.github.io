## 一句话概括

Serverless 说白了就一句话：**你把"进程"交出去了**。不再有常驻的 node 进程让你 `setInterval`、存内存缓存、挂长连接，取而代之的是"平台按请求给你一个执行环境，用完就冻结"。

换来的好处很实在：没人访问就零成本、突然涨十倍流量也不用你扩机器。代价是**生命周期不由你控制**——这正是面试的考点所在。面试官问「你部署过 Next.js 吗」，想听的不是 `vercel deploy`，而是：冷启动卡在哪、全局变量能不能当缓存、接口里 `setTimeout` 之后的任务去哪了、为什么一上 Serverless 数据库连接数就爆。

## 核心知识点

### 1. 运行时模型：常驻进程 vs 一次一环境

| 维度 | 传统服务器 / 容器 | Serverless 函数 |
|---|---|---|
| 进程 | 你启动，一直活到你杀它 | 平台按需创建，用完冻结，几小时后回收 |
| 状态 | 内存、磁盘随你造 | 只有 `/tmp` 保留，其余默认不复用（但**可能**复用） |
| 扩容单位 | 机器/副本，要提前或自动伸缩 | 按并发自动开实例，Lambda 默认上限 1000，每 10 秒可再开 1000 个 |
| 计费 | 机器开着就花钱 | 按调用次数 + 执行时长（或 CPU 时间） |
| 长连接 | 随便挂 | 基本不能（HTTP 请求结束即返回） |

一次调用的完整生命周期分三段，这是官方口径：

1. **Init**：平台调度 + 建执行环境（微虚拟机或容器）+ 启动运行时 + 跑你 handler 之外的初始化代码
2. **Invoke**：跑 handler，返回响应
3. **Shutdown**：回收。**没有任何扩展时是 0ms，注册了外部扩展最多 2000ms**，超时直接 SIGKILL

注意第 3 段的 0ms：**handler 一返回，环境立刻进入可冻结状态**，你根本没有"退出前再做点事"的窗口（除非平台额外给了 `waitUntil` 之类的口子）。

### 2. 冷启动：三段里你只能优化最后一段

官方对冷启动的定义很克制：**"下载您的代码和设置环境"这两步通常称为冷启动**，再加上 handler 外那段初始化代码，就是全部。

| 阶段 | 谁决定的 | 你能做什么 |
|---|---|---|
| 调度 + 建环境 | 平台（微虚拟机启动、镜像/代码下载） | 换平台、用预留并发、别把函数放 VPC 里 |
| 运行时启动 | 平台 + 语言 | 选 Node 这种启动快的运行时 |
| **你的初始化代码** | **你** | 拆小包、别在模块顶层做重活、连接懒加载 |

落到代码上，第三行要分两种情况，别一刀切：

```js
// ✅ 官方推荐：连接、SDK client 放 handler 之外，冷启动建一次，热实例一直复用
const pool = mysql.createPool({ connectionLimit: 2 });

exports.handler = async (event) => {
  const [rows] = await pool.query('select 1');
  return rows;
};

// ❌ 每次调用都新建连接：并发一上来数据库直接被连接数打满（还慢）
exports.handler = async (event) => {
  const conn = await mysql.createConnection(config);
  const [rows] = await conn.query('select 1');
  await conn.end();
  return rows;
};
```

但**"可能用不到的重活"反过来要懒加载**：顶层同步读一个 20MB 的 JSON、把几千个模板全预编译，会让每个新实例的冷启动都白付几百毫秒，而大部分请求根本用不上——这种才该挪进函数里、第一次用到再建。

包体是硬门槛：Lambda 的 .zip 压缩后 **50MB**、解压后含层总共 **250MB**、最多 **5 层**。Vercel 函数同样吃 250MB 这条线（Python 是 500MB）。前端项目一不小心把整个 `node_modules` 打进去，冷启动就白优化了。

顺带纠一个常被混着说的数字：**"Worker 冷启动 5ms、Lambda 200ms"不是同一件事**。Lambda 是容器/微虚拟机级别，Workers 是 V8 isolate（进程里开个 JS 沙箱，没有内核启动、没有运行时初始化），架构不同，数字没有可比性。面试里能点出这一层，比背数字值钱。

### 3. 实例复用：全局变量、`/tmp` 和"被冻结的后台任务"

官方话说得很明白：**"在函数处理程序方法的外部声明的对象保持已初始化的状态"**，所以连接、SDK client、配置都可以放模块顶层。但有个前提必须一起说：**复用是优化，不是契约**。同一时刻可能有 50 个实例在跑，你不能假设"一定复用"，也不能假设"一定是新的"。

三条边界，第二条最反直觉：

- **全局变量**：同一实例内能跨调用复用，可以放连接池、客户端、只读配置；**不能放业务状态**（计数器、缓存用户的临时数据），因为下一个请求可能落到别的实例。
- **`/tmp` 会保留**：Lambda 给 512MB–10GB 的临时盘，环境冻结后内容还在，可以当"同实例内的磁盘缓存"，但同样不能当持久化。
- **后台任务不会消失，而是被冻结，下次调用时继续跑。** 官方原文：「如果 Lambda 重复使用执行环境，则由 Lambda 函数启动但在函数结束时未完成的后台进程或回调将继续执行。确保代码中的任何后台进程或回调在代码退出前已完成。」

第三条是真正的坑：你以为 `setTimeout` 发出去的埋点会丢，实际上它会在**几十秒后、处理另一个用户的请求时**接着跑。后果是日志时间线错乱、埋点算到别人头上、甚至写脏数据。

```js
// ❌ handler 返回后，环境被冻结；这个写库操作会在下次解冻时突然执行
exports.handler = async (event) => {
  setTimeout(() => db.update(...), 3000);
  return { ok: true };
};

// ✅ 必须完成的，就在 handler 里 await 完
exports.handler = async (event) => {
  await db.update(...);
  return { ok: true };
};

// ✅ 需要"响应先走、活继续干"的，交给平台能力或队列：
// Vercel / Workers 用 waitUntil（Workers 里响应后最多延长 30s）
// AWS 用异步调用、SQS、Step Functions
```

### 4. 并发模型：一实例一请求 vs 一实例多请求

这是 2025–2026 年变天的地方，也是连接池问题的根因。

| 模型 | 代表 | 并发怎么算 | 全局变量意味着什么 |
|---|---|---|---|
| 一实例一请求 | 传统 Lambda | 并发数 ≈ 实例数 | "实例私有"，安全 |
| 一实例多请求 | Vercel Fluid Compute、Cloudflare Workers isolate | 一个实例里同时跑多个请求 | **变成共享状态**，`let counter = 0` 不再安全 |

所以你会看到两种截然相反的博客：一种说"全局变量可以放心当缓存"，另一种说"绝对不行"。都对，取决于并行模型。

再往下就是前端最容易踩的坑——**数据库连接数被打满**。

一个实例开 10 个连接的池，平时 2 个实例没事；大促 200 并发 → 200 个实例 → 2000 个连接，MySQL 直接 `Too many connections`。三种解法，按场景选：

- **每实例极小池**（`connectionLimit: 1~2`）+ 服务器端有上限，最简单，适合低频接口
- **外部连接池代理**：RDS Proxy、Supavisor、PgBouncer，Serverless 侧连代理，代理持有真连接
- **HTTP 型数据库驱动**：Neon / Supabase 的 HTTP 接口，一次查询一次 HTTPS 请求，天然无连接状态（代价是事务和多语句会变贵变慢）

Edge 运行时还有个附带限制：**没有 TCP 长连接**，`pg` / `mysql2` 这类驱动根本跑不起来，只能走 HTTP 驱动或 ORM 的 edge 版本。这不是配置问题，是运行时能力问题。

### 5. 两套运行时：Node 和 Edge 到底差在哪

前端最常遇到的"选运行时"，其实是在这两者之间选：

| 维度 | Node 运行时 | Edge 运行时 |
|---|---|---|
| 底座 | 完整 Node 进程（Vercel 底下是 Lambda） | V8 isolate（Workers / Vercel Edge） |
| API | 全部 Node API：`fs`、`net`、原生模块、`sharp` | 只有 Web 标准：fetch / Streams / Web Crypto，**没有 `fs`、`net`、`child_process`** |
| 位置 | 固定区域（Vercel 默认 `iad1`） | 就近用户，全球多节点 |
| 典型限制 | Vercel 默认 300s，Pro 最长 800s；请求体 4.5MB；包 250MB | Vercel Edge 必须 25s 内开始响应、最多流式 300s；Workers 免费 10ms CPU、付费默认 30s（可到 5min）、**128MB/isolate**、包 64MiB |
| 适合 | ORM、文件处理、PDF、上传、需要 npm 生态 | 鉴权、重写、A/B、地理路由、SSR 流式、AI token 转发 |

Cloudflare Workers 的 `nodejs_compat` 能把 `node:buffer`、`node:crypto`、`node:stream`、`node:events` 等映射过去，但 `fs` 和 `net` 是**故意没有**的——边缘节点上就没有文件系统和裸 socket。所以"我的 Express 能直接跑在 Workers 上吗"答案是不能，要换 Hono 这类基于 Web 标准的框架。

一个 2026 年的加分点：**Next.js 16 把 `middleware.ts` 改名成了 `proxy.ts`，并且固定跑在 Node 运行时**。官方原文：「Proxy defaults to using the Node.js runtime. The `runtime` config option is not available in Proxy files. Setting the `runtime` config option in Proxy will throw an error.」

这意味着两件事：一是以前为了 Edge 兼容而绕开的 `pg`、`jsonwebtoken`、`bcrypt`，现在能直接用了；二是"中间件跑在离用户最近的边缘节点"这个卖点，在 Next.js 16 的 proxy 上没有了——路由中间件的延迟回到和服务端同区域。

### 6. 什么时候别用 Serverless

| 场景 | 为什么不适合 | 该用什么 |
|---|---|---|
| WebSocket / 长轮询 | 调用结束即冻结，连接留不住 | 常驻服务、DO、托管 WS 服务 |
| 常驻定时任务、消费者 | 没有"一直活着的进程" | 平台 Cron（有最小粒度）/ 常驻 worker |
| CPU 密集（图像、视频、加密） | CPU 时间被卡死且贵 | 容器、批处理、专门的转码服务 |
| 需要本地文件 / 原生二进制 | 只有 `/tmp`，二进制要匹配平台架构 | 容器 |
| 稳定低延迟的核心链路 | 冷启动不可预测，尾延迟高 | 常驻服务 + 预留容量 |

成本也要算清楚：**请求稀疏（比如一天几百次）时 Serverless 便宜到几乎免费；持续高负载时反而比一台常驻机器贵**，因为按量计费的单价远高于包年包月的机器。面试里说"看流量曲线形状选"比背价格表靠谱。

### 7. 前端接入的四个具体坑

- **环境变量别想当然**：服务端函数的 `env` 前端拿不到；Next.js 只有 `NEXT_PUBLIC_` 前缀才会打进客户端包——**反过来说，加了前缀的就不是秘密**，数据库密码绝不能加。
- **请求体有硬上限**：Vercel 是 4.5MB，超了直接 413。文件上传必须走"前端直传对象存储 + 后端只收 URL"。
- **超时默认值会咬人**：Vercel 函数超时返回 504 `FUNCTION_INVOCATION_TIMEOUT`，长任务要显式配 `maxDuration`，别指望默认值够。
- **冷启动会串到首屏**：SSR 页面落在冷实例上，TTFB 就是几百毫秒起。所以首页该静态化就静态化（ISR/SSG），别让每个请求都去摸函数。

## 其实你每天都在用

- 你在 Vercel 上部署的 Next.js，`app/api/xxx/route.ts` 每个文件就是一个函数。
- 登录页"发送验证码"接口，背后通常就是个函数：收请求 → 调短信服务 → 返回。
- 图片 CDN 自动裁剪、格式转 WebP，本质是边缘函数在图片请求时实时处理。
- AI 聊天里打字机效果，一半功劳在 Edge 运行时转发 SSE——它只搬字节，不占 CPU。
- GitHub / 支付平台的 Webhook，最省事的接法就是一个函数 URL，配好签名校验就完事。
- 对象存储上传完成后触发的回调、缩略图生成，都是事件驱动的函数。

## 常见误解（FAQ）

**❌ 误区1："Serverless 就是不用管服务器，所以也不用管架构"**

你只是不用管机器，**状态、连接、并发、超时全归你管**。最典型的就是连接池：常驻服务一个池子够用，Serverless 下要按"实例数 × 并发"重新算。

**❌ 误区2："全局变量在 Serverless 里绝对不能存东西"**

反了。官方明确推荐把连接、SDK client 放 handler 之外，靠实例复用省掉重复初始化。不能放的只有**业务状态**——因为你不确定这次和下次是不是同一个实例。

**❌ 误区3："handler 返回后，没跑完的异步任务就丢了"**

不是丢，是**冻结**。环境被复用时它会继续执行，跑在别人的请求里。所以要么 `await` 完再返回，要么交给队列，绝不能 fire-and-forget。

**❌ 误区4："冷启动慢，把内存调大就快了"**

Lambda 的 CPU 是按内存比例给的（1769MB 约等于 1 vCPU），所以加内存确实能加速**初始化代码**那段。但调度和建环境那段你改不了。而且反过来，内存调大单价也涨——优化包体和初始化逻辑才是性价比最高的。

**❌ 误区5："Edge 运行时就是更快的 Node"**

不是快慢问题，是**能力子集**问题。`fs`、`net`、原生模块、TCP 数据库连接统统没有，`eval` 和 `new Function` 也被禁。能跑的前提是所有依赖都只用 Web 标准 API。

**❌ 误区6："Serverless 一定比服务器便宜"**

只在"请求稀疏、波峰波谷悬殊"时成立。7×24 稳定高负载跑下来，按量计费通常比一台常驻机器贵，这也是很多团队"平时用函数、核心链路用容器"的原因。

## 一句话总结

**Serverless 的代价不是"没有服务器"，而是"你不再拥有进程"——想清楚每个请求要活多久、状态放哪、连接从哪来，冷启动和连接池这两个坑就不会踩。**
