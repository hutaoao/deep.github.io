## 一句话概括

「Node 只能用一个核」是入门话，面试官真正想听的是下一句：**那你们线上怎么把它跑满、跑稳？**

答案由三件事拼起来：`cluster` 把一个进程变多个（吃满多核）、进程守护让挂了自己起来（PM2）、优雅退出让发版时正在处理的请求不被打断。串起来就是一道完整的口头题：**一个端口怎么被多个进程共享 → 谁在分发连接 → 发版怎么不停机 → 停不下来的请求怎么办**。这四步答顺了，比背一堆 PM2 命令有用得多。

## 核心知识点

### 1. cluster 只做两件事：共享端口 + 决定谁来 accept

worker 是 `child_process.fork` 出来的，所以能和主进程走 IPC 传句柄。worker 里调 `server.listen(3000)` 时，真正干活的是主进程——主进程 listen，再把 accept 到的 socket 句柄发给某个 worker。所以**你只写一份 `listen(3000)`，所有 worker 都在 3000 上接客**，不需要谁去分端口。

官方给了两种分发方式，差别很大：

| 策略 | 谁 accept | 实际表现 |
|---|---|---|
| `SCHED_RR`（默认，**除 Windows 外**） | 主进程 accept 后轮询发给 worker | 均匀，且有内建逻辑避免压给繁忙进程 |
| `SCHED_NONE`（Windows 默认） | 主进程只建 listen socket，各 worker 自己 accept | 理论最优，实测严重失衡——官方原文说见过「8 个进程里 70% 的连接只落在 2 个进程上」 |

```js
const cluster = require('node:cluster');

// 必须在 fork 第一个 worker 之前设置，之后就被冻结了
cluster.schedulingPolicy = cluster.SCHED_RR;
// 等价的环境变量写法：NODE_CLUSTER_SCHED_POLICY=rr

if (cluster.isPrimary) {
  require('node:os').cpus().forEach(() => cluster.fork());
}
```

这段设置是**一次性**的：官方明说「一旦 fork 出第一个 worker 或调用 setupPrimary()（以先发生者为准），这个全局设置就冻结了」。写在 fork 后面等于没写。

**但 RR 是按连接轮询，不是按请求轮询。** 这是最容易答错的地方。同一条 keep-alive 连接上的所有请求，永远落在同一个 worker 里。本机起两个 worker 实测：

| 客户端发起方式 | 连续 6 个请求落到哪个进程 |
|---|---|
| 每次新建连接（`agent: false`） | `9070 9069 9070 9069 9070 9069`（严格交替） |
| 复用一条 keep-alive 连接 | `9070 9070 9070 9070 9070 9070`（全在一个） |

还有个更隐蔽的点：**Node 19 起 `http.globalAgent` 默认 `keepAlive: true`**，也就是说服务端之间互相调接口、不显式传 agent 的时候，连接本来就在复用。客户端一个连接打满，RR 就退化成「一个 worker 吃满、另一个闲着」。所以 cluster 的均衡度取决于**并发连接数**，而不是 QPS——高 QPS 少连接的场景（内网 RPC、长轮询、SSE）尤其容易翻车。

### 2. PM2 替你做的其实是三件事

别把 PM2 当"启动器"，它是在你进程外面套了三层保障：

| 能力 | 关键配置 | 默认值 |
|---|---|---|
| 守护（挂了拉起） | `autorestart` / `min_uptime` / `max_restarts` / `max_memory_restart` | `true` / `1000ms` / `16` / 不设 |
| 集群（吃满多核） | `instances` / `exec_mode` | `1` / `fork` |
| 发版（不停机重启） | `wait_ready` / `listen_timeout` / `kill_timeout` | 不设 / 不设 / `1600ms` |

```js
// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'api',
    script: 'server.js',
    instances: 'max',       // 设了 instances 就自动进 cluster 模式
    exec_mode: 'cluster',
    wait_ready: true,       // 等我 process.send('ready') 再算启动完成
    listen_timeout: 5000,
    kill_timeout: 5000,     // 给优雅退出留 5s，默认只有 1.6s
    max_memory_restart: '512M',
    merge_logs: true,       // 默认 false：每个实例一个日志文件
  }],
};
```

`min_uptime` + `max_restarts` 是一对：进程起来不到 1s 就挂、连挂 16 次，PM2 判定「起不来了」，**停止重启**。所以线上改错配置导致秒挂时，你会看到状态从 `online` 变成 `errored` 而不是无限重启把自己刷死。

跑起来之后 `instances: 2` 的本机实测：

```
# pm2 jlist 里每个实例的字段
id 0  pid 5336  exec_mode: 'cluster_mode'  NODE_APP_INSTANCE: 0
id 1  pid 5337  exec_mode: 'cluster_mode'  NODE_APP_INSTANCE: 1
# 日志实际落在两个文件里（merge_logs 默认 false）
pm2demo-out-0.log  pm2demo-out-1.log
```

`NODE_APP_INSTANCE` 是 PM2 注入的实例序号，多实例下**定时任务只让它在一个实例跑**就靠它：

```js
// ❌ 4 个实例 = 同一个定时任务跑 4 遍，发 4 条短信
setInterval(sendDailyReport, 24 * 60 * 60 * 1000);

// ✅ 只让 0 号实例跑
if (process.env.NODE_APP_INSTANCE === '0') {
  setInterval(sendDailyReport, 24 * 60 * 60 * 1000);
}
```

另一个冷知识：PM2 起的进程里 `process.argv[1]` 不是你的 `server.js`，而是 `.../pm2/lib/ProcessContainer.js`——你的代码是被它 `require` 进来的。所以任何靠 `process.argv[1]` 推断项目根目录的代码，在 PM2 下都会拿到错误路径，要用 `__dirname` 或 `process.cwd()`。

### 3. reload 不是「一个个重启」，是「先起后杀」

这是本篇最值得记住的一条，因为绝大多数文章都写错了。看 PM2 7.0.4 的源码 `lib/God/Reload.js`，`reload` 走的是 `hardReload`：

1. 把旧 worker 挪到临时槽位 `_old_<id>`（不是立刻杀）
2. `executeApp` 起一个新 worker
3. 等新 worker 发来 `ready`（配了 `wait_ready`）或 `listening` 事件
4. **这时候才** `deleteProcessId(_old_id)` 杀掉旧的
5. 等不到就由 `listen_timeout` 兜底，或者新进程起不来就把旧的挪回来（`unparkOldWorker`）

所以同一个实例的日志，顺序一定是这样（本机实测）：

```
[boot]   pid=6008 NODE_APP_INSTANCE=0     ← 新 worker 先起来并 listen
[listen] pid=6008 port=3999
[signal] pid=5336 got SIGINT              ← 才轮到旧的
[closed] pid=5336 server closed
[exit]   pid=5336 exiting
```

新进程没起来之前，旧的一直在接流量。这就是 reload 敢叫「0 秒停机」的底气。

**顺带纠正一个常见简化说法："restart 会把所有进程同时杀掉"。** 实测 4 实例跑 `pm2 restart`：

```
[signal] pid=7637 got SIGINT     ← 两个一批
[signal] pid=7638 got SIGINT
（1.3s 后）
[signal] pid=7639 got SIGINT
[signal] pid=7640 got SIGINT
```

源码里写得很清楚：`concurrent_actions = envs.parallel || conf.CONCURRENT_ACTIONS`，而 `CONCURRENT_ACTIONS` 默认是 **2**，并且 `ids.length <= 2` 时强制改成 **1**。所以准确的说法是：**restart 是"按并发度分批杀"，默认一批 2 个**。它比"全杀"温和，但每一批都是杀完再起，那段时间容量就是少了——和 reload 的"先起后杀"是本质区别，别混着说。

### 4. 优雅退出：PM2 先发的是 SIGINT，不是 SIGTERM

这个细节决定了你的 handler 写在哪个事件上。官方文档原话：catch the `SIGINT` signal「the first signal sent on exit by PM2」。本机实测也是 `SIGINT`。

流程是：`SIGINT` → 等 `kill_timeout`（默认 1600ms）→ 还没退就 `SIGKILL`。实测把 `kill_timeout` 设成 300ms、而代码需要 1200ms 才退出，日志里**根本没有 `[exit]` 那一行**，进程被硬杀了：

```js
// server.js
const server = app.listen(3000, () => {
  if (process.send) process.send('ready'); // 配了 wait_ready 才需要
});

let closing = false;
function shutdown(sig) {
  if (closing) return;           // 幂等：SIGINT 和 SIGTERM 可能都来
  closing = true;
  server.close(async () => {     // ① 不再 accept 新连接
    await db.end();              // ② 关掉连接池，让在飞请求写完
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 4000).unref(); // ③ 兜底，比 kill_timeout 短一点
}
process.on('SIGINT', shutdown);
process.on('SIGTERM', shutdown);
```

三个坑必须知道：

- **`server.close()` 会不会关掉 keep-alive 空闲连接，看 Node 版本**。同一段脚本（一个请求走完、连接留在池里，再调 `server.close()`）本机对照：Node **18.20.4** 上 3 秒后回调都没触发，Node **22.22.2** 上 **8ms** 就触发了——v19 起 `server.close()` 会顺手关掉空闲连接。所以老文章里"必须手动 `closeIdleConnections()`，否则要等到连接超时"只在旧版本成立；但**正在处理中的请求**它照样会等，兜底超时还是得配。
- **`kill_timeout` 和上游超时要对齐**。PM2 默认 1600ms 对很多业务是不够的（一个慢 SQL 就超了），但也不能无脑调到 30s——你调多大，发版时每个实例就最多卡多久。
- **容器里必须用 `pm2-runtime`**。普通 `pm2 start` 会 daemonize 到后台、主进程直接返回，容器立刻以为进程结束了就退出。`pm2-runtime ecosystem.config.js` 才保持前台。而上了 Kubernetes，`terminationGracePeriodSeconds` 默认 30s，比 PM2 的 1600ms 宽松得多，两边的超时顺序要自己捋一遍：K8s 发 SIGTERM → PM2 转 SIGINT → kill_timeout → SIGKILL。

### 5. 多进程之后，四样东西就不再是"你的"了

一个进程变四个，原来理所当然的东西全变成共享资源问题：

| 原来靠什么 | 多实例后变成什么 | 解法 |
|---|---|---|
| 内存里存 session / 验证码 | 下一个请求打到别的实例就"登录失效" | Redis / 数据库 |
| `setInterval` 跑定时任务 | 跑 N 遍，用户收到 N 条推送 | `NODE_APP_INSTANCE === '0'` 或独立 worker |
| 本地 Map 做限流计数 | 实际阈值变成 N 倍 | Redis 原子计数 |
| WebSocket 连接留在进程内 | reload 时这一批连接全断；广播要挨个实例发 | 粘性会话 + Redis pub/sub adapter |

最后一条在面试里是加分项：**reload 的"零停机"只对 HTTP 短连接成立**。WebSocket 是长连接，旧 worker 被杀，那几十个连接就是断的，客户端得重连。所以有长连接的服务，reload 要配合客户端的重连退避，或者干脆分机器灰度。

### 6. 负载分三层，混着说就错了

| 层级 | 谁在做 | 分发单位 | 解决什么 |
|---|---|---|---|
| 单机进程内 | cluster（`SCHED_RR`） | 连接 | 把一台机器的多核吃满 |
| 单机入口 | Nginx `upstream`（RR / `least_conn` / `ip_hash`） | 请求 | TLS、静态资源、跨机器前的第一道分摊 |
| 跨机器 | LVS / 云 SLB / K8s Service | 连接/请求 | 多台机器、健康检查、扩缩容 |

`least_conn` 要比默认 RR 更贴近真实负载，因为它看的是"当前谁身上连接少"；但只要客户端 keep-alive 密集，各种按连接计的算法都会失真——想按请求精确分摊，只能在七层按请求转发。

**结论一句话**：cluster 的 RR 是"进程级"的，Nginx 是"机器内/机器间"的，它们是串联的两层，不是替代关系。也别指望 PM2 做跨机器的事——**PM2 是单机方案，上了 K8s 它反而成了反模式**（一个 Pod 里塞多个进程，扩缩容、健康检查、资源限制全乱套，正确做法是一个 Pod 一个 node 进程，让 K8s 去调度）。

## 其实你每天都在用

- 打开任何一个中型站点，背后都是 Nginx 把请求分给好几个 node 进程，你只是看不见。
- 自建 Nuxt / Next 服务时那句 `pm2 start npm -- start`，用的就是 fork 模式而不是 cluster。
- 支付回调接口发版时"偶发 502"，十有八九是 reload 没配 `wait_ready` 或没做优雅退出。
- 后台的日终对账任务，代码里一定有个 `if (process.env.NODE_APP_INSTANCE === '0')`。
- 凌晨收到内存告警，`pm2 monit` 里某个实例内存曲线一路向上——`max_memory_restart` 只是止血，泄漏还得查。
- 手机 App 里"网络开小差，请重试"，有时候就是发版瞬间长连接被踢了。

## 常见误解（FAQ）

**❌ 误区1："生产上 Node 必须用 PM2"**

PM2 只解决"单机上多进程 + 守护 + 发版"。上容器和 K8s 之后，这三件事分别由 Deployment 副本数、存活探针、滚动更新接管，PM2 反而添乱（PID 1 信号、日志、多进程模型都要额外处理）。面试答"PM2 是单机/裸机时代的方案，容器时代用进程管理器或直接用编排系统"才算完整。

**❌ 误区2："cluster 的多个 worker 共享内存，所以缓存可以放进程里"**

完全不共享。每个 worker 是独立进程、独立堆、独立事件循环，`cluster` 唯一共享的东西是那个监听 socket 的句柄。任何"进程内状态"在多实例下都要外部化。

**❌ 误区3："配了 `pm2 reload` 就一定零停机"**

要同时满足三条：`wait_ready` + 代码 `process.send('ready')`（否则 PM2 只等 `listening`，端口开了但数据库还没连上就切流量）、优雅退出（否则 `kill_timeout` 到点直接 SIGKILL 掉在飞请求）、应用无状态（否则新实例接不住旧实例的内存态）。缺一条就是"看着没问题，高峰期偶发 502"。

**❌ 误区4："`kill_timeout` 调大一点更安全"**

它同时是"发版时每个实例最多卡多久"。调到 30s，8 个实例滚动一轮最坏就是几分钟；而且容器和 K8s 还有自己的超时，K8s 默认 30s 一到直接 SIGKILL，PM2 设多大都没用。正确姿势是：按业务最长请求耗时定，且**小于上游（Nginx / 网关）的读超时**。

**❌ 误区5："多实例之间定时任务会自己协调，只有一个会跑"**

不会。cluster 只共享端口，不共享任何调度。不写 `NODE_APP_INSTANCE` 判断，就是 N 个实例各跑一遍。

**❌ 误区6："cluster 的 RR 就是负载均衡，不需要 Nginx 了"**

RR 只在一台机器内、按连接轮询、不看请求耗时和 CPU。跨机器、健康检查、TLS 卸载、静态资源，统统不归它管。

## 一句话总结

**cluster 负责把一台机器吃满，PM2 负责让它挂了能起、发版不断，优雅退出负责让最后几百毫秒的请求体面收尾——三者缺一，Node 服务就只能算"跑起来了"，算不上"跑在生产上"。**
