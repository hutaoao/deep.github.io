## 一句话概括

分包不是「把文件挪个文件夹」，它是微信给小程序划的**下载单元**，也是**注入单元**。

面试问分包，本质是在问两件事：**冷启动怎么优化**、**多团队怎么解耦**。所有答案都指向同一条因果链——主包是冷启动的必经之路，所以主包必须最小；分包在用户进入时才下载，所以有了预下载；下载完还要注入执行，所以有了按需注入。

记住这个链条，后面每个配置项你都能说出它优化的是哪一段。

## 核心知识点

### 1. 三条体积红线，先背数字

| 项目 | 上限 |
| --- | --- |
| 主包 | ≤ 2M |
| 单个分包 | ≤ 2M |
| 所有分包总和 | ≤ 30M（服务商代开发的小程序 ≤ 20M） |

注意总和是 **30M**，不是网上到处传的 20M——20M 是老口径，现在只有服务商代开发的场景才卡 20M。

另外两条硬规则，比数字更容易被忽略：

- **`tabBar` 页面必须在主包内**。因为切 tab 不能等下载。
- **`subPackages` 的根目录不能是另一个 `subPackages` 内的子目录**，分包不能嵌套。

配置长这样：

```json
{
  "pages": ["pages/index/index", "pages/cart/cart"],
  "subPackages": [
    { "root": "packageOrder", "name": "order", "pages": ["pages/list/list", "pages/detail/detail"] },
    { "root": "packageActivity", "pages": ["pages/act/act"], "independent": true }
  ]
}
```

真正容易翻车的是这条打包原则（官方原文）：**「`subPackages` 配置路径外的目录将被打包到主包中」**。

所以你新建了 `pages/new-feature/` 忘了写进 `subPackages`，它不会报错，只会悄悄把主包撑大，直到某次上传被拒：`main package source size 2071KB exceed max limit 2048KB`。分包配置是**白名单**，不是黑名单。

### 2. 四种加载形态的分工，别混着答

| 类型 | 什么时候下载 | 能访问主包资源吗 | 典型场景 |
| --- | --- | --- | --- |
| 主包 | 启动就下载 | —— | 首页、tabBar、公共工具 |
| 普通分包 | 进入该分包页面时 | 能 | 订单、设置、个人中心 |
| 独立分包 | 进入时只下自己 | **不能** | 扫码直达的活动页、广告落地页 |
| 分包异步化 | 显式 `require.async` 或用占位组件时 | 能跨分包 | 低频大依赖、跨包复用组件 |

独立分包为什么快，一句话：**从独立分包页面启动时，主包不需要下载**。所以它适合「用户从外部（扫码、分享卡片、公众号菜单）直接进来」的页面——这类场景下主包纯属拖累。

代价是四条限制，必须能一口气说出来：

1. **不能依赖主包和其他分包的任何内容**——JS、template、wxss、自定义组件、插件全都不行（用了分包异步化的话，JS / 自定义组件 / 插件例外）。
2. **主包的 `app.wxss` 对独立分包无效**，别在独立分包页面里指望全局样式。
3. **`App` 只能在主包定义**，独立分包里定义会造成「无法预期的行为」。
4. **独立分包暂时不支持使用插件。**

第 3 条还牵出一个高频追问：独立分包里 `getApp()` 拿到什么？

- 用户**从独立分包页面启动**时，主包不存在，`App` 没注册，`getApp()` 返回 `undefined`。
- 用户**从主包/普通分包跳过去**时，`App` 已存在，能拿到真对象。

要共享全局数据，用 `getApp({ allowDefault: true })`（基础库 2.2.4 起）：主包没加载时先返回一个默认对象，等 `App` 注册后，默认对象上的属性会被**合并**进真正的 `App`。

```js
// 独立分包页面里
const app = getApp({ allowDefault: true })  // 主包没加载时是 {}
app.token = 'xxx'                            // 先存在这里

// app.js
App({ data: 123 })
// 主包加载后 getApp() => { data: 123, token: 'xxx' }
```

顺带一个容易答错的点：从独立分包启动时，主包 `App` 的 `onLaunch` 和首次 `onShow` **不是不执行，是延后**——延到用户首次进入主包或其他普通分包页面时才执行。想在独立分包里监听应用级事件，得用 `wx.onAppShow` / `wx.onAppHide` / `wx.onError`。

### 3. 分包之间不能互相 `require`，这是设计约束

官方引用原则写得很直白：`packageA` 无法 `require` `packageB` 的 JS，无法 `import` `packageB` 的 template，也无法使用 `packageB` 的资源；但**可以用主包和自身的**。

为什么这么设计？因为分包是独立的下载单元。A 里的代码如果要 `require` B，那加载 A 就必须先把 B 也下下来——分包就退化成「一个大包切碎存着」，按需加载的意义没了。

于是立刻产生一个矛盾：**公共代码放主包能让所有分包复用，但主包会变大**。这个矛盾的标准解法就是分包异步化。

### 4. 分包异步化：跨包引用怎么「等」

基础库 **2.11.2** 起。它干的事是：允许跨分包引用，但引用结果**异步返回**，不阻塞当前代码执行。

JS 侧两种写法，回调风格和 Promise 风格：

```js
// 回调风格：第三个参数是失败回调
require('../subPackageB/utils.js', (utils) => {
  console.log(utils.formatPrice(99))
}, ({ mod, errMsg }) => {
  console.error(`加载失败: ${mod}, ${errMsg}`)
})

// Promise 风格（推荐）
const { formatPrice } = await require.async('../commonPackage/index.js')
```

组件侧用**占位组件**，这是异步化里最容易被追问的一环：

```json
// subPackageA/pages/index.json
{
  "usingComponents": {
    "heavy-chart": "../../subPackageB/components/chart/index",
    "price-tag": "../components/price-tag/index"
  },
  "componentPlaceholder": {
    "heavy-chart": "view",
    "price-tag": "price-tag-skeleton"
  }
}
```

含义：`heavy-chart` 还没下载完时，先渲染内置 `view` 顶着；`price-tag` 用本分包内的骨架屏顶着；分包下载完，占位组件自动替换成真组件。

两个补充点，说了显得你读过文档而不是背博客：

- 基础库 **2.24.3** 之后可以用 `wx.onLazyLoadError` 监听加载失败，做降级。
- 占位组件不是只服务异步化的——在开了按需注入的前提下，**给组件配了 `componentPlaceholder`，它就会自动变成「用时注入」组件**。这两件事共用一套配置。

### 5. 预下载：用 2M 的额度换一次点击的等待

分包是「进页面才下载」，那用户点下去到页面出来之间的白屏就是纯损失。`preloadRule` 就是提前把这个下载做掉。

```json
{
  "preloadRule": {
    "pages/index/index": {
      "network": "all",
      "packages": ["order"]
    },
    "packageActivity/pages/act/act": {
      "packages": ["__APP__"]
    }
  }
}
```

- `packages` 填分包的 `root` 或 `name`；`__APP__` 表示**主包**（独立分包可以预下载主包，这条很多人不知道）。
- `network` 默认是 **`wifi`**，可选 `all` / `wifi`。默认值就是 wifi，说明官方默认让你别烧用户流量。
- 触发时机：**进入配置的那个页面时**，由框架静默下载。

然后是面试最爱挖的限制（官方原文）：**「同一个分包中的页面享有共同的预下载大小限额 2M」**。

意思是限额是按「页面所属的分包」算的，不是按页面算的。同一分包里页面 A 预下载了 0.5M，页面 B 最多还能预下载 1.5M，而且这个限额在开发者工具打包时就会校验报错。

所以「把所有分包都配进预下载」是错的，正确做法是**只配主包页面真正会跳过去的那一两个分包**。验证有没有生效：vConsole 里搜 `preloadSubpackages` 开头的日志。

### 6. 按需注入：真正决定「注入」耗时的那一环

分包解决的是**下载**，但下载完还有**注入**——JS 要合并进运行环境并执行。官方说得清楚：「注入代码量的大小与内存占用与注入耗时正相关。」

默认行为很不划算：**启动时把启动页面依赖的所有代码包（主包、分包、插件包、扩展库）的 JS 全部合并注入**，包括你没访问的页面、没用到的自定义组件，而且这些 JS 会**立刻执行**。

开启只要一行（基础库 2.11.1 起）：

```json
{
  "lazyCodeLoading": "requiredComponents"
}
```

开了之后「仅注入当前访问页面所需的自定义组件和页面代码」。但注意官方那句提醒——**页面 JSON 里声明的所有组件、以及 `app.json` 里全局声明的组件，都被视为该页面的依赖**。也就是说：

```json
// ❌ 声明了 5 个组件，页面里只用了 1 个 —— 开了按需注入也照样注入 5 个
{ "usingComponents": { "a": "...", "b": "...", "c": "...", "d": "...", "e": "..." } }
```

这就是「配了 `lazyCodeLoading` 但没感觉变快」的最常见原因。配套动作是：**清掉 `usingComponents` 里没用到的声明，别在 `app.json` 里全局注册低频组件**。

再往前一步是「用时注入」（2.11.2 起）：在开了按需注入的前提下给组件配 `componentPlaceholder`，这个组件就变成**首次渲染时才注入**——先渲染占位组件，渲染结束再注入，注入完替换回来。

还有一条边界：**插件包和扩展库不支持按需注入。** 想让插件也按需，只能把插件放进一个分包，用分包异步化异步引入。

### 7. 主包瘦身：给一套能落地的顺序

面试官问「主包超了怎么办」，别只答「分包」，要给顺序：

1. **图片全走 CDN**，本地只留 icon 级资源。这一步收益最大、风险最低。
2. **UI 库按需引入**，一个全量引入的组件库轻松吃掉几百 KB。
3. **重依赖单独拉一个分包**：富文本编辑器、图表库、地图 SDK、PDF 预览，这类单个就 500KB～1MB 的，别留在主包。
4. **用分包异步化把低频大依赖踢出主包**：主包不再 `require` 它，改成 `require.async`。
5. **清理未使用的组件声明和未引用文件**，用开发者工具的「代码依赖分析」扫一遍。
6. **最后才考虑拆页面**，因为拆页面会带来跨包跳转的等待成本。

一句话总结选型：**能不能进分包，看「用户不点它会不会影响首屏」；要不要独立分包，看「用户会不会从它直接进来」。**

## 其实你每天都在用

- 打开电商小程序点「我的订单」，那 1～2 秒的白屏，就是分包正在下载。
- 双十一活动页扫码直接打开、不经过首页，那就是独立分包（否则得先下主包）。
- 小程序启动时那一小段空白，很多是代码注入的耗时，不是网络慢。
- 上传时那句 `main package source size 2071KB exceed max limit 2048KB`，是主包超了 2M。
- 你在页面 JSON 里复制粘贴留下的、早就删掉的组件声明，正在拖慢每一次启动。
- 用 uni-app 时 `pages` 目录默认全在主包，得在 `pages.json` 里手动配 `subPackages`。
- 跳转分包页面时那一瞬间的骨架屏，本质就是「占位组件」的思路。

## 常见误解（FAQ）

**❌ 误区1：「小程序总包上限 20M。」**
已经是 30M 了，只有服务商代开发的小程序才是 20M。答 20M 会被认为看的资料过期了。

**❌ 误区2：「配了 `subPackages`，主包就自动变小了。」**
分包是白名单机制，只有真的把文件移到分包根目录、且主包不再引用它，主包才会变小。只写配置不搬文件，文件还在主包里。

**❌ 误区3：「独立分包就是加载更快的分包。」**
只在「用户从独立分包页面启动」时快，因为省掉了主包下载。从主包跳到独立分包，该有的成本一样不少。

**❌ 误区4：「预下载配得越多，体验越好。」**
同一分包内的页面共享 2M 预下载额度，超了打包就报错；而且默认只在 wifi 下预下载，你配了一堆在 4G 用户身上根本不生效。

**❌ 误区5：「开了 `lazyCodeLoading` 启动就一定变快。」**
页面 JSON 里声明的组件依然算依赖。不清 `usingComponents`，等于开了个寂寞。插件包和扩展库也压根不支持按需注入。

**❌ 误区6：「分包异步化能让分包之间随便互相引用。」**
它只解决「异步等待」，不解决「同步依赖」。跨分包 `require` 必须用 `require.async`，跨分包组件必须有 `componentPlaceholder` 兜底，否则下载期间就是渲染不出来。

## 一句话总结

分包本质是拿「一次跳转的下载等待」换「冷启动的主包体积」，预下载、异步化、按需注入做的都是同一件事——把这个等待挪到用户看不见的地方。
