## 一句话概括

小程序登录的核心不是"调 `wx.login` 拿 code"，而是**微信只负责认人，登录态得你自己建**。微信给你的是一串身份标识（openid / unionid）和一把密钥（session_key），它并不会给你一个"登录状态"。真正让用户下次还能免登录进来的，是你自己服务端签发的 token。

面试为什么爱问？因为它同时考三样东西：你懂不懂小程序这套凭据的流转与生命周期（code 一次性、session_key 会被顶替）、会不会设计登录态（双 token、无感刷新、并发处理）、以及有没有安全边界意识（前端传来的身份字段一个字都不能信）。答"wx.login 拿 code 换 openid 就登录了"的人，这三样一个都没答到。

## 核心知识点

### 1. 三段式：微信认人，你发牌

面试官问「小程序登录流程讲一下」，按三段讲，别一段就结束。

1. 小程序端调 `wx.login()` → 拿到**临时登录凭证 code**，回传给你自己的服务端；
2. 服务端用 code 调 `auth.code2Session` → 换回 **openid、unionid（若已绑定开放平台）、session_key**；
3. **服务端根据 openid 找到（或创建）自己的用户，签发自己的登录态**（token / session），返回给小程序。

第 3 步才是"登录"。前两步只是"证明你是微信里的哪个用户"。

一句话答法：**微信负责认人，登录态是你自己的事。**

### 2. code 的四条硬规则

| 规则 | 依据 |
| --- | --- |
| **只能用一次** | 官方原文：「临时登录凭证 code 只能使用一次」 |
| **有效期 5 分钟** | `wx.login` 返回参数说明：「用户登录凭证（有效期五分钟）」 |
| **必须服务端换** | code2Session 要带 appid + secret，secret 一旦进前端就等于公开 |
| **session_key 不下发** | 官方原文：「开发者服务器不应该把会话密钥下发到小程序，也不应该对外提供这个密钥」 |

第 4 条要多讲一句原因：**session_key 是"对用户数据进行加密签名的密钥"**。旧版解密手机号、用户信息全靠它——谁拿到 session_key，就能解开这个用户的所有密文数据。

再补一个反直觉的点：**同一用户同一时刻只有一个有效的 session_key**（官方原文）。所以：

- 用户在另一台设备或另一次 `wx.login`，会生成新的 session_key 把旧的**顶替失效**；
- 顶替不只是 `wx.login` 触发的——官方在 `checkSession` 页面明确写了，**「数据预拉取」也会触发获取 code，从而让旧 session_key 失效**。

这就是"解密偶发失败"最常见的真凶：你以为 session_key 还在，其实早被另一次取 code 的操作顶掉了。

### 3. openid / unionid / session_key 三者分工

| 字段 | 是什么 | 用在哪 | 关键注意 |
| --- | --- | --- | --- |
| `openid` | 用户**在该小程序内**的唯一标识 | 建唯一索引、绑用户表 | 换了 AppID 就变了 |
| `unionid` | 用户在**微信开放平台账号下**的唯一标识 | 同一主体多应用（小程序 / 公众号 / App）打通账号 | **只有小程序绑定了微信开放平台账号才会返回**，没绑就是 `undefined` |
| `session_key` | 会话密钥 | 只在服务端存，用于解密与签名校验 | 会过期、会被顶替、绝不下发 |

面试加分点：**如果你的系统有多个小程序或公众号，用户体系的主键应该用 unionid（或自己生成的 uid），openid 只作为"某个端上的身份"存在。** 只用 openid 做主键，同一个用户在不同端会被建成多条记录——这就是很多"同一人领了两次新人券"的根因。

### 4. 手机号：新版拿 code 换，旧版才解密

这里有两个版本，面试一定要能分清，因为还在一堆老项目里写旧链路。

**新版（基础库 2.21.2 起，当前推荐）**

- 小程序端用 `button` 的 `open-type="getPhoneNumber"`，用户点击同意后回调里拿到 `e.detail.code`；
- 前端把 code 发给自己的后端；
- 后端调 `POST https://api.weixin.qq.com/wxa/business/getuserphonenumber?access_token=xxx`，用 code 换回真实手机号。

官方说明：**每个 code 只能使用一次，有效期 5 分钟**。

**旧版（老的 encryptedData 链路）**

回调返回 `encryptedData` + `iv`，后端用 `session_key` 做 AES-128-CBC 解密（PKCS#7 padding），解出来是 JSON，末尾带 `watermark.appid`——**必须校验 appid 是不是自己的**，防止拿别的小程序的密文来重放。

我把这条链路实跑了一遍，几个能直接引用的结论：

```js
// session_key 是 base64 的 16 字节 → 所以是 AES-128-CBC，不是 AES-256
Buffer.from(sessionKey, 'base64').length   // 16
Buffer.from(iv, 'base64').length           // 16
// 用错 session_key 解密不会给你"看起来能读"的数据，直接抛错
// crypto: ERR_OSSL_BAD_DECRYPT error:1C800064:...:bad decrypt
// 解密成功后 watermark.appid 与自己的 appid 一致才可信
```

**为什么新版更好**（这三条就是标准答案）：

1. 前端全程不接触任何密文，手机号明文只在自己的服务端出现；
2. 后端不用再维护 session_key 与用户的对应关系——旧版解密失败的头号原因就是 session_key 被顶替或过期；
3. 敏感数据少一次传输。

两个必须记住的边界：

- **`getPhoneNumber` 的 code 只能换手机号，不能换 openid**。要 openid 还是得走 `wx.login`。
- **头像昵称走"头像昵称填写能力"**：`button open-type="chooseAvatar"` 拿头像，`input type="nickname"` 拿昵称。`wx.getUserProfile` 从 **2022-10-25** 起被收回，新版本调用**不报错**，只是静默返回默认灰色头像和"微信用户"这个昵称——线上悄悄退化成假数据，这是最坑的地方。

### 5. 登录态怎么维持：双 token + 无感刷新 + 并发排队

单 token 的两难：有效期给长不安全，给短用户老被踢。所以拆成两个职责不同的令牌。

| | `access_token` | `refresh_token` |
| --- | --- | --- |
| 用途 | 每个业务请求都带 | 只用来换新的 access_token |
| 有效期 | 短（常见 2 小时） | 长（常见 7~30 天） |
| 存储 | 请求头 | 单独 key 存，加密或绑定设备标识 |

然后是三个真正体现"做过"的工程细节：

**① 无感刷新。** 收到 401 不要直接跳登录页，而是拿 refresh_token 静默换一个新 access_token，**然后重试原请求**。用户正在填的表单不能因为 token 过期就丢——这一点特别容易在真机上翻车。

**② 刷新必须串行化。** 页面首屏并发 5 个请求同时 401，就会触发 5 次刷新；后发的把先发的作废，前面几个请求全挂。标准做法是**全局唯一刷新 Promise**：第一个请求触发刷新时把 Promise 存下来，其余请求 `await` 同一个 Promise，刷新完统一重试。

```js
let refreshPromise = null;

async function ensureFreshToken() {
  // ✅ 并发时都复用同一个刷新 Promise，只发一次刷新请求
  if (!refreshPromise) {
    refreshPromise = requestRefresh().finally(() => { refreshPromise = null; });
  }
  return refreshPromise;
}
```

**③ refresh_token 轮转（rotation）。** 每次刷新都签发一对新令牌，旧的立即作废。这样被偷走的 refresh_token 只要用户正常使用过一次就失效了，服务端还能把"已作废令牌被再次使用"当成一个高价值异常信号来告警。

再配三条兜底（都是线上真实踩过的）：

- **改密码 / 登出要能按会话吊销。** 服务端维护独立的会话表，别把 token 直接塞在 user 表的一个字段上——否则"B 手机改了密码，A 手机还能继续下单"。
- **刷新失败先重试一次，仍失败才登出。** 网络抖一下就把用户踢回登录页，是最招骂的一类 bug。
- **判断过期用服务端时间戳**，别信客户端时钟。

顺带一个经常被追问、又特别容易混的点：上面说的 `access_token` 是**你自己签发**的登录态；而服务端调微信服务端接口要用的那个 `access_token` 是**微信下发的、全局唯一的**，有效期 7200 秒（官方另有 `stable_token` 接口）。后者必须在服务端集中缓存、提前刷新（也就是常说的"中控"模式），否则多实例各刷各的会互相顶掉，表现为接口随机报 token 无效。两个 `access_token` 同名不同物，别答混。

### 6. 该静默就静默，该授权才授权

**静默登录**：小程序启动就 `wx.login` → 服务端拿 openid 找用户 → 找到就直接下发 token。整个过程**没有任何授权弹窗**，用户完全无感。

为什么这么设计？因为 openid 已经能唯一标识用户，弹窗打断用户是不必要的；更何况 `getPhoneNumber` 这类能力**必须用户主动点击触发，不能静默获取**。所以正确的姿势是"**先静默登录，用到个人信息时再按需授权**"——一进小程序就弹手机号授权，既不合规也掉转化率。微信回收 `getUserProfile` 的官方理由就是这个：太多小程序在用户刚打开、或者支付前这种不合理路径上强制要授权，拒绝就不可用。

**然后是 `wx.checkSession` 的真相**，这题很容易答错：

- 它校验的是**最后一次获取 code 操作对应的那个 session_key**，不是"你手里存的任意一个 session_key"；
- 要校验指定的 session_key 是否有效，得在**服务端**调 `checkSessionKey`；
- session_key 的过期规律由微信维护、对开发者透明——用得越勤越不容易过期；触发取 code 的操作会生成新 session_key 顶掉旧的。

所以实践上有两条路，我更推荐第二条：

1. 经典写法：`wx.checkSession` 失败就 `wx.login` 重新换；
2. **不主动 check，让服务端在解密/校验失败时返回特定错误码，前端收到再静默重新登录**。少一次无意义往返，也不会因为"最后一次 code 对应的 session_key"这个语义而产生误判。

### 7. 安全边界：小程序端不是安全边界

这句话一定要说出口：**小程序代码可以反编译、可以调试、可以抓包，所以前端传来的任何身份字段都不可信。**

清单：

- `AppSecret` 绝不能出现在小程序代码里——混淆也没用，反编译就能拿到；
- `session_key` 不下发、不落日志，存 Redis 时单独一个 key；
- 用户身份一律以**微信服务端返回的** openid / unionid 为准，不看前端传的 userId；
- 全站 HTTPS；写操作加防重放（一次性 nonce + 时间戳窗口）；
- 登录态和业务缓存分 key 存，清缓存别顺手把登录态清了（用户会莫名被登出）；
- 鉴权统一在请求中间件里做（从 Header 取 token、查会话表、把 userId 注入上下文），业务代码里别再手写判断；
- 前端的按钮隐藏、路由拦截只是 UX，**接口必须逐个校验**——token 是可以被伪造和重放的。

## 其实你每天都在用

- 打开任何小程序，不点任何"允许登录"就能看内容——这就是静默登录在跑。
- 一到下单、领券、开会员才弹手机号授权——这就是"按需授权"。
- 好几天没打开的小程序，第一次进去会慢半拍——后端在重新跑一次 `code2Session`。
- 你在 A 手机改了密码，B 手机上的小程序过一会儿自动退出——这是按会话吊销。
- 点"换头像"时弹出来的是微信头像候选列表——`chooseAvatar`。
- 填昵称时输入框上方自动带出你的微信昵称——`input type="nickname"`。
- 同一个小程序在微信里进和在 App 里进，账号能对上——unionid 的功劳。
- 前端最熟的那段代码：请求拦截器里"401 就刷新、刷新失败就跳登录"——本质就是这套东西。

## 常见误解（FAQ）

**❌ 误区1："小程序的登录态就是 session_key。"**
session_key 是**微信给你的会话密钥**，不是登录态。它是用来解密和校验签名的，不能下发、也不能当 token 用。真正的登录态是你自己服务端签发的那个 token。

**❌ 误区2："code 可以缓存下来重复使用。"**
一次性的，用完即废；有效期 5 分钟。拿同一个 code 再换一次会直接报错。

**❌ 误区3："前端可以直接请求 code2Session。"**
不行。这个接口需要 appid + secret，secret 只应该存在于你的服务端。前端调用等于把密钥公开。

**❌ 误区4："有 openid 就够了，不用管 unionid。"**
单端够用，多端就出问题：同一主体的小程序 + 公众号 + App，只用 openid 会变成三个独立账号。绑了开放平台就该用 unionid 打通。

**❌ 误区5："获取手机号还是用 encryptedData 解密。"**
那是旧版。当前推荐 `open-type="getPhoneNumber"` 拿 code、服务端用 code 换手机号；旧版解密链路只在维护老项目时还要用，且必须校验 `watermark.appid`。

**❌ 误区6："用户拒绝授权手机号，小程序就不能用了。"**
openid 已经能标识用户，浏览、加购、看订单这些都不需要手机号。强制授权既不合规也掉转化率——微信回收 `getUserProfile` 就是为了治这个。

**❌ 误区7："access_token 过期就直接跳登录页。"**
体验灾难。正确做法是静默刷新 + 重试原请求，而且刷新必须全局唯一、串行化，否则并发场景下会出现"刷新互相覆盖、请求全挂"。

**❌ 误区8："前端把按钮藏起来就等于做了权限控制。"**
前端隐藏只是 UX 优化。接口必须逐个校验——token 能被伪造、能被重放，鉴权只能在服务端做。

## 一句话总结

小程序登录的本质是**「微信认人（code → openid / session_key）＋ 自己发牌（服务端签发双 token）」**；把 code 一次性且 5 分钟、session_key 绝不下发、静默登录按需授权、并发刷新串行化这四条讲清楚，这道题就满分。
