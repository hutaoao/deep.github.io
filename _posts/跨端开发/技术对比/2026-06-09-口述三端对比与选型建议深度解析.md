## 一句话概括

面试官问"RN/Flutter/ArkUI 怎么选"，不是在考你偏好，而是在考你的技术决策能力——能否在"动态化""跨端一致性""原生集成深度"这三角中，根据场景给出有理有据的判断。


## 核心知识点

### 1. 三个框架的本质定位

```js
// RN：我是"原生组件的调度者"，JS 驱动原生
// Flutter：我是"像素的主人"，Skia/Impeller 自己画
// ArkUI：我是"鸿蒙的亲儿子"，NAPI 直通系统底层

// 一句话记住：
// RN 的动态化成本 = 0（CodePush 即插即用）
// Flutter 的 UI 一致性 = 100%（同一渲染引擎到处跑）
// ArkUI 的系统集成 = 无感（不存在 Bridge/PlatformChannel 等中间层）
```

### 2. 动态化能力对比

```js
// RN：CodePush 上线 6 年了，成熟度拉满
// 线上出 bug → 热修 js bundle → 用户无感知更新

// Flutter：2026 年了仍然没有官方热更新
// Shorebird（第三方）≈ CodePush 体验，但按 App 计费
// 路由方案（如 fair、mxflutter）≈ 小程序套壳，非真正热更新

// ArkUI：HAP 更新受华为应用市场策略约束，自由度受限
```

### 3. 团队匹配度速查

```js
// React/Web 团队 → RN，React 知识 ≥70% 直接迁移
// 原生 iOS/Android → Flutter，Dart ≈ Java/C#，Widget ≈ 原生布局思想
// 零基础 → Flutter，封闭体系学完就能独立做 App
// 大厂渐进迁移 → Flutter Add-to-App（Module 嵌入）体验远好于 RN 混编
```

### 4. 坑与真相

```js
// ❌ "Flutter 性能一定比 RN 好" → 大部分场景差距感知不到，纯列表两者都 60fps
// ❌ "RN 只能做简单 App" → Discord/Shopify/Walmart 都用 RN 跑核心业务
// ❌ "鸿蒙适配选 Flutter 就行" → 如果你主要服务鸿蒙用户，ArkUI 的体验差距不是 10% 而是 50%
// ✅ 真实差距在边界场景：复杂动画（Flutter 胜）、原生嵌套（RN 胜）、系统集成（ArkUI 胜）
```

### 5. 选型决策树

```
需要每天发版/运营活动频繁？
 ├─ 是 → RN（CodePush）
 └─ 否 → 只服务鸿蒙？
          ├─ 是 → ArkUI
          └─ 否 → 需要 Web + Desktop？
                  ├─ 是 → Flutter
                  └─ 否 → 团队有 React 背景？→ RN | 否则 → Flutter
```

## 其实你每天都在用

- **闲鱼的 Flutter 混编**：淘宝系最先大规模上 Flutter 的 App，你的每一次闲鱼浏览背后都是 Flutter Widget → Skia 渲染
- **React Navigation**：跟 Vue Router / React Router 思路一致，push/pop 调用就是桥接原生 UINavigationController
- **RN 的 StyleSheet**：本质就是 CSS-in-JS，你用 `flex: 1` 和写 CSS 一样，但最终转成了原生 Yoga 布局
- **Hermes 引擎**：你在 RN 里写的每一个 `setState`，运行时都是由 Meta 专门为移动端裁剪的 JS 引擎执行的
- **ArkUI 的 @State 装饰器**：跟 Vue 的 `ref()` / React 的 `useState` 同类概念——数据变了 UI 自动刷新，但底层走的是方舟编译器的响应式图

## 常见误解（FAQ）

**❌ 误区一：Flutter 性能碾压 RN**

这是一个被过度简化的说法。在标准列表滚动、表单输入等常规场景，RN Hermes + Fabric 新架构帧率几乎和 Flutter 持平。Flutter 的真正优势在**极端自定义 UI**（如 Lottie 级动画、粒子效果），而不是日常业务页面。面试时如果只说"Flutter 比 RN 快"而不区分场景，说明你只是复读结论。

**❌ 误区二：ArkUI 没有跨端价值**

这个角度把"跨端"理解得太窄了。ArkUI 虽然只跑在鸿蒙上，但它跨的是**鸿蒙生态内的设备**——手机、平板、手表、车机，一套代码同步适配。这是另一种维度的"跨端"。

**❌ 误区三：选 Flutter 就是放弃了动态化**

不完全。2026 年的 Flutter 生态已经有多种折中方案：服务端下发 DSL 模板 + Flutter 解析渲染（类似小程序思路）、Feature Flag 控制功能开关、以及 Shorebird 的商业方案。只是没有 RN CodePush 那么"零成本"，不是没有。

**❌ 误区四：Flutter 不适合嵌入原生 App**

这可能是 2020 年前的老印象。Flutter Add-to-App（从 1.12 开始支持）已经非常成熟，一个 Module 就是一个独立 Flutter 页面，原生和 Flutter 可以无缝跳转。国内闲鱼、得物的实践已经验证了这条路径。

## 一句话总结

选框架不是在做技术竞赛，而是在做**约束条件下的最优解**——你的团队、你的发布节奏、你的平台目标、你的 UI 复杂度，这四个约束比"哪个框架快"重要得多。
